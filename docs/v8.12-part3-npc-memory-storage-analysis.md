# V8.12 Part 3 前置分析：CK3 NPC Memory 存储结构

## 文档性质

本文是 V8.12 第三部分的前置勘探记录，不是实施报告，也不代表第三部分已经施工完成。

本次仅对实际 CK3 存档和本机 CK3 类型定义进行只读分析，没有修改 Save、没有把 Save 或日志复制进仓库，也没有修改应用代码。

## 分析范围与证据

本次检查的对象是项目当前使用的 CK3 autosave.ck3 的 gamestate 文本内容，检查时游戏日期为 1161.1.1。

同时对照了同一局较早的 autosave_2.ck3（游戏日期 1159.1.1），以及 CK3 的：

~~~
game/common/character_memory_types/character_memories_1.txt
~~~

类型定义文件。

当前项目的 Save 容器读取位于 resources/app/out/main/worldline/save-container.js，GameState 字段适配位于 resources/app/out/main/worldline/game-state-adapter.js。现有适配器已处理人物、头衔、战争等数据，但尚未完整解析 character_memory_manager。

## 核心结论

character_memory_manager 是一个全局 Memory 数据库：

~~~
character_memory_manager.database[Memory ID] -> Memory 实例
~~~

Memory 实例本身没有直接的 owner 或 holder 字段。NPC 持有关系通过人物记录反向表达：

~~~
Character.alive_data.memories -> Memory ID 列表
~~~

因此，Part 3 不能只扫描 character_memory_manager.database，必须同时建立 Memory ID -> holder Character ID 的反向索引。

## 八项问题结论

### 1. Owner / holder Character ID

管理器条目中没有 owner 字段。实际关系是：

~~~
Character.alive_data.memories -> Memory ID
~~~

例如 #50534 的 alive_data.memories 包含 7237，所以 7237 的 holder 是 #50534。

### 2. Memory type / category

每条实例直接保存 type：

~~~
type=lost_title_memory
type=joined_allys_war
type=hanfan_zhiguan_xunguan_memory_1
~~~

categories 不重复保存于每条实例，而属于 CK3 的 Memory 类型定义。例如：

~~~text
imprisoned={
    categories={ negative prison intimidation }
    participants={ imprisoner }
    duration={
        years=memory_default_duration
    }
}

joined_allys_war={
    categories={ war martial alliance war_started }
    participants={ ally enemy }
    duration={
        years=memory_default_duration
    }
}

lost_title_memory={
    categories={ negative title }
    participants={ new_holder }
    duration={
        years=memory_default_duration
    }
}
~~~

### 3. Event date / created date / duration / expiry

Save 实例实际保存：

~~~
creation_date=1141.8.5
end_date=1271.8.5
~~~

没有单独的 event_date 或 created_date 字段。当前 UI 已知记录的显示日期与 creation_date 一致，但不能因此断言所有 Memory 的事件发生时间都必然等于 Memory 创建时间。

duration 来自类型定义，end_date 是计算后写入的到期日期。当前实例没有单独的 expiry 字段。

### 4. Participants

participants 是可选结构，键名表示角色语义，值是 Character ID，例如：

~~~text
participants={
    ally=50979
    enemy=49490
}
~~~

已确认的角色键还包括 imprisoner、new_holder、other_party 等。自定义 hanfan_* Memory 可以没有 participants。

### 5. Title / war / position / character 结构化参数

当前 Save 中确认存在：

| 类型 | Save 表现 | 含义 |
|---|---|---|
| Character | type=char identity=... | 角色 ID |
| Landed Title | type=lt identity=... | 头衔 ID |
| Value | type=value identity=... | 数值 |
| Flag | type=flag flag="..." | 原因或枚举 |
| Boolean | type=boolean identity=... | 布尔值 |

战争信息没有发现直接的 type=war 对象。战争 Memory 主要通过 Memory 类型、participants 和 war_* 变量表达。

当前 manager 数据中没有发现 type=position、type=office 或类似职位对象。自定义官职 Memory 的职位含义可能只存在于类型名和本地化中。

### 7. 不同 NPC 是否引用同一个事件

当前 autosave.ck3 的统计结果：

| 指标 | 数值 |
|---|---:|
| manager Memory 条目 | 78,739 |
| 角色 Memory 引用 | 75,803 |
| 引用缺失 | 0 |
| 被多个角色共同引用的 Memory ID | 0 |

同时发现不同 NPC 之间存在 type + creation_date + end_date + variables 完全相同、但 Memory ID 不同的记录。

因此当前证据支持：

> 同一底层事件如果被多个 NPC 记住，会分别生成独立 Memory；Save 中没有可用于跨 NPC 共享的事件 ID。

后续实现必须保留 holderCharacterId 和 memoryId，不能把相同内容的 Memory 直接合并成一个公共事实。

### 8. Memory 消失后的 Save 行为

对比同一局：

- autosave_2.ck3：1159.1.1
- 当前 autosave.ck3：1161.1.1

旧存档中有 2,511 条在两个检查点之间到期的 Memory，全部不再出现在新存档的 character_memory_manager.database 中。

当前没有发现：

~~~
expired=true
status=expired
tombstone
~~~

因此，在当前 CK3 版本和这组存档中，Memory 到期后的行为是：

> 从 manager 数据库物理删除，而不是标记 expired，也不是保留 tombstone。

当前 Save 仍存在一部分没有角色反向引用的 manager 条目，但它们是未引用的完整 Memory 记录，不能直接视为 expired tombstone。

## 对 Part 3 的直接影响

后续正式施工应遵守以下边界：

1. 解析全局 character_memory_manager.database，建立 memoryId -> memory。
2. 扫描所有角色的 alive_data.memories，建立 memoryId -> holderCharacterId。
3. 保留 Memory ID、holder、participants 和 typed variables，不能只保留中文摘要。
4. 将“事件去重指纹”和“NPC 知识持有关系”分开：相同事件可以有多个独立 NPC Memory。
5. 对 lost_title_memory 优先读取 landed_title、lost_titles、new_holder 和 creation_date，用于历史头衔变化验证。
6. 对自定义 hanfan_* 类型设置类型定义/本地化解析；没有结构化头衔或职位 ID 时必须标记证据不足，不能猜测。
7. 在 Memory 到期前进行 Shadow 归档，否则到期后的 Save 无法恢复该 Memory。
8. 将 Memory 作为 NPC 的主观知识证据，而不是直接当作全局 Current Runtime Truth。

## 当前限制

- 本文分析的是指定 Save 快照和当前本机 CK3 类型定义，不代表所有 CK3 版本、DLC 或 Mod 都完全相同。
- hanfan_* 自定义 Memory 的完整类型定义和本地化不在当前 Save 实例中，需要在后续施工阶段继续定位其 Mod 源文件。
- 本文没有修改 game-state-adapter.js，因此应用目前还不能通过正式 Worldline DTO 使用这些 Memory 数据。
