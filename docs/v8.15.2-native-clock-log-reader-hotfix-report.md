# V8.15.2 独立日期桥与日志读取器热修

日期：2026-10-08。主代理保持客户端选择；实现支线与独立 QA 使用 GPT-6 Luna Max。世界记忆 CURRENT_DATE 已由用户实机确认，本轮不修改该模块。

## 事故定案与 V7 对照

用户再次实测一个月，Tracker/Reconciled 为空，A1/A2 为 RUN_FILE_NOT_EXECUTED。Payload 日是发信时的固定日，不应改成持续日期；真正需要推进的是 Tracker 当前日。

只读 App 日志显示启动监听后进入 Restarting，之后整段测试都没有 Stopped/Started 完成记录。与此同时 CK3 日志实际写出了三次 A2 的 LETTER_TRANSPORT/B 和对应 RUN_ACK；App 没读到执行证据不能等同于 CK3 没执行。对话结束后的保留日志未见持续 DATE 或 letters.txt 执行，因此还存在独立日期/非对话执行入口缺口。日志被游戏主动清除，不能据缺少 LOAD 推断启动钩子一定未调用。

旧库真实复现：@logdna/tail-file 在消费者关闭前积压超过高水位，quit() 等待 flush；但没有消费者排空，stopLogTailing 在 150ms 检测期限内不返回。这是对真实旧库与真实 Manager 的可复现停止阻塞，不是模拟状态机定案。deadline 只证明期限内未返回，结合代码的 flush 等待解释持续 RESTARTING。此前父 widget 热修不足以解决本轮事故。

按用户要求复读 [V7.10 官方动作/信件恢复报告](v7.10-official-action-letter-recovery-implementation-report.md) 的 RC6 Final Rev2/Rev3：正式投递固定走 votc.txt 持久队列；letters.txt 仅兼容日期/旧诊断；A1/A2 只以唯一执行标记判定，与日期推进无关，后续诊断还需逐项执行与可见结果。未知写入无 ACK 为 STALLED，不盲目回放。以上成功合同保持，本次替换失败的日期入口和监听生命周期。

## 实现

- 新增 letters/letter-log-reader.js 并在 main.js 注入：启动定位当前 EOF，只读取后续完整行；每批最多 64 KiB、打开/读取/关闭，停止不等待 flush，不持有长期文件句柄。UTF-8 与半行由 reader 保留；轮转、截断或已读锚改写时清除半行并重新定位 EOF，避免把旧 payload/ACK 当成新输入。
- LetterManager 的 start/stop/restart 串行；先退役旧 reader 再关闭 readline，旧回调、错误与 reset 不影响新 reader。日志 reset 清会话、日期及扫描缓存，继续保留物理 LOAD 边界、ACK ID/kind、队列和接受锁合同。
- Mod 新增 registry、全局透明 widget 与只读 scripted GUI。两秒循环直接读取 CK3 日期并写出原 rich DATE 协议，不依赖 letters.txt、votc.txt、信件事件窗口或 after-lobby 的创建时机；对话中也读取日期。非对话时通过原 console Run File 入口轮询正式队列；对话时文件留给原对话 consumer，避免两个执行入口竞争。
- 新桥注册后旧 letters_runner 暂停重复轮询，未注册时保留后备。load epoch 首次递增前显式 set=0，修复未设置变量警告。未改变官方 Artifact Effect、接受弹窗、去重与接收后摘要。

原版 _scripted_widgets.info 明确自动创建 registry widget；当前 Mod 的场景选择器与本机汉番礼制已有相同机制。原版 console.gui 有 ExecuteConsoleCommand，汉番礼制有双状态循环执行 ScriptedGui 的实例。未找到本机 debug_log 在 scripted GUI 内的既有正例：此组合合理但仍必须验证 CK3 引擎实际执行，不把静态语法/模型当作实机通过。
