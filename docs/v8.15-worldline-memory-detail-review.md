# V8.15 世界线与 Memory4 逐链路审查报告

审查日期：2026-10-06。基线 HEAD：`69dbfe0b617e00da7a55e73783233c514af34d8c`，包含工作区尚未提交的 V8.15 修复1.1。本轮只审查并编写报告，未修复生产代码、修改测试或迁移用户数据。实现模型沿用客户端；三条独立审查支线使用 GPT-6 Luna Max。

后续修复入口：[V8.15.1 实施报告](v8.15.1-implementation-report.md)。本文保留修复前证据；用户随后明确姓名只保留主体绑定、不新增 NAME 披露类型，并要求优化自报和他人直接公开头衔/特质。

## 结论

世界线能够读取当前 autosave 的人物、头衔、战争及身份绑定，但不能据此认定所有字段正常：确认新存档的信仰字段未适配，文化数值 ID 未转换为有效文化标识。另有关系空值兼容问题。

Memory4 当前文件没有发现索引与正文不一致，但确认快照失败恢复、提交后派生恢复、canonical-only 召回及前端旧正文回流四处缺口。以下七项分为一项 P1、六项 P2；没有在本轮证明 P0，但也不作“所有其他路径无 bug”的保证。

用户补充的“自报姓名、头衔仍无披露”另列专项：当前保存的 34 条人物认知中披露事实总数确为 0。姓名并非现有 TITLE/TRAIT/AGE 披露类型；头衔失效需要区分句式、Owner 方向、事实候选和终局状态，不能直接认定只是界面问题。

## 已确认问题

### W1 / P1：新存档的 rite 信仰链未接入世界线

- 位置：[game-state-adapter.js](../resources/app/out/main/worldline/game-state-adapter.js#L168)，人物字段白名单及 `faith: scalar(fields.faith)`；根级白名单第 360 行也未读取 `rites`、`faiths`。
- 实际存档：44,210 名 living 角色均有 `rite`，直接 `faith` 字段为 0。`rites.database` 有 194 个记录，`faiths.database` 有 140 个记录；存在可解析的 `character.rite -> rites.database[id].faith -> faiths.database[id].faith_type` 链。该链没有进入当前适配器。
- 合成复现：角色 `rite=34`，rite 34 的 `faith=100`，faith 100 的 `faith_type=taoism`。使用生产 `parseGameState` 后，角色 `faith=null`；`getCurrentTruth(..., "faith")` 返回 `CURRENT_TRUTH_VALUE_UNAVAILABLE`，解析诊断仍为 `missingFields=[]`、`parseWarnings=[]`。
- 影响：存档世界线的信仰事实缺失且诊断没有显式报告该字段覆盖缺口。debug.log 的当前在场角色可以另有宗教数据，不能扩大为“整个应用所有宗教均不可用”。
- 建议：按真实存档模式补齐 rite/faith 关联、确定性标识和展示转换；对大量人物系统性缺失的字段记录覆盖诊断。不可猜测人物信仰或借历史 Definition 补成游戏当前事实。

### W2 / P2：文化 runtime ID 直接进入事实与 Prompt

- 位置：[game-state-adapter.js](../resources/app/out/main/worldline/game-state-adapter.js#L187)、[current-truth-adapter.js](../resources/app/out/main/worldline/current-truth-adapter.js#L22)、[world-knowledge-classifier.js](../resources/app/out/main/worldline/world-knowledge-classifier.js#L76)、[subjective-prompt-context.js](../resources/app/out/main/worldline/subjective-prompt-context.js#L32)。适配器保留数值字符串，根级未解析 `culture_manager`，展示层和 Prompt 沿用原值。
- 实际快照：78,995 个非空 culture 值全部为数值字符串；原始存档 `culture_manager.cultures` 有 `name`、`culture_template` 等映射字段。
- 合成复现：人物 `culture=17`，culture 17 对应 `name=han`。通过生产解析、事实分类、主观视图及 Prompt 格式化后，出现 `Fixture当前文化为17`，没有得到 canonical `han`。不是仅仅管理界面的显示问题。
- 影响：世界线虽然有 culture 字段，输出却不能提供准确可用的文化身份。建议将 runtime ID、canonical key 和本地化展示分开，映射缺失保持未知。

### M1 / P2：Owner 快照构建失败后没有可重试任务

- 位置：[memory-engine.js](../resources/app/out/main/memory-system/memory-engine.js#L1279) 先提交叙事摘要并删除叙事 recovery，再在第 1309 行后启动 Memory4；[memory4-coordinator.js](../resources/app/out/main/memory-system/memory4-coordinator.js#L983) 的 `buildOwnerSnapshot` 在 `finishOwner` 保存 PENDING 之前执行，外围 catch 仅返回 `EXTRACTION_FAILED`。
- 合法上下文复现：临时 MemoryEngine、两个 Owner、正常同场 spoken fragments、有效日期，仅让第一次 `store.filterForgottenSnapshot` 抛出一次模拟瞬态 I/O 错误，随后恢复原方法。结果为一个 Owner 抽取失败、recovery 文件 0、pending/manual/invalid 全为 0，`recoverPending` 找到 0 项。
- 影响：该 Owner 本场结构化抽取掉出恢复队列，普通“重试失败记忆”不能找到它。普通叙事和 Legacy 已保存，不是整场对话内容全部丢失。另有叙事 recovery 删除到首份 Memory4 recovery 落盘间的崩溃窗口。
- 建议：在叙事到逐 Owner 抽取的交接边界保留可验证恢复材料；非法来源须隔离并可诊断，而不是放宽授权。针对快照阶段瞬态失败及交接中退出添加故障注入回归。

### M2 / P2：重启恢复已提交 Detail 时不补调度 Year/Life

- 位置：[memory4-store.js](../resources/app/out/main/memory-system/memory4-store.js#L713) 持久化 `derivedDirty`；[memory4-coordinator.js](../resources/app/out/main/memory-system/memory4-coordinator.js#L864) 普通 `alreadyCommitted` 分支只补披露并删除 recovery。正常新提交第 967 行才调度派生；[memory4-derived.js](../resources/app/out/main/memory-system/memory4-derived.js#L283) 使用进程内异步调度。
- 复现：提交一条有日期的 observed Detail，保留 PENDING recovery，模拟 Detail 已落盘但派生未启动即退出；重新构造引擎后恢复。得到 `alreadyCommitted=true`、recovery 已删除、`derivedDirty=true`、`scheduleCalls=0`，Year/Life 均未生成。
- 影响：有合法事件日期的长期记忆也可能在重启后缺少年度和人生视图。Detail 本身保留，人工重建可补救。Legacy 重压缩的已提交分支另有重建处理，本发现针对普通终局恢复。
- 建议：已提交恢复与启动 dirty reconciliation 衔接，重建保持幂等、revision 校验及手工版本保护，不能仅删除任务后宣告恢复完成。

### M3 / P2：有效 canonical-only sidecar 被 Legacy 目录门禁挡住

- 位置：[memory4-recall-planner.js](../resources/app/out/main/memory-system/memory4-recall-planner.js#L296) 在找不到 `${ownerId}_*` Legacy 目录时提前返回 `OWNER_FOLDER_MISSING`；[memory4-store.js](../resources/app/out/main/memory-system/memory4-store.js#L124) 却明确支持独立 `.memory4/<owner>/<campaignHash>`。
- 真实 Store 夹具：只建立合法 canonical sidecar，owner/campaign/knownBy、index/body hash、source revision 和日期均通过。`loadIndex` 返回 revision 1，`readEntry` 正常读到 sentinel；Planner 返回 0 条。仅增加一个空 `2_fixture/` Legacy 目录后，同一条记录成功召回。
- 影响：Legacy 目录删除而 canonical 保留等场景会失去召回；没有由此发现跨 Owner/Campaign 泄漏。当前实机没有证明已处于此目录布局。
- 建议：用共享 Scope/目录解析合同判断 Canonical 是否可读，Legacy 无目录只关闭 Legacy lane；损坏索引仍须 fail-closed。

### M4 / P2：同 Owner 刷新后，迟到正文请求能回填旧缓存

- 位置：[memory4-manager.js](../resources/app/out/renderer/memory4-manager.js#L43) 列表 load 使用 `requestSequence` 并清空 entries；第 253 行正文请求只检查 `contextEpoch`。同 Owner 普通 load 不增加 epoch，因此旧请求仍被接纳。
- 复现：在内存中执行实际组件代码，模拟 React 状态与延迟 IPC。旧 revision 1 正文请求未返回时，刷新列表取得 revision 2、清空缓存；旧请求随后返回。结果 `freshCatalogRevision=2`、`displayedBodyRevision=1`，打开记录显示 `OLD_BODY`。
- 影响：刷新后的阅读和编辑入口可以显示过时正文；后端 expectedRevision 校验仍在，不据此宣称旧正文可无条件覆盖持久新版本。该复现是组件逻辑验证，不冒充本轮打包窗口验收。
- 建议：正文响应同时绑定列表请求世代或 index/entry revision；同 Owner 刷新与 mutation 也撤销旧正文请求。

### W3 / P2：关系字段的空值 0 可生成伪人物 #0

- 位置：[game-state-adapter.js](../resources/app/out/main/worldline/game-state-adapter.js#L190) 保留关系标量 `"0"`；[world-knowledge-classifier.js](../resources/app/out/main/worldline/world-knowledge-classifier.js#L92) 按字符串真值生成父母/配偶事实；`current-truth-adapter.js` 第 24 行及亲属图 ID 转换也接受它。
- 合成复现：`spouse=0`、父母或 liege 为空标量 0 时可以产生 `#0`。既有夹具使用过 spouse/liege 0，头衔层已有 de_facto_liege 0 的无上级语义。
- 影响边界：当前实机快照这些关系字段的 0 数量为 0，未证明此次存档受损；这是条件性存档兼容缺口。不得把所有数值 0 全局过滤，文化等枚举 ID 的 0 未必无效。
- 建议：按关系字段的 schema 归一化空引用，补齐事实层、Current Truth 和亲属图的共同测试。

## 人物披露专项与待补证据

1. 现有 `memory4-disclosure.js` 候选及 Store 校验只允许 TITLE、TRAIT、AGE，没有 NAME 类型。人物名字/昵称用于识别主体，并不等于一条“姓名已披露”的证据。用户自报姓名未显示为披露，属于现有能力缺口，不能假报已实现。
2. 披露是方向性的：玩家说“我是某头衔”，应保存在听到这句话的 NPC Owner 下，目标人物是玩家；不在玩家自己的 Owner 下再添加自己。扫描明确跳过 `entityId === ownerId`。
3. 当前记录在终局 `finishOwner` 成功抽取/提交后调用 `recordDisclosures`，并非每说一句立即持久化。若长期抽取失败，确定性披露也延后到重试；M1 场景还可能没有可重试材料。
4. 自动披露只匹配 CK3 当前事实候选及可证明的直接原话；第三人转述、否认、假设、歧义身份和过期 Fact Epoch 不授权。这些是保留的安全合同，不应为追求显示而全局放宽。
5. 当前真实保存的披露事实确为 0，说明不能仅把事故归为 UI 过滤。用户确认查看的是生成的人物文件夹中的人物认知页，并补充关闭游戏/Mod 后无法读取；尚未提供具体自报原话、文件夹对应的 Owner 及终局完成情况。本轮不读取真实对话正文或冒认实机根因。
6. **关闭后的可查看性不等于持久性。** [summaries-manager.js](../resources/app/out/main/summaries/summaries-manager.js#L273) 的 `getMemory4ReadContext` 要求仍有 conversation、已加载的 `gameData.characters` 和明确 Campaign。已结束但保留 GameData 的会话可以只读归档；完全没有该上下文时入口拒绝。Store 的 `known-entities.json` 才是持久披露载体，代码没有在关闭游戏时删除它。因此当前实现缺少独立离线选择可信 Campaign 的查看入口，但不能从“页面读不到”推出“此前披露被删除”。当前真实披露为 0，也没有可用记录证明该用户场景已保存后丢失。若扩展离线查看，须显式选择已持久 Campaign/Owner，不可跨战役拼接或伪造实时事实。

追加合成验证：当前候选为 `TITLE=皇帝`，玩家为 speaker、NPC 为 Owner，并有合法 spoken/knownBy/sourceRole=user 证据时，`我是皇帝。`、`我现在是皇帝。`、`我的头衔是皇帝。`、`我叫赵明，如今是皇帝。`、`本人乃皇帝。` 均命中头衔。不要求特殊引号。正常终局返回 `COMPLETE/NO_DURABLE_CONTENT` 后，披露为 `AUTO_DISCLOSED`、effectiveKnown=true；注入 Provider 抽取失败后为 `PARTIAL_FAILURE/EXTRACTION_FAILED`、disclosure=false，并保留 PENDING recovery。后一条与 M1 不同：M1 是快照构建更早失败，连 recovery 都未产生。此验证不使用真实 Provider，也未替代原子 rename。

这排除了“所有常见自报头衔句式都不支持”，但没有排除用户原话未匹配候选、查看方向错误或某段来源/终局异常。当前候选只有皇帝时，国王、王、旧头衔不能仅凭自称转成当前事实。姓名持久知情与独立离线档案浏览若要新增，应另有明确合同与 UI，不把它们冒充已实现的披露。
