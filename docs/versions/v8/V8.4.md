# V8.4 Luna + Terra：年度 Delta 对账矩阵

状态：已完成 S0→S1 的人物、Title、War 第一版对账矩阵；这是前置验证产物，不是正式 Delta Merger 或 Worldline Projector 的实现。

<a id="source-559744d91a89--证据等级"></a>
## 证据等级

- `CONFIRMED_BY_GAMESTATE`：两个 checkpoint 中存在直接、可重复读取的字段证据。
- `PARTIAL`：主事实已确认，但关系或事件时间仍需补充来源。
- `PROMOTED_TO_SUPPLEMENTAL`：GameState 不能充分重建，必须保留事件摘要或 delta。
- `RECONCILIATION_UNKNOWN`：当前样本不足以做可靠对账。

<a id="source-559744d91a89--矩阵"></a>
## 矩阵

| Delta 类别 | S0→S1 观察 | 当前结论 | 后续动作 |
| --- | --- | --- | --- |
| `CHARACTER_ALIVE_UPDATE` | 稳定 Runtime ID 的年龄、faith、location、positions 等字段可对比 | `CONFIRMED_BY_GAMESTATE` | 后续确定字段白名单与投影策略 |
| `CHARACTER_DIED` | 1,799 条 living→dead bucket 转移；死亡样本可读日期/原因 | `PARTIAL` | 补充事件顺序与死亡事件时间边界 |
| `NEW_CHARACTER/BIRTH` | 3,004 个 S1 新人物；其中玩家新子女 4 个，可读出生日期、dynasty、employer | `PARTIAL` | 父母关系当前未从新人物记录直接读出，不能仅凭 employer 强行替代亲子字段 |

<a id="source-262867f190b3--v84-ck3-save-容器与提取报告"></a>
# V8.4 CK3 Save 容器与提取报告

<a id="source-262867f190b3--1-样本"></a>
## 1. 样本

完整测试样本为用户指定的 `autosave_1.ck3`。仓库文档不保存用户机器的绝对路径，也不复制存档内容；以下尺寸、头部和 metadata 是本次只读勘探的脱敏结果。

<a id="source-262867f190b3--2-头部判定"></a>
## 2. 头部判定

| 项目 | 结果 |
| --- | --- |
| 文件大小 | 229,445,646 bytes（约 218.82 MiB） |
| magic/version | `SAV0100` |
| kind | 0，`TEXT_UNCOMPRESSED` |
| envelope header | 24 bytes |
| metadata length | `0x9583` = 38,275 bytes |
| body start | byte offset 38,299 |
| body size | 229,407,347 bytes |
| ZIP signature | 未发现 `PK\\x03\\x04` 或 `PK\\x05\\x06` |
| body 编码 | UTF-8 可解码；未发现 replacement character |
| Ironman | `no` |
| 分类 | `PLAIN_TEXT_SAVE` |

kind 0 使本样本可以直接按 `headerLength + metaLength` 定位 Gamestate。它不是需要从 ZIP entry 中解压的样本，因此本轮未执行 ZIP entry stream；不能据此宣称 ZIP 路径已经通过。

<a id="source-262867f190b3--3-metadata-与-body-一致性"></a>
## 3. metadata 与 body 一致性

解析到的 metadata 包含：

- `save_game_version=15`
- `version=1.19.0.6`
- `meta_date=1154.1.1`
- `meta_player_name` 为存档中的当前玩家名称
- `meta_title_name` 为存档中的当前领地名称
- `ironman=no`

body 的 `/date` 和 `playthrough_id` 可直接读取，body date 同样为 `1154.1.1`。metadata/body 日期一致，但这只证明该文件的内部一致性，不证明文件当前仍是游戏进程最新状态。

<a id="source-262867f190b3--4-同目录轮换观察"></a>
## 4. 同目录轮换观察

同一 save games 目录共发现 21 个 `.ck3`。其余文件仅做头部/metadata 快照：当前目录同时存在 `TEXT_UNCOMPRESSED` 与 `UNIFIED_TEXT_ZIP`，所以不能把文件名或扩展名当作容器类型。

快照中按文件修改时间最新的文件为 `autosave_2.ck3`，其 metadata date 为 `1155.10.26`；`autosave.ck3` 为 `1155.1.1`；指定样本 `autosave_1.ck3` 为 `1154.1.1`。这支持“读取后按 header + metadata date + fingerprint 排序”的建议，但一次目录快照不能证明 CK3 autosave rotation 的完整规则。

<a id="source-262867f190b3--5-ironman-与安全边界"></a>
## 5. Ironman 与安全边界

指定样本 `ironman=no`，本次没有触发 `IRONMAN_BLOCKED`。正式 adapter 仍必须先检测 kind、Ironman 和异常/截断文件，再决定是否进入解析；不能把普通文本解析失败当成 Ironman 失败，也不能把 ZIP 读成功当成内容可信。

<a id="source-262867f190b3--6-交叉核对与未覆盖项"></a>
## 6. 交叉核对与未覆盖项

头部字段布局与 Jomini 上游的 SaveHeader/envelope 实现交叉核对：[SaveHeader 字段解析](https://raw.githubusercontent.com/rakaly/jomini/master/src/envelope/header.rs)、[文件与 metadata/gamestate 范围处理](https://raw.githubusercontent.com/rakaly/jomini/master/src/envelope/file.rs)。

未覆盖项：ZIP entry 的实际解压耗时、binary kind、split save、Ironman 加密样本、损坏/截断样本。它们必须在正式 parser 选型前用独立 fixture 或额外样本验证。

# V8.4 Terra：Duplicate Definition ID / Mod Override 验证

状态：`PARTIAL`。已读取当前 Launcher active playset、源定义和 S0 Gamestate；没有证据支持由 VOTC 猜测 CK3 的最终覆盖 winner。

<a id="source-00f31acec715--方法与边界"></a>
## 方法与边界

- 只读读取 `launcher-v2.sqlite`：当前 active playset 有 54 个已启用 Mod，其中 6 个提供 `history/characters` 源目录。
- Launcher 原始 position 为零基：溥天之下更多剧本与兵种 `3596186602` 为 16，Oriental Empires `2506311074` 为 35。position 仅证明 Launcher 保存的排序元数据，不在没有 CK3 resolver 输出或受控新局的情况下推定“后者必定覆盖前者”。
- 扫描基础游戏与上述 active 源目录，选择 5 个重复 Definition ID；对每项读取 S0 `character_lookup` 和对应 Runtime Character（若存在）。
- 不写 CK3 游戏目录、Workshop Mod、存档或 VOTC 生产运行时。

工具：[explore-v8.4-definition-override.js](../../../scripts/explore-v8.4-definition-override.js)。

<a id="source-00f31acec715--样本结果"></a>
## 样本结果

| --- | --- | --- | --- |

| `1059987` | 基础 `tangut.txt:3041` 为 `religion=zhengyi`；`2506311074/tangut.txt:3112` 为 `religion=vajrayana`；其余主要身份字段相同 | `1059987 -> 95795`，dead_unprunable；name/birth 同时匹配两源，raw faith=15 | `CONFLICT`；raw faith ID 未建立到源 religion key 的可验证映射 |

<a id="source-00f31acec715--v84-结论"></a>
## V8.4 结论

| 问题 | 结论 |
| --- | --- |
| 当前 active playset 是否可读取 | `PASS` |
| 重复 ID 是否可定位并保留全部来源 | `PASS` |
| `character_lookup` 是否能证明某些 Definition ID 已实例化 | `PASS` |
| Launcher position 是否单独证明 CK3 覆盖 winner | `NO` |
| 当前样本是否可标 `LOAD_ORDER_CONFIRMED` | `NO` |

V8.4 V1 应保存全部 source rows、base/Mod ID、Launcher position、字段差异和 `CONFLICT` 状态；不得替 CK3 猜 winner。若要把任何条目标为 `LOAD_ORDER_CONFIRMED`，需要受控新局或明确的 CK3 resolver/调试输出，证明最终 Runtime 字段唯一对应某一源定义。

# V8.4 GameState Adapter 与 Index Proposal

<a id="source-01fa3e01a287--1-目标与非目标"></a>
## 1. 目标与非目标

目标是为 V8.4 后续阶段提供一个可隔离、可诊断、可回滚的 CK3 Save/GameState 读取边界。它必须支持当前已确认的未压缩文本样本，并为 ZIP、binary、split 和异常文件保留显式分支。

本提案不是实现计划的授权，不在本轮新增生产 adapter、worker、持久化 schema 或 Prompt 投影。

<a id="source-01fa3e01a287--2-推荐边界"></a>
## 2. 推荐边界

```text
CK3SaveSource
  -> ContainerDetector
  -> Metadata/Gamestate Extractor
  -> Parser Worker
  -> CK3 Schema Adapter
  -> Normalized Snapshot
  -> Bounded Indexes
  -> Read-only Query Service
```

<a id="source-01fa3e01a287--source-与-detector"></a>
### Source 与 detector

`CK3SaveSource` 只负责 path、stat、header bytes、可读性和临时文件生命周期。`ContainerDetector` 输出 `PLAIN_TEXT_SAVE`、`COMPRESSED_ARCHIVE`、`BINARY_CONTAINER`、`IRONMAN_UNREADABLE` 或 `UNKNOWN`，并保留 header/version/kind/meta length。检测失败不得静默回退到“当作纯文本”。

<a id="source-01fa3e01a287--extractor-与-worker"></a>
### Extractor 与 worker

Extractor 先读 metadata，再按容器类型输出 Gamestate stream 或临时文件。完整文本 Query 和 ZIP/binary parser 建议在 worker/child process 中运行，主进程只收取 bounded result。worker 失败要返回 diagnostics，不得阻断现有对话和日志链路。

<a id="source-01fa3e01a287--3-normalized-snapshot-草案"></a>
## 3. Normalized Snapshot 草案

```js
{
  source: {
    containerKind,
    gameVersion,
    saveGameVersion,
    gameDate,
    playthroughId,
    contentFingerprint,
  },
  characters: {
    byId: Map<string, CharacterSummary>,
    nameToIds: Map<string, string[]>,
  },
  titles: { byId: Map<string, TitleSummary> },
  wars: { activeById: Map<string, WarSummary> },
  diagnostics: { missingFields, parseWarnings, limits },
}
```

`CharacterSummary` 只保留历史解析和当前关系需要的字段：id、name keys、birth、gender hint、culture/faith raw ID、dynasty、family references、alive/dead date、location、domain/title references、court employer/positions 和 selected traits。不要把原始完整 record 传入 renderer 或 Prompt。

`TitleSummary` 只保留 key、holder、de facto/de jure liege、date、history、capital 和必要 laws；`WarSummary` 只承诺样本确认的 attacker、defender、start date、CB、called-to-war、battle result 和 variables。Ended war 不应凭空补字段。

<a id="source-01fa3e01a287--4-index-建议"></a>
## 4. Index 建议

| Index | 用途 | 样本观察 |
| --- | --- | --- |
| `characterById` | 精确 ID 查询 | 144,287 条 |

| `historicalIdToCharacterIds` | 若未来 parser 发现直接 ID | 当前为 0 |
| `titleById` | holder/history/title graph 起点 | 20,504 条 |
| `titleHolderHistory` | 时间边界和继承诊断 | 8,089 条有 history 的 title |
| `realmToRuler` | 有限 realm ruler 查询 | 原型仅得到 149 条，不能视为完整王国图 |
| `warById` | active war 查询 | 107 个对象 |

索引 key 必须统一为 string。`nameToCharacterIds` 不得在重复名字时覆盖；所有推导关系要带 source path、sample date 和 confidence/status。

<a id="source-01fa3e01a287--5-cache-与身份"></a>
## 5. Cache 与身份

建议 cache key 至少组合：`playthroughId`、game date、game version、容器 kind、文件 size/mtime 和内容 hash fragment。`playthroughId` 在样本中可读，但 branch identity 只有一个样本无法确认；在 branch 合同确认前不得只用 playthrough ID 覆盖 Worldline。

cache 必须是只读 snapshot cache，不能成为人物绑定、Prompt 注入或 worldline mutation 的隐式入口。任何过期、时间倒退、fingerprint 不一致都应返回 `UNKNOWN`/diagnostic 并等待重新抽取。

<a id="source-01fa3e01a287--6-查询合同草案"></a>
## 6. 查询合同草案

```text
getSaveMetadata() -> metadata + status
getCharacter(id) -> bounded summary + source paths
findCharactersByName(name) -> candidates[] + ambiguity status
getTitleHistory(titleId, asOfDate) -> entries[] + status
getActiveWars(asOfDate) -> wars[] + status
getDiagnostics() -> parser/container/index warnings
```

接口只返回明确存在的字段；`historical_id` 未发现时返回 `NOT_FOUND`，不能用姓名、文化或现任头衔替代成“已解析”。

- 对 20–30 条人工 Ground Truth 做姓名歧义、出生/性别、死亡边界和当前状态分离校准。

## 1. 测试口径

<a id="source-37a9d55197aa--3-解释"></a>
## 3. 解释

1. 纯读文件很快，但语义 Query 和索引构建的主要成本来自文本解析、对象 materialization 和索引复制。
2. 顶层 scanner 可以在不构造完整对象的情况下发现 section occurrence，当前能力为 `PARTIAL`，不能回答任意深层路径。
3. 观察到的内存量足以支持把完整解析放进 worker/child process，隔离 Electron main process 的延迟和 OOM 风险；本轮只形成建议，没有施工。
4. 不能用这次未压缩样本推断 `UNIFIED_TEXT_ZIP`、binary 或 split save 的时间。正式 benchmark 至少需要每种容器一个样本、冷/热缓存各一次和失败路径一次。

<a id="source-37a9d55197aa--4-索引原型尺寸"></a>
## 4. 索引原型尺寸

| 原型 | 条目 | JSON 序列化尺寸 |
| --- | ---: | ---: |
| `characterById` | 144,287 | 30,164,502 bytes |
| normalized records | 144,287 | 28,882,036 bytes |
| `titleById` | 20,504 | 5,833,785 bytes |
| `warById` | 107 | 38,670 bytes |
| `historicalIdToCharacterIds` | 0 | — |

这说明“把完整 Character record 放入常驻 renderer/main 内存”不是合适的默认方案。建议由 worker 生成受限的 normalized index，并按查询类型返回小结果；正式实现还需测量 raw object 释放后的常驻内存和并发访问。

## 4. Title 与 realm

`landed_titles/landed_titles` 有 20,504 条记录。一个选定的 current title record 有直接 `holder` 和 13 条 `history`：最新记录为 `appointment_succession`，上一条为 `appointment`。全局 title field union 显示 `holder`、`de_facto_liege`、`de_jure_liege`、`history`、`heir`、laws 等并非每条都有。

## 5. War 与 history

<a id="source-e95ae757cb2b--6-schema-设计输入"></a>
## 6. Schema 设计输入

1. 所有 ID 在 normalized layer 保持 string，避免大整数和 key/value 类型差异。
2. 日期同时保存 raw string 和经过校验的 calendar value；无效日期必须进入 `UNKNOWN`，不能按 JS Date 猜测。
3. 角色候选采用数组，不使用同名覆盖；身份 evidence 与当前状态 evidence 分离。
4. 任何缺失 field 都要在 adapter 输出中保留可诊断的 absence，而不是填入“未知男性”“无配偶”等推断值。
5. `triggered_event` 等重复顶层 section 需要 stream parser 的 occurrence model，不能只保存最后一次。

# V8.4 第二轮：Historical Definition Catalog 提案

状态：提案与一次性勘探原型，不是正式 V8.4 adapter，不进入生产运行时。

<a id="source-d124c0c365c5--目标"></a>
## 目标

建立一个可审计的“源定义目录 + 存档运行时映射”中间格式，解决以下问题：

- 同名人物不能依赖 localization key 直接绑定；
- 基础游戏与多个 Mod 可能重复 Definition ID；
- Runtime ID 会随世界状态和创建顺序变化；
- save 的 `character_lookup` 是强证据，但不是所有人物都有条目；
- 目录必须保留来源、加载集合和置信度，便于人工复核。

<a id="source-d124c0c365c5--建议的最小结构"></a>
## 建议的最小结构

```json
{
  "schemaVersion": 1,
  "sourceSet": {
    "baseGameFingerprint": "...",
    "activeMods": [{ "steamId": "...", "position": 0, "path": "..." }]
  },
  "definitions": [{
    "definitionId": "...",
    "keyType": "string",
    "sourceType": "base_game|workshop",
    "modId": "...",
    "relativeFile": "history/characters/...",
    "line": 0,
    "name": "...",
    "birth": "...",
    "dna": "...",
    "identityEvidence": {}
  }],
  "runtimeBindings": [{
    "runtimeId": "...",
    "definitionIds": ["..."],
    "confidence": "DIRECT|INDIRECT_CONFIRMED|HEURISTIC|AMBIGUOUS|NOT_FOUND|UNKNOWN",
    "evidence": []
  }]
}
```

正式实现不应把绝对用户路径或原始存档内容写进持久化目录；`sourceSet` 只需使用可比较的逻辑路径、Mod ID、版本和内容指纹。

<a id="source-d124c0c365c5--映射规则"></a>
## 映射规则

<a id="source-d124c0c365c5--强规则"></a>
### 强规则

1. `character_lookup[definitionId] = runtimeId`：`DIRECT`。
2. 同一 `runtimeId` 由多个 Definition ID 直接指向：`AMBIGUOUS`，不得自动选第一项。
3. Definition ID 在源目录不存在但出现在 save lookup：保留 lookup 记录，目录侧标 `NOT_FOUND`，不得丢弃。
4. Character record 有 Runtime ID 但无 lookup 反向键：只能标 `NOT_FOUND` 或 `UNKNOWN`。

<a id="source-d124c0c365c5--弱规则"></a>
### 弱规则

出生日期、性别、文化、信仰、dynasty、DNA、父母、标题和 bookmark 只能形成证据集合。它们可以支持人工复核或未来的 `INDIRECT_CONFIRMED`，但不能把当前 `140239` 这样的候选直接升级为 `DIRECT`。

<a id="source-d124c0c365c5--mod-规则"></a>
### Mod 规则

目录必须以 active playset 为主视图，同时保留基础游戏和非 active 源的 provenance。相同 Definition ID 在不同源出现时，先记录冲突，再由真实 CK3 新局验证最终有效定义；不能用字典遍历顺序模拟覆盖规则。

<a id="source-d124c0c365c5--本轮原型与基准"></a>
## 本轮原型与基准

`scripts/explore-v8.4-definition-mapping.js` 是一次性只读原型：

- 逐文件扫描外层 brace block，能够处理同一行连续定义；
- 记录数字/字符串键、源 Mod、文件、行号、人物字段和目标证据摘要；
- 通过临时 Jomini Query 读取样本 `character_lookup` 与控制人物；
- 只将目标块和有界重复 ID 样本写到临时 JSON，不写完整目录、不写 save/log/user data。

本轮实际基准：基础游戏 207 个文件、17,420,591 bytes；包含历史人物目录的 Workshop 源 25 个；总定义 500,130；唯一键 369,689；重复键 66,844；目录扫描/摘要构建约 13.67 秒。该数字是勘探机器上的一次性基准，不是正式产品 SLA。

<a id="source-d124c0c365c5--生产前-hard-gate"></a>
## 生产前 Hard Gate

- 两个同 campaign checkpoint 证明 Definition ID → Runtime ID 的重载/变化行为；
- 两个不同新开局验证 source set 与 Runtime ID 不被错误混用；
- active Mod 加载顺序与重复 `han_12371` 的最终生效源做实机核验；
- 临时 `GetHistoryId` probe 覆盖 bookmark、Mod 历史人物、随机 NPC、玩家子女、事件人物；
- ZIP/binary/split/Ironman 存档边界与大存档 worker 隔离另行通过；
- 失败映射必须 fail-safe，不能影响现有 VOTC 对话、Memory、Action、Letter 或 Worldline 合同。

在上述 Gate 完成前，Catalog 只用于诊断和人工复核，不接入 V8.4 正式 Prompt、Memory 或 Historical Figure Resolver。

# V8.4 第二轮：Historical Definition ID 勘探报告

状态：前置勘探完成，未施工。本文只记录对基础游戏、当前启用 Mod、`autosave_1.ck3` 和 CK3 日志的只读证据。

<a id="source-6981b66e9596--结论摘要"></a>
## 结论摘要

1. `history/characters` 的外层键是 CK3 历史人物数据库使用的 Definition ID；它不是统一的数字格式，基础游戏和 Mod 同时存在数字键与字符串键。
2. Definition ID 与运行时 Character ID 是两套身份。样本存档在独立的 `character_lookup` section 中保存了部分 Definition ID → Runtime ID 映射，但运行时 Character 对象本身没有 `historical_id`、`historicalId` 或 `historical_character_id` 字段。
3. `autosave_1.ck3` 中已直接确认两条映射：`tangyin_yue_014 → 96895`、`nansong_yue_085 → 96896`。两者分别位于 `dead_unprunable` 与 `living`，说明历史定义的运行时状态可以发生变化，而 Definition ID 不随之改写。
4. `licheng_xin_006` 和 `han_12371` 在当前源目录中存在，但未在该存档的 `character_lookup` 中找到直接映射。存档中观察到的辛弃疾候选 Runtime ID `140239` 也没有反向 Definition ID；不能据此硬绑定。
5. “跨新开局、跨读档或跨 Mod 组合保持稳定”的结论仍是 `UNKNOWN`。本轮只有一个获授权的完整存档样本。

## 术语边界

| 名称 | 本轮定义 | 是否等同 |
| --- | --- | --- |
| Definition ID | `history/characters` 中 `key = { ... }` 的外层键，例如 `han_12371`、`tangyin_yue_014` | 不等同 Runtime ID |

<a id="source-6981b66e9596--对计划问题的回答"></a>
## 对计划问题的回答

<a id="source-6981b66e9596--外层键是不是稳定-historical-definition-id"></a>
### 外层键是不是稳定 Historical Definition ID？

作为 CK3 历史数据库的输入键，结论为 `CONFIRMED`：基础游戏 bookmark 配置以 `history_id = han_12371` 这样的字段引用它，CK3 的 `GetScriptedCharacterByHistoryID` 也以历史 ID 查询人物。源文件实际使用的键包括数字和字符串，因此“外层键永远是数字”不成立。

作为跨新开局、跨 checkpoint、跨 Mod 组合的长期稳定业务主键，结论为 `UNKNOWN`。当前证据只支持“在相同有效内容集合中作为源定义键使用”，尚未提供第二个完整存档或新开局样本。

<a id="source-6981b66e9596--runtime-id-会不会变化"></a>
### Runtime ID 会不会变化？

会，而且不能把它当历史身份。样本中 `tangyin_yue_014` 的 Runtime ID 是 `96895`，`nansong_yue_085` 的 Runtime ID 是 `96896`；另一个观察到的辛弃疾候选是 `140239`。Runtime ID 还被头衔 holder、亲属、库存、 pinned character 等大量运行时关系引用，显然是当前世界状态的对象 ID。

<a id="source-6981b66e9596--definition-id-与-runtime-id-如何建立关系"></a>
### Definition ID 与 Runtime ID 如何建立关系？

优先使用存档的 `character_lookup` 精确查找，才标记 `DIRECT`。不得用同名、出生日期、DNA 或 dynasty 单独推断为直接绑定。源定义重复、没有 lookup、或一个 Runtime 候选对应多个源定义时，必须保留 `AMBIGUOUS`、`NOT_FOUND` 或 `UNKNOWN`。

<a id="source-6981b66e9596--失败闭环与停止边界"></a>
## 失败闭环与停止边界

- 不把 `first_name = Yuefei_name` 当成岳飞身份；本轮同时发现女名“越妃”、张飞的 `Fei_name11` 和其他同名候选。
- 不把 `140239` 反向解释成 `han_12371` 或 `licheng_xin_006`；当前存档没有对应 `character_lookup` 条目。
- 不把 `character_lookup` 当成所有人物的完整反向索引；随机 NPC、玩家子女和动态创建人物仍可能无条目。
- 未执行第二个完整存档、新开局、跨 checkpoint、读档继承或 Mod 切换实验，因此这些问题保留 `UNKNOWN`。
- 本报告不写入存档，不改变历史人物文件，不修改 V8.4 正式运行时。

<a id="source-c46080e49bc6--2-已确认的-live-probe-能力"></a>
## 2. 已确认的 live probe 能力

- `log_gamedata_v3`、`v3s`、`v3l` 会输出 `VOTC:IN` 和 `VOTC:CAMPAIGN`，并调用 `log_character_v2`。
- `log_character_v2` 聚合了 memory、secret、modifier、income、treasury、troops、title laws、relatives、persona numbers 等日志效果。
- `v3` 会先记录 recipient 和同地点 pinned character，再将 player 追加到有序列表；`v3s`、`v3l` 的参与者集合不同，不能把三种日志格式当作同一 record。
- 选定 companion `debug.log` 中有辛弃疾的 relatives 行和 CK3 character window 的 internal ID 行，证明当前安装环境可以通过既有 VOTC/CK3 日志观察到目标人物。
- 同一日志没有可靠的 CK3 游戏日期行；墙钟时间如 `[23:13:49]` 只能作为 log ordering，不能作为游戏日期。

<a id="source-c46080e49bc6--4-推荐组合方案"></a>
## 4. 推荐组合方案

在没有全局 delta hook 前，正式设计应采用：

```text
Live Probe（按需、交互触发）
  -> append-only raw log cursor
  -> 结构化日志解析与去重
  -> bounded live overlay
  -> 下次 checkpoint 与 CK3 save reconcile
```

Live probe 只能作为“观测到的当前局部状态”，不能覆盖或修正 save snapshot。Save 是时间锚；live log 没有可验证游戏日期时，所有跨时间合并都应降级为 `UNKNOWN`。任何 probe 行都必须保留来源、墙钟时间、触发类型和字段缺失诊断。

<a id="source-c46080e49bc6--5-未执行的实机动作"></a>
## 5. 未执行的实机动作

计划书要求的 S0/S1 实机动作、游戏内触发变化、重新读取 debug.log、保存第二个 checkpoint 和 Save A/B 对照，本轮没有伪造完成。原因是用户只授权以 `autosave_1.ck3` 作为测试样本；静态日志审计不能替代 CK3 实机操作。

<a id="source-c46080e49bc6--6-冻结边界"></a>
## 6. 冻结边界

<a id="source-b6f63f932d94--sol-修复"></a>
## Sol 修复

<a id="source-b6f63f932d94--save-readerworker-与-checkpoint"></a>
### Save Reader、Worker 与 Checkpoint

- 主进程路径校验改为只读取 64-byte header、受限 metadata 和极小 body prefix，不再把 200 MB 以上存档整文件读入 Electron Main。
- 只接受 plain text 与 unified ZIP；binary、split/未知 kind 和 Ironman 明确失败，不把未知容器标成 `VALID`。
- ZIP 解压增加输出上限；Worker 增加 120 秒超时、1.5 GiB old-generation 上限、Snapshot 数量边界，以及解析前后 size/mtime 一致性检查。
- Snapshot 指纹覆盖完整 Gamestate，不再只比较首尾片段。
- Checkpoint 只有在候选及 Delta 原子落盘成功后才替换内存态；写入失败保留旧 Checkpoint 与旧 Delta。
- Delta 仅在同一非空 `playthrough_id` 且日期递增时生成；跨 campaign 不生成、不在当前 UI 视图混入旧 campaign，持久层不再以固定 5,000 条静默删历史。

<a id="source-b6f63f932d94--identitysupplemental-与-prompt"></a>
### Identity、Supplemental 与 Prompt

- `characters`、姓名索引和 Definition 映射使用无原型对象，特殊 key 不再污染索引。
- 同一 Runtime ID 对应多个 Definition ID 时标记 `AMBIGUOUS_PROVENANCE`，不再显示为确定的 `DIRECT`。
- Supplemental 新增持久化 `hidden` 状态；隐藏条目立即失效缓存且不进入召回。
- Supplemental create/update/delete 先持久化候选再替换内存态，写盘失败不会制造“UI 看似成功、重启后回滚”的假状态。
- 生产 Prompt 仅接受 `VALID + ACTIVE + configured autosave.ck3 + source exact match` 的 Checkpoint；手工诊断存档、STALE Checkpoint 和错误路径均不能注入。
- Supplemental 只召回非隐藏 `PUBLIC_WORLD`，并显式声明不能覆盖 Live、GameState、角色自身资料或场景直接事实。
- PromptBuilder 将 stable Game Truth 放在 Personal topic patch 前，并把 world topic、Supplemental、current world 分成不同块；同时保留 V7 已冻结的“当前用户消息 → Turn Recall”顺序。

<a id="source-b6f63f932d94--renderer--preload--main--worker-管线"></a>
### Renderer → Preload → Main → Worker 管线

# V8.4.1 Terra-3 CK3 Localization Resolver 实施报告

<a id="source-aa93cca44988--实现"></a>
## 实现

- 新增 `CK3LocalizationResolver`，通过 CK3 用户目录的 `dlc_load.json`、启用 Mod descriptor 与 Steam Workshop 路径反推出基础游戏及当前启用 Mod 的本地化来源。
- 支持 `title`、`character` first-name key、`dynasty`、`culture`、`faith` 与 `war` 六类查询，默认读取 `simp_chinese`。

真实 `h_china` 发现三条活跃来源：

- 基础游戏 `titles_l_simp_chinese.yml`：`中华`；
- Mod `2506311074` 的 `oe_titles_l_simp_chinese.yml`：`华夏`；
- 同一 Mod 的 replace 文件：`华夏`。

## Terra-5：Freshness / as-of

`getCheckpointStatus()`、Overview、Diagnostics 与 Prompt Context 现都输出：

- `pipelineState`
- `checkpointAsOf`
- `liveDate`
- `ageDays`
- `freshnessStatus`
- `freshnessReason`

原设计没有规定具体阈值，本实现采用保守且可测试的规则：同日为 `FRESH`，Live 比 Checkpoint 新 1–365 天为 `AGING`，相差至少 366 天、pipeline 非 `ACTIVE`、Live 日期无效或早于 Checkpoint 时为 `STALE`。没有 Live Probe 时，ACTIVE Checkpoint 可保持可用，但 `ageDays` 为未知且 Prompt 明确写出“Live Probe 未提供”。

```text

Live 当前日期：…
只有 Live Probe 直接提供的信息可表述为 Live 当前日期的实时状态；
未被 Live Probe 更新的可变事实仍仅截至 Checkpoint 日期。
```

这替代了“缺失实时信息时仅可使用 Checkpoint”可能造成的实时误读；Game Truth、Supplemental 与 current world block 的原有排序未改变。

<a id="source-03fa179cbcb4--2-实施范围"></a>
## 2. 实施范围

<a id="source-03fa179cbcb4--21-conversation-生命周期"></a>
### 2.1 Conversation 生命周期

- `ConversationManager` 使用单调递增 `conversationEpoch` 创建新会话。
- 新会话替换旧会话时，旧会话只进入异步 Memory Finalization，调用 `closeGameScene: false`，不再发送旧的 `mcc_event_v2.9002`。
- 正常结束会话仍发送 Close，并携带 `scopeId`、`epoch`、15 秒 TTL、`destructive` 和 `supersedable` 元数据。
- `RunFileManager.setCurrentConversationEpoch()` 会隔离并 quarantine 旧世代的 Close。

<a id="source-03fa179cbcb4--22-run-command-queue-v3"></a>
### 2.2 Run Command Queue v3

- 队列状态版本由 v2 升为 v3；旧状态启动时迁移，旧 `written` 状态规范化为 `awaiting_ack`。
- Close 默认 `expiresAt = queuedAt + 15000`，dispatch 前和 watchdog 中都会检查过期与世代。
- 未写出的 Close 启动恢复为 `expired`；已写出但 ACK 不确定的 Close 为 `quarantined`，均不会自动重放。
- Close ACK 超时立即 quarantine；普通 `action_effect` ACK 超时保留为 `stalled`，但必须由用户明确授权 retry，避免未知执行状态下重复 Effect。
- 被 quarantine/取消的 active command 会先按 command ID 校验并 neutralize `votc.txt`；carrier 属于其他 command 时拒绝清理。
- 迟到或乱序 ACK 只记录 `late_ack ignored`，不会改变当前队首或再次触发 dispatch。

<a id="source-03fa179cbcb4--23-可观测性"></a>
### 2.3 可观测性

- 所有关键状态变更统一输出 `[RunCommand]` 日志，包含 command ID、kind、owner、scope、epoch、年龄、写入次数、前后状态和原因。
- `letters:getStatuses` 的 Date Tracker 状态中增加 `runCommandHealth`，包括 active command、队列年龄、stalled、expired、quarantined、HOL blocked 和 late ACK 计数；原有 BLOCKED/STALLED 操作入口保持不变。

<a id="source-03fa179cbcb4--3-durable-state-与-carrier-边界"></a>
## 3. Durable state 与 carrier 边界

`run-command-queue.json` 是唯一 durable source of truth；`run/votc.txt` 只作为当前 dispatch carrier。

启动恢复顺序由主进程保持为：扫描并 reconcile 已存在的 ACK、启动日志 tail、再次 reconcile、迁移/隔离未确认命令、清理匹配 carrier，最后才允许恢复有效的 queued command。任何有写入历史但没有 ACK 的命令都不会因为重启自动重写 carrier。

普通 Action 的安全合同仍是：

```text
写入历史 + 无 ACK → STALLED + carrier neutralize
                     ↓
              explicit retry 或 cancel
```

这会保留重复 Effect 风险提示，但不再允许 Close 以 stalled 状态永久卡住整个队列。
