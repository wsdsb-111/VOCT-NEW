# V8.15 修复1实施报告

日期：2026-10-06。依据用户提供的 `v8.15-修复1.md`。主代理沿用客户端模型，实现与独立 QA 子代理均为 GPT-6 Luna Max。

<a id="source-e81d08fa2765--修复范围"></a>
## 修复范围

- Explicit Target Final Selection：显式人物的 split Legacy Detail 可以替换最低分的非目标 Detail，不替换另一个显式目标；Canonical、Legacy、Derived 的预算裁剪使用同一显式目标优先级。无显式目标保留原选择行为，Detail 上限及 Packet 1200 token 上限不变。
- Durable Forget Fail-Closed：持久遗忘不确定、Owner folder 不可定位或来源不足时，在改动旧记忆与可见摘要前拒绝，返回 `MEMORY4_FORGET_INCOMPLETE`。现有 mutation journal 回滚，不报删除成功。加载时计算的 folder-summary ID 不充当真实持久来源证明。
- Safe Skip：仅当 Campaign、Owner、人物对明确，原摘要没有来源引用，该 scope 的所有合法 Memory4 sidecar 位置均不存在且 Recovery 无相关记录时，返回 `SKIPPED_SAFE_NO_FOOTPRINT`。只凭 projectionId 缺失不能安全跳过；损坏、symlink、未知文件或不确定 scope 不视为零 footprint。
- Pre-V8.15 Ghost：新增只读审计及明确确认后的遗忘。正常启动没有审计或清理钩子，不自动修改用户数据。清理复用既有 Engine/Coordinator/tombstone/journal/派生与披露撤销链路，不创建另一套物理删除算法。

没有改动 Fact Epoch、Owner/Campaign 授权、Presence、Worldline、Speaker Provenance、信件运行时代码或 Three-Mod。UI 仍显示 V8.15 / Memory Engine 4.0，协议 3.0、摘要存储 2.5、App 2.0.4、原 Prompt block IDs 和 Anchor 不变。

<a id="source-e81d08fa2765--审计合同"></a>
## 审计合同

`memory4-orphan-audit.js` 读取合法 scope 的 Canonical、Disclosure、Recovery、可见摘要与遗忘账本，返回 projection、Owner、counterpart、conversation/finalization、source IDs 及状态，不返回记忆正文。

- `ACTIVE`：可见摘要存在确切映射。
- `FORGOTTEN`：账本已经遗忘该投影，不再作为清理建议。
- `ORPHANED_PRE_V815_PROJECTION`：来源可证明、可见投影已不存在、尚未遗忘。
- `UNKNOWN`：来源、可见映射或共享正文的分离无法证明；正在生成的投影也不视为可清理 orphan。

无旧 projection lineage 时，仅单一人物对、完整 conversation/finalization 与准确 source segment 可建立候选；多人缺失 lineage 不猜测。共享 Canonical 仅在 C lineage 足以独立覆盖正文时允许遗忘 A；无法分离的共享 Legacy 来源保留并标 UNKNOWN。仍可见的 C 摘要即使没有 Canonical 候选，其真实 Legacy ID 也阻止 A 连带遗忘。缺失/非法 counterpart 的可见记录不能被忽略后误判为 orphan。

审计不写 index、metadata、known-entities、遗忘账本、entries、years、life、Legacy 或 Recovery。`auditToken` 绑定当前文件内容和审计结果；执行前重新审计，可见摘要、sidecar 或 recovery 变化均拒绝旧确认。只有 `confirmed: true` 且当前状态仍为 ORPHANED 才执行；当前 Campaign/context/write Gate 仍适用。

<a id="source-e81d08fa2765--诊断接口"></a>
## 诊断接口

不新增正式管理 UI，提供现有 preload/IPC 桥接：`conversationAPI.auditMemory4Orphans` 与 `conversationAPI.forgetMemory4Orphan`。没有入口会自动确认或自动执行。开发者控制台先获取当前 context、查看 DTO，再由用户选择单一 projection 确认：

```javascript
const ctx = await conversationAPI.getMemory4OwnerData({ ownerId: 95735, contextOnly: true });
if (!ctx.success) throw new Error(ctx.error);
const request = { ownerId: ctx.ownerId, expectedCampaignToken: ctx.campaignToken, expectedContextId: ctx.contextId };
const audit = await conversationAPI.auditMemory4Orphans(request);
if (!audit.success) throw new Error(audit.error);
console.table(audit.items);
```

核对 Owner、counterpart 和来源后，使用刚刚审计返回的单一 projectionId；下例字符串必须替换为已核对的 ID，不能批量确认：

```javascript
await conversationAPI.forgetMemory4Orphan({
  ...request,
  projectionId: "替换为已核对的 ORPHANED projectionId",
  expectedAuditToken: audit.auditToken,
  confirmed: true
});
```

读取归档允许只读审计；遗忘仍要求当前有效对话上下文与当前 Owner，不对离场或结束的归档绕过写门禁。相关未知来源如需人工修复，应另行设计高风险流程，本轮不提供强制清空开关。

### W1 / P1：新存档的 rite 信仰链未接入世界线

- 位置：[game-state-adapter.js](../../../resources/app/out/main/worldline/game-state-adapter.js#L168)，人物字段白名单及 `faith: scalar(fields.faith)`；根级白名单第 360 行也未读取 `rites`、`faiths`。

- 合成复现：角色 `rite=34`，rite 34 的 `faith=100`，faith 100 的 `faith_type=taoism`。使用生产 `parseGameState` 后，角色 `faith=null`；`getCurrentTruth(..., "faith")` 返回 `CURRENT_TRUTH_VALUE_UNAVAILABLE`，解析诊断仍为 `missingFields=[]`、`parseWarnings=[]`。
- 影响：存档世界线的信仰事实缺失且诊断没有显式报告该字段覆盖缺口。debug.log 的当前在场角色可以另有宗教数据，不能扩大为“整个应用所有宗教均不可用”。

### M1 / P2：Owner 快照构建失败后没有可重试任务

<a id="source-5383d5f6538d--人物披露专项与待补证据"></a>
## 人物披露专项与待补证据

1. 现有 `memory4-disclosure.js` 候选及 Store 校验只允许 TITLE、TRAIT、AGE，没有 NAME 类型。人物名字/昵称用于识别主体，并不等于一条“姓名已披露”的证据。用户自报姓名未显示为披露，属于现有能力缺口，不能假报已实现。
2. 披露是方向性的：玩家说“我是某头衔”，应保存在听到这句话的 NPC Owner 下，目标人物是玩家；不在玩家自己的 Owner 下再添加自己。扫描明确跳过 `entityId === ownerId`。
3. 当前记录在终局 `finishOwner` 成功抽取/提交后调用 `recordDisclosures`，并非每说一句立即持久化。若长期抽取失败，确定性披露也延后到重试；M1 场景还可能没有可重试材料。
4. 自动披露只匹配 CK3 当前事实候选及可证明的直接原话；第三人转述、否认、假设、歧义身份和过期 Fact Epoch 不授权。这些是保留的安全合同，不应为追求显示而全局放宽。
5. 当前真实保存的披露事实确为 0，说明不能仅把事故归为 UI 过滤。用户确认查看的是生成的人物文件夹中的人物认知页，并补充关闭游戏/Mod 后无法读取；尚未提供具体自报原话、文件夹对应的 Owner 及终局完成情况。本轮不读取真实对话正文或冒认实机根因。
6. **关闭后的可查看性不等于持久性。** [summaries-manager.js](../../../resources/app/out/main/summaries/summaries-manager.js#L273) 的 `getMemory4ReadContext` 要求仍有 conversation、已加载的 `gameData.characters` 和明确 Campaign。已结束但保留 GameData 的会话可以只读归档；完全没有该上下文时入口拒绝。Store 的 `known-entities.json` 才是持久披露载体，代码没有在关闭游戏时删除它。因此当前实现缺少独立离线选择可信 Campaign 的查看入口，但不能从“页面读不到”推出“此前披露被删除”。当前真实披露为 0，也没有可用记录证明该用户场景已保存后丢失。若扩展离线查看，须显式选择已持久 Campaign/Owner，不可跨战役拼接或伪造实时事实。

追加合成验证：当前候选为 `TITLE=皇帝`，玩家为 speaker、NPC 为 Owner，并有合法 spoken/knownBy/sourceRole=user 证据时，`我是皇帝。`、`我现在是皇帝。`、`我的头衔是皇帝。`、`我叫赵明，如今是皇帝。`、`本人乃皇帝。` 均命中头衔。不要求特殊引号。正常终局返回 `COMPLETE/NO_DURABLE_CONTENT` 后，披露为 `AUTO_DISCLOSED`、effectiveKnown=true；注入 Provider 抽取失败后为 `PARTIAL_FAILURE/EXTRACTION_FAILED`、disclosure=false，并保留 PENDING recovery。后一条与 M1 不同：M1 是快照构建更早失败，连 recovery 都未产生。此验证不使用真实 Provider，也未替代原子 rename。

这排除了“所有常见自报头衔句式都不支持”，但没有排除用户原话未匹配候选、查看方向错误或某段来源/终局异常。当前候选只有皇帝时，国王、王、旧头衔不能仅凭自称转成当前事实。姓名持久知情与独立离线档案浏览若要新增，应另有明确合同与 UI，不把它们冒充已实现的披露。

## 连续交接与循环保护

## 根因与生产修复

<a id="source-258f035c9060--f5-p1-01停机回执"></a>
### F5-P1-01：停机回执

`LetterLogReader` 启动时从 EOF 开始，因此 App 停机或 reader 暂停期间已经追加的合法回执不会进入原实时处理入口。隔离真实 Manager/reader/RunFile/finalization 夹具在补丁前稳定失败：重启后原接收锁仍存在，未生成摘要。这是自动化复现，不是新 CK3 实机事故。

Reader 仍从 EOF 监听。新增 `letter-receipt-recovery.js`，仅在启动/监听重启时处理已写入 Effect、尚未归档的带 token 原信件。新投递在写 Effect 前持久化原物理日志身份、设备、LOAD 字节边界、发送时 EOF 和末尾锚点摘要；恢复只读该发送位置后的完整行，单次最多 32 MiB、每块 64 KiB，并让出事件循环。重验当前 Campaign/玩家、原双方来源快照、全部既有 receipt 条件、文件身份及最新物理 LOAD。当前 NPC 可以改变，归档双方仍使用发信快照。

缺证明、错身份/日期、仅 RUN_ACK、轮转/截断、新 LOAD、未写完的 LOAD 或扫描超限均保留 pending 和锁，不归档、不重发。旧 pending 没有新增发送证明时不能安全自动补消费；仍支持原实时回执，单封人工补建沿既有明确授权流程。状态提供 `RECOVERED_VERIFIED`、`NO_VERIFIABLE_RECEIPT` 或 `AMBIGUOUS_OR_STALE` 与原因，不输出回信正文或原始日志。

实时与恢复共用 `letterAcceptanceTransition`；恢复候选在锁内重新验证。pending version 4 保持，新增字段兼容；写入改为同目录临时文件、fsync、原子 rename。接收证明先落盘，再转 SENT 并捕获既有归档任务；捕获成功后才移除 pending。证明落盘后、归档捕获前崩溃（包括 SENT/锁已释放）可在重启时续同一任务。失败只续记忆，不重建宝物、不生成新回信；恢复本身不推进下一封投递。

<a id="source-258f035c9060--f5-p2-01date-扫描"></a>
### F5-P2-01：DATE 扫描

旧扫描对不断增长的日志同步倒扫到 LOAD；DATE 高频到来时重复读取历史字节。新增 `letter-date-session-scanner.js`：首次异步分块扫描，之后验证固定 256 字节锚点并只读新增内容。同路径并发扫描合并；UTF-8 偏移按 Buffer 字节计算，半行保留到 LF；同 token 的新物理 LOAD 清除旧日期。轮转、截断、文件扫描中变化或锚点不符返回 UNKNOWN，下一次冷恢复；不完整 LOAD 禁用旧 DATE，待完整后再增量恢复。异步等待后复验 reader 身份，退役 callback 不推进日期。

`lastDateScanResult.scan` 包含模式、bytesRead、durationMs、maxBlockMs、backscanBytes、日志身份摘要和边界是否已知。冷扫描期间显示 `DATE_SOURCE_RECOVERING`，不以旧日期投递；首次写 Effect 前若扫描失效，立即停止写入并保留待发信件。未调整 native DATE 桥、RunFile/ACK 或退休计时器。

### 3. 首都资料绕过非本人知识门禁

独立红测通过真实 PromptBuilder 最终消息复现：D 会收到玩家的合成首都标记。修复将 `capitalLocation` 加入既有非本人私密字段过滤，当前回应者自身保留完整值，原始 GameData 不修改；未知授权的其他人物首都不注入。姓名仍保留为后台角色绑定标签，已有 Worldline 地点授权不变，不借头衔授权推断地点。

同一原始专项绿测确认：D 最终请求不含玩家首都，D/A 回应时仍各自保留自身首都。这能封堵已确认的地点资料入口，但不单独证明全部复述细节都由它生成。

<a id="source-034e27525660--4-无来源传闻生成约束"></a>
### 4. 无来源“传闻”生成约束

在现有回应角色身份知识提示中明确：私聊和信件不会自动传播到全世界；同国、同地、亲友、声望或经过时间都不证明听过其他人物的私聊。只能引用当前请求提供给该角色的授权记忆、来源明确的公开事实或当前已听见的对白。无来源时不能借“听说／传闻／有人告诉我”补造玩家往事或后台资料的传播渠道。

这是生成约束，不替代确定性的 ACL；也不保证未经真实 Provider 测试的模型必定遵守。
