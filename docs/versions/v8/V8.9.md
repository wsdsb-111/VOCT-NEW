<a id="source-e9b11c4134c3--1-实施范围"></a>
## 1. 实施范围

本轮按《VOCT-真实RequestDiff与Conversation-Responder-Scoped-Prefix分析设计》替换已完成的 Synthetic GLM 缓存路径诊断。诊断目标改为观察 VOCT 真实 `requestType=chat` 出站请求，不修改正式 Prompt、Runtime Profile、Action、Relationship、Memory、Worldline、Summary 或 Provider 路由合同。

旧的 GLM 缓存路径探针、缓存路径 IPC、Preload API、诊断页旧工具、专项测试和实现报告已移除。普通真实 Chat 仍进入既有 UsageAnalytics；不再因为诊断用途从正常 Token 统计中排除。

<a id="source-e9b11c4134c3--2-真实请求捕获边界"></a>
## 2. 真实请求捕获边界

捕获发生在 PromptBuilder 与最终 Provider 请求参数组装完成之后、调用 `provider.chatCompletion()` 之前。Provider 通过 `buildDiagnosticRequest()` 暴露实际发送形态：

- OpenAI-compatible 使用最终 `model/messages/stream` 及有效请求参数；
- 智谱保留 `reasoning_effort`、`thinking.clear_thinking` 等实际参数；
- DeepSeek 使用其最终请求转换结果，避免把 Provider 内部变换误判为公共前缀。

每条真实 Chat 元数据包含稳定的 `conversationId` 和稳定的 NPC `responderId`。显示名称、随机诊断 ID 和 API Key 不参与诊断持久化。

<a id="source-e9b11c4134c3--3-比较范围与内存边界"></a>
## 3. 比较范围与内存边界

系统分别维护以下两个最近请求基线，每个 Scope 最多一条，且只存在于当前进程内：

1. Route：`provider + model + requestType`；
2. Conversation / Responder：Route 加 `conversationId + responderId`。

因此，同一路由但换 NPC 时不会把两个角色的公共前缀错误算成同一个 Conversation Prefix；同一 NPC 的连续请求仍可获得更细的消息、Block 和 Chunk 差异。

进程重启后第一条请求明确标为 `cold_local_baseline`，不恢复上一进程的 Prompt 基线，也不在磁盘写入 Prompt 正文。

<a id="source-e9b11c4134c3--4-安全数据合同"></a>
## 4. 安全数据合同

持久化只保留可用于聚合和复核的脱敏字段：消息位置、role、Block ID、estimated tokens、内容 hash、Chunk hash、公共前缀统计、有效参数差异、Endpoint fingerprint、Conversation/Responder ID、时间、状态和 Provider Usage。不会保存 Prompt、系统指令、用户消息、NPC/Memory/Worldline/Family 文本、回复正文、reasoning 正文或 API Key。

消息级诊断提供首个差异位置和 Block；同 role 的首个差异消息还会给出公共内容字符/字节/估算 Token。公共前缀使用确定性的约 512 estimated-token Chunk hash，便于判断前缀在哪个 Chunk 发生变化而不暴露正文。

<a id="source-e9b11c4134c3--5-provider-truth-与对齐判定"></a>
## 5. Provider Truth 与对齐判定

原始 Provider Usage 只保留安全字段，统一识别 `prompt_tokens`、`cached_tokens` 以及 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。Provider 未报告缓存值时保持 `unknown/not_reported`，明确的零不会被转成缺失。

本地公共 Prefix 与 Provider 缓存 Token 分开记录，并按以下状态对齐：

- `aligned`：缓存值与估算公共前缀处于 0.75–1.25 区间；
- `provider_under_hit`：Provider 报告低于本地公共前缀；
- `provider_over_estimate`：Provider 报告高于本地公共前缀；
- `provider_zero_despite_large_prefix`：参数相同、间隔不超过 300 秒、公共前缀至少约 8000 Token，但 Provider 报告零；
- `insufficient`：没有可比较的 Provider 真值或本地前缀不足。

诊断页同时展示 Prefix 长度桶（0–2K 至 16K+）、请求间隔桶（<5 秒至 >300 秒）、同 NPC / 换 NPC 聚合和 Provider A/B 统计。

<a id="source-e9b11c4134c3--6-诊断页与导出"></a>
## 6. 诊断页与导出

新增 IPC/Preload 边界：

## 2. RC1：Provider Truth 与 Outbound 诊断

`finiteNumber` 不再把 `null`、`undefined`、空字符串或非数字字符串转换为 0；`cached_tokens` 因而保留“未报告 / 明确为 0 / 正数”三态。

正式聊天在调用 Provider 之前生成 Outbound 指纹。持久化字段只包含消息位置、role、估算 Token、SHA-256 内容哈希、累计前缀哈希和 Prompt Block ID，不保存 Prompt、回复、reasoning 正文或 API Key。相邻请求以 `provider:model:requestType` 为比较键，输出公共消息数、公共前缀估算 Token、首个差异位置和首差异 Block。

诊断页固定按以下优先级解释证据：

1. Provider 原生 usage / `cached_tokens`。
2. 实际 Outbound 相邻请求公共前缀。
3. Prompt Block 的本地缓存命中归因估算。

Chat 观测同时记录 `requestStartedAt`、`firstReasoningAt`、`firstVisibleContentAt`、`requestCompletedAt`，并派生 reasoning TTFT、visible TTFT、output time 和 total latency。原有 `%APPDATA%/VOTC/provider-diagnostics.jsonl` 的 500 条、10 MB 保留上限不变。

# V8.9.1 缓存统计与 Runtime Profile 补全

日期：2026-09-14。V8.9 实机反馈后的修复与延期 RC4 实施。代码回归与隔离 Electron 通过，GLM 实机命中率目标、RP 和长时 Gate 尚未通过。

<a id="source-1e9d9b4e34db--实机证据与原因"></a>
## 实机证据与原因

只读核对用户截图对应的 56 次 Chat 请求及本地原始 Usage：

| 路由 | 请求 | 输入 Token | 原生命中 Token | 加权命中率 |
| --- | ---: | ---: | ---: | ---: |
| OpenAI-compatible / deepseek-v4-flash-0731 | 35 | 529,913 | 449,536 | 84.83% |
| zhipu / glm-5.3-flash | 21 | 283,937 | 57,600 | 20.29% |

本批 Chat 时间为 2026-09-14 10:06:57—11:09:01（Asia/Shanghai），不是全日统计。DeepSeek Raw Usage 存在 `prompt_tokens_details.cached_tokens`，但 UsageAnalytics 只读 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，兼容 Provider 未做映射，因而显示“—”。例如一条请求输入 17,448、原生命中 14,336，真实未命中为 3,112；不存在该批 DeepSeek 缓存消失的证据。

GLM 的 20.29% 则来自真实原生数字。16 次为 0，5 次正命中；正命中均出现在相邻 Outbound 消息完全相同的重复请求。另有完整 Outbound 相同而返回 0 的请求；普通新轮也有约 9,685—12,572 的公共前缀但返回 0。因此不能把全部零命中归因于应用前缀变化。缓存保留、路由、推理参数处理仍需服务商侧或受控延时 A/B 验证。

[智谱上下文缓存文档](https://docs.bigmodel.cn/cn/guide/capabilities/cache)说明缓存有时效性；并没有提供足以确认本批 GLM 恰好 60 秒过期的证据。本轮不硬编码 TTL、不增加后台付费预热、不把本地公共前缀记成服务商命中，也不宣称 GLM 缓存目标已修复。

<a id="source-1e9d9b4e34db--缓存修复"></a>
## 缓存修复

- `providers/usage-normalization.js` 统一原生 hit/miss 与嵌套 cached_tokens，兼容流式 usage-only 尾块和非流式响应；null、空字符串、负数与非法值保持未知，0 保持明确未命中。原生计数优先。
- `LLMManager.buildUsageRecord`、UsageAnalytics 与 ProviderDiagnostics 在各自边界使用相同归一化；智谱 Provider 也修复了自己的 `null → 0` 路径。
- 报表以 Provider/模型/请求类型/输入与输出 Token/1 秒时间容差唯一匹配旧 Raw Usage，只读补全缺失的缓存计数；重复或歧义候选不回填，已记账证据不能再次分配。当前 35 条全部唯一匹配，原始分析数据与诊断文件未改写。恢复依赖诊断记录仍在保留范围内，新请求直接持久化正确计数。
- 诊断页重新归一化历史记录，显示距上一同模型请求完成的间隔，以及“公共前缀存在但 Provider 返回 0”的提示。

## RC4：人物 Stable / Runtime 拆分

本次补齐的是 pList 人物字段拆分，纠正旧报告中“进程级 Session Runtime 隔离”的不准确表述；本设计不涉及新增操作系统进程。

- 正式 Chat 每轮执行已有描述脚本和既有性别/年龄/亲属适配。EN/ZH pList 的身份、姓名、文化、信仰、性格、性格特质与家族身份项放入稳定部分；实时项进入历史消息之后的 Runtime 部分。
- 年龄、头衔、任职、地点、金币、好感、关系、婚姻、国库、收入、影响力、牧群、正统性、军队、法律、修正、压力和家庭事实均从当前脚本输出重新获取。混合健康/临时状态的“其他特质”保守留在 Runtime，避免冻结疾病或伤势。
- 分离操作保留原始条目文字，复用原脚本隐私过滤与关系结果。无法识别的自定义或其他语言格式完整保留为每轮 Runtime 内容，不猜测删除字段。
- `stableDescriptionCache` 继续存在，但新命名空间只缓存稳定文本；脚本路径、人物、参与者或身份变化时更新。旧的完整人物缓存不会进入 v7。
- 主模板 `character_base` 可能包含自定义实时字段；v7 下使用当前人物并移到 Runtime 尾部，避免旧 `stableProfileCache` 冻结现状。
- Family Fact 构造器、Resolver、Action 请求构建/执行、Summary 指令和 Memory/Worldline 召回选择未修改。

## 默认开关与回退

首次启动本补丁用 `chatPromptRuntimeProfileVersion=1` 完成一次启用迁移。此后玩家关闭开关会持久化，重启不再重新开启。

| Layout | Runtime Profile Split | 实际 Anchor |
| --- | --- | --- |
| 开 | 开 | `VOTC_CACHE_ANCHOR_v7` |
| 开 | 关 | `VOTC_CACHE_ANCHOR_v6` |
| 关 | 任意 | `VOTC_CACHE_ANCHOR_v5` |

诊断页提供第三个可操作开关。新 Anchor 会产生正常冷启动，不能把首轮作为缓存回归结论。主题继续使用 parchment/knight/ink（游牧/骑士/水墨）；新增控件沿用现有样式，本轮验证了打包 DOM 与导航，三主题人工视觉仍待确认。
