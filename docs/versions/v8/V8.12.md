# V8.12 第一部分：安全收口与 Temporal Archive 底座

基线：`702fb7ead3b493efeba964d05d2899a01163371d`（V8.11.1）。

<a id="source-5c6f1d29141b--安全收口"></a>
## 安全收口

- Legacy Summary 缺少 `perspectiveMemoryIds` 时，以 Finalization、Owner 知情和 `isMemoryRelevantToPair` 的 Counterpart 相关性共同映射；缺失角色或无法判定的旧 Segment 阻止修改，不扩大遗忘范围。多人同一次 Finalization 中，删除 1↔2 保留 1↔3 及其他知情角色。
- 旧 Segment 没有显式 projection IDs 时，也按 Pair 过滤；没有参与者信息时仅接受恰好两人的 knownBy。多人、无可判定主题的 Segment 失败关闭。所有映射检查先于撤权。
- 摘要修改/删除后执行 `compactEpisodeReferences()`，移除已不存在的 Memory 引用及明确 `knownBy=[]` 的无用 Segment；有 Recovery、活动 Finalization、`auditRequired` / `recoveryRequired` 的记录保留。继续使用 V8.11.1 日志事务，不迁移 Memory Engine 可见 2.6 / 底层 2.5 合同。
- 冲突优先级为 Direct Observation > Live Runtime > Self Current > Checkpoint。实际生产的 `PRESENCE` 与 `LOCATION` 合并为地点冲突组，避免旧地点和本轮在场事实同时注入。未知或无授权观测仍不进入 Prompt。
- Self 的 SPOUSE / FRIEND / LIEGE / COURT_EMPLOYER / PRIMARY_TITLE 只从本轮 GameData 形成事实，缺失不回退旧 Checkpoint 的社会关系。旧 `consort` 文本不自动当成现任婚姻证明。非社会字段（例如日期限定的地点、生死）仍使用现有 Current Truth；Runtime 内容纳入主观视图缓存指纹。

<a id="source-5c6f1d29141b--archive-模块与提交合同"></a>
## Archive 模块与提交合同

新增主进程 `worldline/` 模块：

- `historical-query-projection.js`：定向字段投影，不复制完整 Parser Object；人物、头衔、战争分别保存结构化历史状态。
- `historical-checkpoint-index.js`：先读小型索引，按 checkpoint/date/character 定位、限量返回；节点按需加载。
- `temporal-archive-store.js`：独立 gzip 节点、checksum、写入门禁、不可变节点、原子 index commit。
- `temporal-archive-diagnostics.js`：索引数量、最近 20 个节点元数据、最新节点可读性；不返回完整人物正文到 UI。
- `temporal-archive-worker.js`：投影、压缩、磁盘和索引读取在独立 Worker 中执行，不在对话路径读取归档。

目录为 `votc_data/worldline-v8.12/history/<campaignId>/<branchId>/`，内含 `index.json` 和 `<gameDate>_<checkpointId>.json.gz`。复用现有 Canon Branch Registry 的身份和确认门禁，不另建分支推断规则。

写入必须有 ACTIVE 且已完成解析的合法 Checkpoint、有效 Campaign/Branch、与配置一致的来源、相等的 Source/Content SHA-256 以及非 STALE 新鲜度。`LOAD_BOUNDARY_CANDIDATE` 即使带 branchId 也不得写入。Checkpoint ID、Schema、日期、记录数量及 Parser 缺失字段均校验。旧 checkpoint 在启动时仍照旧读取为 STALE，成功重解析后才具备首次归档资格。

同日同 fingerprint 为幂等；同日不同 fingerprint 报 `HISTORY_SAME_DATE_REVISION_CONFLICT`，不静默覆盖。节点使用 `temp → fsync → close → rename`，随后以相同方式提交索引。索引成功才出现 `migrationCompleted=true` 与首节点 ID。索引失败留下的完整孤立节点只在内容 checksum 完全相同时被重试采用，不重写文件。

压缩节点读取上限 64 MiB，解压上限 256 MiB；索引上限 64 MiB、每分支 2,000 节点。超限阻止归档，不截断为伪完整历史；不影响现有 Current Worldline。读单个损坏节点记录 `HISTORY_CHECKPOINT_CORRUPT` 并返回空，其他节点仍可读；索引损坏报 `HISTORY_INDEX_CORRUPT`，不重新覆盖已有索引。

每分支写入使用独占 `commit.lock`；异常退出若留下锁，后续写入失败关闭。需先退出应用、确认没有写入者，检查索引/节点后再由维护操作处理残留锁；本阶段不自动破坏锁或重写历史。普通对话不依赖归档锁。

字段来源限制：地点保留来源原值；缺少可靠 primaryTitleId、government、claimantId、targetTitleIds 时为 null/空数组，不从模型或历史常识补齐。Definition ID 仅接受双向唯一映射。战争仅持久化现有可靠 CHARACTER Actors；不扩展 FACTION/TITLE Actor。索引 `totalDays` 为现有 `normalizeGameDate().serial` 日序，用于排序比较，不冒充 Live Probe 原始计数。

不修改或删除 `worldline-v8.4/checkpoint.json`、旧 Annual Delta、Memory、Canon。没有保存过的过去年度不补造；本阶段不导入 Annual Delta 为完整 Snapshot，也不实现历史 Retriever。

<a id="source-3574f173458a--已实现合同"></a>
## 已实现合同

- `AS_OF` 选择目标日期之前最近的有效节点，并明确返回实际 Checkpoint 日期；早于最早节点返回 `HISTORY_UNAVAILABLE`，未来日期返回 `HISTORY_FUTURE_BLOCKED`。
- `RANGE` 比较基线与范围内节点，只生成 Character、Title、War 的变化点。人物时间线覆盖地点、可靠头衔列表、领主、宫廷、生死、配偶与参战状态；朋友/宿敌因当前 Save Parser 没有可靠来源，显式报告未启用，不伪造支持。字段过滤在候选生成前生效，不会被 Top-K 先裁掉。
- Title 时间线覆盖获得/失去头衔、持有人、上级头衔与 Realm Root 变化。War 时间线覆盖活跃、首次出现、不再活跃与参战方变化；战争消失时只陈述“不再出现在活跃列表”，没有明确 `result` 时不推断胜负。
- WarActor 支持 `CHARACTER / TITLE / FACTION / UNKNOWN`。无法解析的一方仍保留为 opaque actor，并报告 `WAR_ACTOR_UNRESOLVED`，不会让整场战争消失。
- Historical Candidate 与 Current Candidate 分离，历史事实携带 Campaign、Branch、Checkpoint、`asOf`、有效期、来源与可见范围。历史 Canon 必须带日期或日期范围，并经过 Branch、ACL、Temporal 与冲突门禁；RANGE 按记录日期选择对应历史投影判断知情范围，不能用区间终点的新关系反推早年知情。
- 新增独立 Historical Scope：支持公开世界、公开领国、历史血亲、历史宫廷、个人记忆与公开战争；当前好友或当前配偶不能反推过去私密地点，无法证明时 fail closed。
- 历史缓存键包含 Campaign、Branch、Archive Revision、Checkpoint/Range、Query Plan、Responder、Policy 与 Canon Revision，不跨分支复用。
- 历史事实只进入 `worldline-turn-recall` Dynamic Tail。GLOBAL_STATIC、CONVERSATION_FROZEN、RESPONDER_FROZEN、Stable Kinship、Cache Anchor 与现有 Stable Prefix 不变。

## 实验记录：NPC 记忆作为历史头衔事件证据（第三阶段设计输入）

本次年度存档实验发现，年度 `autosave.ck3` 会在下一年度复用并覆盖旧文件。年度存档页面可以保留日期或路径状态，但不能据此恢复已经被覆盖的上一年度完整世界快照；切换到新的年度存档分支后，Temporal Archive 也可能从零开始。已被覆盖且未提前归档的 CK3 快照不能由当前文件反推恢复。

用户实机查看 NPC 记忆后发现，NPC 记忆会保留若干带日期的重大事件，并出现人物任职、授爵、头衔或官职变化等叙述。例如岳飞的记忆列表中存在带明确日期的任职与授爵相关记录。这说明 NPC 记忆可以作为“历史事件证据源”，用于验证某人物在某日期前后发生过头衔/官职变化；它不应被当作完整的年度世界快照或当前状态表。

对第三阶段的可行性判断：

- 可将 NPC 记忆按事件日期提取为追加式历史证据，并写入独立的 Temporal Archive 事件索引；年度 `autosave.ck3` 只作为当前状态和补充验证来源。
- 事件至少需要保留记忆持有者、事件主体、事件日期、观察日期、事件类型、头衔或官职标识、可读名称、原始记忆文本、来源检查点和置信度。相同事件被多个 NPC 记忆时必须去重。
- 历史查询只能使用不晚于目标日期的记忆事件；只有“获得/授予”而没有对应“失去/撤销”的证据时，不能直接推断该头衔后来持续保留。冲突或无法绑定稳定人物/头衔标识时应继续 fail closed。
- NPC 记忆是持有者视角的知情证据，且会随时间淡忘、只覆盖部分重大事件，可能存在重复、文本本地化差异和事件缺失。仅凭界面文本或 OCR 不足以建立可靠的历史索引，正式施工前必须确认原始存档字段能提供稳定 ID 和日期。
- 头衔变化可以优先由 NPC 记忆验证；地点、生死和完整当前头衔仍应优先使用 Current Runtime Truth 或结构化存档事实，不能由单条记忆泛化推断。

本实验结论：NPC 记忆适合作为第三阶段“历史头衔/官职变化事件索引”的候选底座，并能弥补年度存档覆盖造成的历史证据缺口；但截至本记录，尚未新增解析器、事件索引、持久化或 Prompt 接入，也未改变第二部分既有合同、Dynamic Tail 安排、实机 Gate 清单或 `V8.12 PART 2` 的未通过状态。上述内容只作为第三阶段方案设计依据。

<a id="source-9cc61a25cc56--核心结论"></a>
## 核心结论

character_memory_manager 是一个全局 Memory 数据库：

~~~
character_memory_manager.database[Memory ID] -> Memory 实例
~~~

Memory 实例本身没有直接的 owner 或 holder 字段。NPC 持有关系通过人物记录反向表达：

~~~
Character.alive_data.memories -> Memory ID 列表
~~~

因此，Part 3 不能只扫描 character_memory_manager.database，必须同时建立 Memory ID -> holder Character ID 的反向索引。

<a id="source-9cc61a25cc56--八项问题结论"></a>
## 八项问题结论

<a id="source-9cc61a25cc56--1-owner--holder-character-id"></a>
### 1. Owner / holder Character ID

管理器条目中没有 owner 字段。实际关系是：

~~~
Character.alive_data.memories -> Memory ID
~~~

例如 #50534 的 alive_data.memories 包含 7237，所以 7237 的 holder 是 #50534。

<a id="source-9cc61a25cc56--2-memory-type--category"></a>
### 2. Memory type / category

每条实例直接保存 type：

~~~
type=lost_title_memory
type=joined_allys_war
type=hanfan_zhiguan_xunguan_memory_1
~~~

categories 不重复保存于每条实例，而属于 CK3 的 Memory 类型定义。例如：

~~~text
imprisoned={
    categories={ negative prison intimidation }
    participants={ imprisoner }
    duration={
        years=memory_default_duration
    }
}

joined_allys_war={
    categories={ war martial alliance war_started }
    participants={ ally enemy }
    duration={
        years=memory_default_duration
    }
}

lost_title_memory={
    categories={ negative title }
    participants={ new_holder }
    duration={
        years=memory_default_duration
    }
}
~~~

<a id="source-9cc61a25cc56--3-event-date--created-date--duration--expiry"></a>
### 3. Event date / created date / duration / expiry

Save 实例实际保存：

~~~
creation_date=1141.8.5
end_date=1271.8.5
~~~

没有单独的 event_date 或 created_date 字段。当前 UI 已知记录的显示日期与 creation_date 一致，但不能因此断言所有 Memory 的事件发生时间都必然等于 Memory 创建时间。

duration 来自类型定义，end_date 是计算后写入的到期日期。当前实例没有单独的 expiry 字段。

<a id="source-9cc61a25cc56--4-participants"></a>
### 4. Participants

participants 是可选结构，键名表示角色语义，值是 Character ID，例如：

~~~text
participants={
    ally=50979
    enemy=49490
}
~~~

已确认的角色键还包括 imprisoner、new_holder、other_party 等。自定义 hanfan_* Memory 可以没有 participants。

<a id="source-9cc61a25cc56--5-title--war--position--character-结构化参数"></a>
### 5. Title / war / position / character 结构化参数

当前 Save 中确认存在：

| 类型 | Save 表现 | 含义 |
|---|---|---|
| Character | type=char identity=... | 角色 ID |
| Landed Title | type=lt identity=... | 头衔 ID |
| Value | type=value identity=... | 数值 |
| Flag | type=flag flag="..." | 原因或枚举 |
| Boolean | type=boolean identity=... | 布尔值 |

战争信息没有发现直接的 type=war 对象。战争 Memory 主要通过 Memory 类型、participants 和 war_* 变量表达。

当前 manager 数据中没有发现 type=position、type=office 或类似职位对象。自定义官职 Memory 的职位含义可能只存在于类型名和本地化中。

<a id="source-9cc61a25cc56--7-不同-npc-是否引用同一个事件"></a>
### 7. 不同 NPC 是否引用同一个事件

当前 autosave.ck3 的统计结果：

| 指标 | 数值 |
|---|---:|
| manager Memory 条目 | 78,739 |
| 角色 Memory 引用 | 75,803 |
| 引用缺失 | 0 |
| 被多个角色共同引用的 Memory ID | 0 |

同时发现不同 NPC 之间存在 type + creation_date + end_date + variables 完全相同、但 Memory ID 不同的记录。

因此当前证据支持：

> 同一底层事件如果被多个 NPC 记住，会分别生成独立 Memory；Save 中没有可用于跨 NPC 共享的事件 ID。

后续实现必须保留 holderCharacterId 和 memoryId，不能把相同内容的 Memory 直接合并成一个公共事实。

<a id="source-9cc61a25cc56--8-memory-消失后的-save-行为"></a>
### 8. Memory 消失后的 Save 行为

对比同一局：

- autosave_2.ck3：1159.1.1
- 当前 autosave.ck3：1161.1.1

旧存档中有 2,511 条在两个检查点之间到期的 Memory，全部不再出现在新存档的 character_memory_manager.database 中。

当前没有发现：

~~~
expired=true
status=expired
tombstone
~~~

因此，在当前 CK3 版本和这组存档中，Memory 到期后的行为是：

> 从 manager 数据库物理删除，而不是标记 expired，也不是保留 tombstone。

当前 Save 仍存在一部分没有角色反向引用的 manager 条目，但它们是未引用的完整 Memory 记录，不能直接视为 expired tombstone。

<a id="source-9cc61a25cc56--对-part-3-的直接影响"></a>
## 对 Part 3 的直接影响

后续正式施工应遵守以下边界：

1. 解析全局 character_memory_manager.database，建立 memoryId -> memory。
2. 扫描所有角色的 alive_data.memories，建立 memoryId -> holderCharacterId。
3. 保留 Memory ID、holder、participants 和 typed variables，不能只保留中文摘要。
4. 将“事件去重指纹”和“NPC 知识持有关系”分开：相同事件可以有多个独立 NPC Memory。
5. 对 lost_title_memory 优先读取 landed_title、lost_titles、new_holder 和 creation_date，用于历史头衔变化验证。
6. 对自定义 hanfan_* 类型设置类型定义/本地化解析；没有结构化头衔或职位 ID 时必须标记证据不足，不能猜测。
7. 在 Memory 到期前进行 Shadow 归档，否则到期后的 Save 无法恢复该 Memory。
8. 将 Memory 作为 NPC 的主观知识证据，而不是直接当作全局 Current Runtime Truth。

<a id="source-9cc61a25cc56--当前限制"></a>
## 当前限制

- 本文分析的是指定 Save 快照和当前本机 CK3 类型定义，不代表所有 CK3 版本、DLC 或 Mod 都完全相同。
- hanfan_* 自定义 Memory 的完整类型定义和本地化不在当前 Save 实例中，需要在后续施工阶段继续定位其 Mod 源文件。
- 本文没有修改 game-state-adapter.js，因此应用目前还不能通过正式 Worldline DTO 使用这些 Memory 数据。

<a id="source-af916fa119a6--已实施合同"></a>
## 已实施合同

- `temporal-anchor-extractor.js` 只从终局原始消息及当场 CK3 游戏日期解析明确年份、年月日、相对年/月/日等时间表达；保留来源 `messageIds`、精度、绝对日期窗口和 `event/past_conversation/unknown` 角色。含糊、假设、无有效日期或无来源 ID 时不制造 Event Time。模型自行返回的时间字段不作为证据。
- `memory-engine.js` 在 Final Summary 质量校验后按来源消息 ID 把时间引用绑定到 Segment 和持久 Memory；本地时间解析失败只令引用为空，不能令有效正文摘要提交失败。恢复快照保留对话日期与 `campaignToken`。`perspective-projector.js` 仅从各 Owner 可见的 Segment/Memory 投影引用，并校验引用与投影一致；`game-data.js` 在 schemaVersion 2 摘要顶层写入 `temporalRefs` 与战役标识，原 `summary.date` 继续表示对话发生日期。
- `memory-store.js` 把摘要顶层引用读取为 `memory.provenance.temporalRefs`。不同时间证据的同文投影不合并；旧摘要没有新字段仍可读取，原无引用摘要的会话键保持原样。编辑摘要正文保留原来源引用，删除与缓存失效后对应索引消失；不扫描旧正文补造年份。
- `summary-date-index.js` 建立 Conversation Time 与 Event Time 双索引。Event Time 仅接收当前 Campaign、当前 Owner、有 Segment 或持久 Memory 绑定且 `timeRole=event` 的引用；Conversation Time 保留旧摘要日期兼容，但旧摘要无 Campaign 标记不能进入有标记战役。`fuzzy-temporal-resolver.js` 以当前 CK3 日期解析查询窗口，区分事件、对话及混合意图，保存最近成功回复的同场时间焦点。场景、战役、对话或话题切换会终止继承；单纯游戏日期推进不会清除绝对时间焦点。
