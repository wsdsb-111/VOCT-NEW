# V8.15.2 修复5实施报告

日期：2026-10-09。比对基线为 `06246a3ab3eb27eabf924a5dcb5e231bc5f4fa3f`（修复4）。本轮仅处理停机回执恢复、DATE 扫描性能及年度预算；设计文件中的施工要求作为修复依据，未扩大到 V9、SQLite、Workshop 或 Three-Mod。

## 根因与生产修复

### F5-P1-01：停机回执

`LetterLogReader` 启动时从 EOF 开始，因此 App 停机或 reader 暂停期间已经追加的合法回执不会进入原实时处理入口。隔离真实 Manager/reader/RunFile/finalization 夹具在补丁前稳定失败：重启后原接收锁仍存在，未生成摘要。这是自动化复现，不是新 CK3 实机事故。

Reader 仍从 EOF 监听。新增 `letter-receipt-recovery.js`，仅在启动/监听重启时处理已写入 Effect、尚未归档的带 token 原信件。新投递在写 Effect 前持久化原物理日志身份、设备、LOAD 字节边界、发送时 EOF 和末尾锚点摘要；恢复只读该发送位置后的完整行，单次最多 32 MiB、每块 64 KiB，并让出事件循环。重验当前 Campaign/玩家、原双方来源快照、全部既有 receipt 条件、文件身份及最新物理 LOAD。当前 NPC 可以改变，归档双方仍使用发信快照。

缺证明、错身份/日期、仅 RUN_ACK、轮转/截断、新 LOAD、未写完的 LOAD 或扫描超限均保留 pending 和锁，不归档、不重发。旧 pending 没有新增发送证明时不能安全自动补消费；仍支持原实时回执，单封人工补建沿既有明确授权流程。状态提供 `RECOVERED_VERIFIED`、`NO_VERIFIABLE_RECEIPT` 或 `AMBIGUOUS_OR_STALE` 与原因，不输出回信正文或原始日志。

实时与恢复共用 `letterAcceptanceTransition`；恢复候选在锁内重新验证。pending version 4 保持，新增字段兼容；写入改为同目录临时文件、fsync、原子 rename。接收证明先落盘，再转 SENT 并捕获既有归档任务；捕获成功后才移除 pending。证明落盘后、归档捕获前崩溃（包括 SENT/锁已释放）可在重启时续同一任务。失败只续记忆，不重建宝物、不生成新回信；恢复本身不推进下一封投递。

### F5-P2-01：DATE 扫描

旧扫描对不断增长的日志同步倒扫到 LOAD；DATE 高频到来时重复读取历史字节。新增 `letter-date-session-scanner.js`：首次异步分块扫描，之后验证固定 256 字节锚点并只读新增内容。同路径并发扫描合并；UTF-8 偏移按 Buffer 字节计算，半行保留到 LF；同 token 的新物理 LOAD 清除旧日期。轮转、截断、文件扫描中变化或锚点不符返回 UNKNOWN，下一次冷恢复；不完整 LOAD 禁用旧 DATE，待完整后再增量恢复。异步等待后复验 reader 身份，退役 callback 不推进日期。

`lastDateScanResult.scan` 包含模式、bytesRead、durationMs、maxBlockMs、backscanBytes、日志身份摘要和边界是否已知。冷扫描期间显示 `DATE_SOURCE_RECOVERING`，不以旧日期投递；首次写 Effect 前若扫描失效，立即停止写入并保留待发信件。未调整 native DATE 桥、RunFile/ACK 或退休计时器。

### F5-P2-02：年度预算

`memory4-derived.js` 原先让 Year 和 Life 共用 1000 Token 门槛。现按 kind 统一选择：Year 硬限 1500、目标 1200；Life 片段硬限 1000、目标 700。免压缩判断、压缩提示、响应校验和添加来源标注后的最终校验均使用对应硬限；最终 tokens 仍由真实文本计数。来源 ID 恰好一次、否定/条件/计划、获知日期标注、授权、Forget、修订及手工覆盖保护保留。Recall 400、压缩 maxTokens 4096、Provider 设置和稳定 Prompt/cache 块保持。
