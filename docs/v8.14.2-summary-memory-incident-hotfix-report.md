# V8.14.2 摘要编辑与长期记忆事故热修

## 范围与证据

2026-10-04，用户报告普通摘要无法编辑、连续对话后 Detail/Year/Life 仍为空。根代理只读核对本地归档状态和脱敏日志；实现与独立 QA 子代理使用 GPT-6 Luna Max。没有更换根模型、修改用户摘要、调用真实 Provider、操作 CK3 或重启运行中的用户实例。

- Renderer 将 Memory4 的归档只读限制递归施加到整个 Legacy 摘要树，清除了普通摘要按钮的事件处理器。原 `updateSummary` / `deleteSummary` 并不要求活动对话，并已有 Official 逐项保护。
- 后台确实执行了 `memory4_durable` 请求；日志连续出现 `memory4_candidate_rejected / unknown_entity`，随后被记录为 `NO_DURABLE_CONTENT`。读取时 Owner 95735 有六次空归档、零 Detail。源模型候选未保存在日志中，不能断言每次拒绝究竟来自 Owner ID、字符串 ID 还是未知第三方。
- 代码可复现：实体白名单仅含引用片段的 speaker/entityIds，漏掉已证明知情的当前 Owner；Prompt 又未区分实体授权与在场 ID。所有候选被拒绝后，归档仍按空成功提交并删除恢复快照，Year/Life 因没有有效 Detail 而没有输入。

## 精准修复

- `renderer/memory4-manager.js` 移除对普通 Legacy 内容的禁用包装。普通摘要可在对话结束后编辑/删除；Official 仍由 Renderer 和后端保护。Memory4 Detail、Disclosure、派生重建及重压缩继续要求活动 Owner/Campaign/版本，不放松归档写入门禁。
- `memory4-contract.js` 只在所有引用片段的 `knownBy` 已包含当前 Owner 后，将该 Owner 纳入实体白名单。不将所有在场者或其他 Owner 自动授权；实体 ID 仍必须是原始正整数，不猜测或转换字符串 ID。
- `memory4-coordinator.js` 的抽取 Prompt 分开提供 `allowedEntityIds` 与 `participantIds`，说明 Owner 可用于相关的自身/听者事实，出席不等于实体授权。所有分块汇总后，若无有效条目或承诺状态转移且有未知实体拒绝，返回 `EXTRACTION_FAILED / memory4_response_no_valid_entries` 并保留恢复快照；混合结果保留有效条目/状态转移。真正的空结果仍正常归档。
- Legacy 单篇重压缩同样区分全候选校验失败和真正无内容；失败保留原摘要，不改旧摘要仅状态转移的提交范围。`memory-trace.js` 仅补安全 Owner ID 与拒绝数量，不记录候选正文。
- 未改 Disclosure 源文证明、日期/ACL、年度/人生来源合同、冻结 Recent2、Cache Anchor、Prompt Block ID、GLM 静态布局或包版本。Memory Engine 4.0 可见标签、`engineVersion: 3.0`、摘要 2.5 存储继续兼容。

## 实机边界与旧数据

旧的误记空归档没有自动回填或删除。它们缺少完整原始候选，不能据此伪造长期事实；已有 Legacy 原文和可恢复快照继续保留。重启应用后，新对话终局使用修复后的抽取合同；历史内容只有具备可核验来源时才可在活动上下文中由用户确认重压缩，年度/人生仅从有效 Detail 派生。普通摘要手工编辑不等于自动重建全部 Memory4。

真实 Provider 是否按新 Prompt 返回合法候选、CK3 对话后实际生成率及 Soak 仍交用户复测。不保证每场闲聊都产出长期事实，也不补造未导出的官方追忆。本轮离线与隔离窗口通过不等于实机验收或 Full Freeze。
