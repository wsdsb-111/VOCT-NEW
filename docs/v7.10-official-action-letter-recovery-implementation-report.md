# VOTC v7.10.0-RC1 至 RC6 Final Rev.2 Candidate 实施报告

## 版本基线

- CK3 Workshop：2.0.4
- 外挂 UI/package：2.0.4
- VOCT 核心：v7.10.0
- 发布状态：V7.10.0-RC6 Final Rev.2 Candidate（未宣称 Stable）
- Memory Engine：2.5
- Action System：Official VOTC 2.0.3
- Letter Kernel：Official VOTC 2.0.3 + Delivery Recovery 2.0 外层

## Action System

V7.10 删除自研 AE3/AE4、Candidate Gate、Semantic Resolver/Rescue、Precision Judge、Performance/Precision、Explicit Pending、Social Consequence 和 Engine Version Router 的运行文件。官方 2.0.3 的 ActionEngine、ActionPromptBuilder、Registry、Sandbox、EffectWriter、RunFileManager、i18n、Schema、response healing 与 28 个 standard actions 成为唯一运行基线。

动作只在 NPC 回复完整结束后执行一次 `ActionEngine.evaluateForCharacter(conversation, npc, signal)`；玩家消息不触发 Action 评估。结构化 Schema 名保持 `votc_actions`。首个 v7.10 基线不加载 custom actions，但不删除用户目录中的自定义文件。操作页不再提供 Action Mode，统计页只标识 `ACTION SYSTEM — Official VOTC 2.0.3`。

`scripts/test-v7.10-official-action-system.js` 对官方安装包进行 Prompt、完整/精简 Schema 对比，校验 28 个动作的规范化 SHA256、Registry 基线、Effect Writer 输出、唯一 NPC 调用点以及旧运行目录清空。

## 实机前 P1 兼容修复

`LLMManager.sendActionsRequest()` 保持官方结构化请求边界，但不再覆盖所选动作 Provider 的 `temperature`、`max_tokens` 或 `thinking`。RC1/RC2 的 DeepSeek 基线由 `DeepseekProvider` 执行 `json_schema → json_object + schema injection`；RC3 仅对 `votc_actions` 增加可回退的 Schema Delivery Mode，并继续只在该适配层关闭 thinking。普通 Chat 与 Summary 请求保持原参数。

官方 `z_leavesConversation.js` 未修改。新增的 `Conversation.createCharacterLeavingSummary(characterId, summaryPrompt)` 只负责通过 Summary Provider 生成字符串：它以 Memory Engine 2.5 的 Presence 窗口筛选人物实际可见历史，中途入场前和暂离期间内容不会进入 Prompt；共享滚动摘要只在人物从首条消息起连续在场时复用。该方法不保存摘要、不删除人物，异常时返回 `null`，由官方动作继续执行离场。

审批的 `none` / `non-destructive` / `all` 运行语义不变，中文标签明确为“全部动作手动确认 / 仅危险动作需要确认 / 自动执行全部动作”。首次实机烟测按规格使用 `all`。

新增 `scripts/test-v7.10-action-provider-parity.js`、`scripts/test-v7.10-deepseek-action-compatibility.js` 与 `scripts/test-v7.10-official-leaves-conversation.js`，分别覆盖参数直通、DeepSeek 局部适配，以及正常三人离场、摘要失败仍离场、中途入场 5–7 轮和暂离返回后的 Presence 边界。

RC2 保留官方 ActionEngine 的 Full/Minimized variant 选择语义，不在 Action Core 内增加 Provider 特判。DeepSeek Action Provider 在设置仓库边界统一返回 `useMinimizedActionsSchema: false`，即只使用官方 Full Schema；不承诺 Full/Minimized 之间的绝对体积关系。`temperature=0.1`、`max_tokens=512` 仍是独立 Action Provider 推荐配置，不覆盖普通 Chat 或 Summary。

Action 用量记录新增 `action_system_intro`、`action_recent_messages`、`action_recent_actions`、`action_roster`、`action_available_actions`、`action_provider_schema`、`action_examples` 与 `action_final_instruction` 八个旁路分块。用量页把区块自身 Token 与最早断点造成的下游未命中分开显示，并明确该值是有序前缀估算而非服务商缓存断点遥测。现有用户数据中的旧 Action 记录没有 RC3 分块元数据，不能作为 RC3 Token 验收结果。

## RC3 Action Token Transport

Official ActionEngine、ActionPromptBuilder、28 个标准动作、官方 Full Schema 对象、本地校验与 response healing 均未修改。DeepSeek `votc_actions` 新增两个 Provider Transport 模式：

- `official_full_injected`：保留 RC2 的 Full Schema Prompt 注入，用于真实 A/B 基线和立即回退。
- `optimized_local_validation`：默认模式。ActionEngine 仍构建官方 Full Schema，并把它保留给本地校验、healing、analytics fingerprint 与 parity；DeepSeek HTTP 请求只使用 `json_object`，不再重复追加整份 Schema 消息。

30 组确定性传输检查覆盖给钱、囚禁、脱衣、换场景、表情、受伤、无动作与关系类别，确认 optimized 模式不改变官方 messages、Full Schema 对象或 Action Core，测试样本估算序列化 Token 从 7187 降至 3347。该结果只是静态传输与估算验证，不是 30 次真实 DeepSeek Recall A/B，也不能证明 Raw Average 已达到 4200 Gate。

DeepSeek-only Stable Prefix Adapter 只重排 messages copy，不修改 ActionPromptBuilder；顺序为 intro、available actions、examples、roster、recent actions、recent messages、final instruction。`deepseekActionStablePrefixOptimization` 默认 `false`，必须完成至少 50 次真实 A/B 并满足 Recall、Wrong Target、Critical FP、Cache Hit 与 Cache Miss Gate 后才允许考虑默认开启。

## Letter Delivery Recovery 2.0

LetterPromptBuilder 恢复官方 2.0.3 的 block 顺序和行为，不再向官方 Prompt 内核注入自研的 routed retrieval 或最小 Prompt fallback。Letter Delivery 保持官方原子 Effect：`create_artifact`、`votc_letter_artifact`、全局 `votc_latest_letter` 与 `message_event.362`。

可靠性外层保留 100/200/350/600/1000 ms 有界载荷重试、`pending-letters.json` 跨重启恢复、`VOTC:DATE` 推进和信件摘要写入。RC3 的 Pending-only Date Tracker Supervisor 每 5 秒检查 debug.log 存在性、identity、size/mtime、tail state 与最后日期时间；truncate、recreate、tail failure 或 stale 会重启 tail，并只扫描日志尾部最多 1MB 的最新日期 Marker。向前补追无论跨度都保留 Pending 并投递到期信件，只有向后时间旅行才清理回滚日期之后创建的信件。状态页提供手动 debug.log 日期重同步，并显示当前日、扫描日、来源、tail 状态和扫描时间。

DeepSeek Letter 不新增第四层自动重试；Provider 原有 `retryWithBackoff` 在最终失败时附带 provider、model、error class、HTTP status、code/cause、attempt count 与 retryable。`GENERATION_FAILED` 可使用原 letterId 和持久化原始 Prompt context 手动重试；进入 Pending、Effect 写入、已投递或正在重试的同一 letterId 会拒绝重复生成。

到期信件按单通道串行投递；写入 `letters.txt` 后状态为 `EFFECT_FILE_WRITTEN`，收到 CK3 的 `LETTER_ACCEPTED` 后标记 `SENT/DELIVERED` 并清除待投递记录。Workshop 源码对照表明该信号由事件窗口 `on_start` 自动复制，只能证明 Popup 启动流程已进入，不能证明玩家点击接受或 Artifact 已正常显示。摘要失败不阻断已经到期的 Effect 写入。

状态诊断额外返回 `awaitingAcceptanceLetterId`、`effectFileExists`、`effectFileAge`、`lastDateLogReceivedAt`、`storedLettersCount`、Effect Payload 真值、creator scope、`effectWrittenAt`、`popupTriggeredAt`、`letterAcceptedAt`、`acceptLatencyMs` 与 `suspicious_immediate_letter_acceptance`。Diagnostic 2.2 为每个 A/B/C/D 写入唯一 `VOTC:LETTER_DIAG/<stage>/<id>` Marker，并把状态拆成 `WRITE_OK`、`WAITING_FOR_CK3_EXECUTION`、`EXECUTION_CONFIRMED`、`ARTIFACT_VISUAL_CHECK_REQUIRED`、`PASS/FAIL` 或 `RUN_FILE_NOT_EXECUTED`。B/C/D 只允许从已知 Letter ID 下拉框选择，并严格在前一阶段收到 Marker 且完成人工可见结果确认后解锁；正式 Letter 管线繁忙时拒绝诊断，避免覆盖 `letters.txt`。`scripts/test-v7.10-letter-delivery-recovery.js`、`scripts/test-v7.10-rc2-letter-effect-diagnostics.js`、`scripts/test-v7.10-rc3-letter-date-tracker.js`、`scripts/test-v7.10-rc3-letter-provider-retry.js` 与 `scripts/test-v7.9.2-letter-payload-race.js` 覆盖这些静态合同和恢复边界。

## RC4 Letter Transport Recovery 与 Numeric Gate

RC4 不修改 ActionEngine、ActionPromptBuilder、28 个标准动作、Schema、Provider Action 参数、Stable Prefix 默认值或 Action EffectWriter。新增 `letters/letter-effect-transport.js` 只在 Letter 外围提供 `legacy_letters_file` 与 `votc_run_file` 两种承载：A1 向 `letters.txt` 写入唯一 Transport Marker，A2 必须调用既有 Action RunFileManager 向 `votc.txt` 写入 Marker并保留 `mcc_event_v2.9003` 根触发合同。只有持久化记录真实 A1 `RUN_FILE_NOT_EXECUTED` 和 A2 `PASS` 后，正式 Outbound Letter Effect 才切换到 `votc.txt`；其他完整判定矩阵均保持 `letters.txt`。Inbound Payload 请求仍使用原协议，官方回信 Effect Body 逐字节保持 RC3 基线。

Letter Pipeline 入口现在先验证 `letterId`、`content`、`totalDays` 与 `delay`。两个数值只接受有限、非负整数或对应数字字符串，且相加后的 `expectedDeliveryDay` 仍须有限整数；失败 Payload 完成既有五段短延迟重读后以 `INVALID_LETTER_PAYLOAD_NUMERIC` 结束，不进入 `storedLetters`、`pending-letters.json` 或日期计算。加载旧 Pending 时，非法记录移入 `invalid-pending-letters.json` 并标记 `LEGACY_INVALID_PENDING`。所有日期 UI 都以 `Number.isFinite` 防御，异常统一显示“日期数据异常”。

Diagnostic 2.3 顺序固定为 A1 `letters.txt Execution`、A2 `votc.txt Execution`、A3 `Minimal Artifact creator=root`、B `Creator Scope`、C `Global Variable`、D `Message Event`。A1/A2 只依赖 CK3 Marker，A3/B/C/D 还需要人工确认可见结果；B/C/D 继续使用 Known Letter ID 下拉框，正式投递繁忙时全部锁定。已完成或超时的诊断命令会被精准移除，不带入下一阶段。状态页另提供带确认的一键清除待送达功能，清理 `storedLetters`、`deliveryInProgress`、等待 ACK 锁和对应 Letter Effect，并保留状态历史为 `cancelled`；`votc.txt` 中无关的 Action 命令不会被手动清理删除。

## Sol 最终审查与 Letter 契约裁定

官方 Desktop 2.0.3 的 `writeLetterEffect` 与当前实现逐项一致：`message_second_scope_<letterId>`、`votc_latest_letter`、`votc_letter_artifact`、Artifact 类型/visuals/modifier 和 `message_event.362` 均未漂移。Workshop 2.0.4 在 `message_event.360` 写入同名收件人 global scope，`message_event.362` 使用同名窗口，`letter_message` 从全局 `votc_latest_letter.Artifact.GetDesc` 读取正文。因此没有发现 Desktop 2.0.3 与 Workshop 2.0.4 的命名或 Effect contract drift，不批准修改官方 Letter Effect。

Popup/ACK 的静态根因已经确认：`message_event.362.desc` 本身是 `VOTC:LETTER_ACCEPTED`，而 `event_window_widget_message_open.gui` 在 `widget_show.on_start` 调用 `EventWindowData.CopyToClipboard`，之后才在 `on_finish` 创建 `votc_letter.gui`。所以快速 ACK 是窗口启动信号，不是玩家接受操作；自定义信件窗口本身只有点击关闭后才执行 hide/clear。Artifact 缺失仍必须根据 A/B/C/D 的真实 CK3 结果裁定，静态源码不能替代该实机证据。

## RC5 Action Recall 与 Token 优化

RC5 不修改官方 28 个 `z_*.js` 动作、Action Registry、官方 Schema、本地 Validator、Action EffectWriter 或 Letter RC4 管线，也不恢复 Regex Detector、Keyword Gate、本地 Rescue、候选过滤、Top-K、Secondary Judge 或 Semantic Resolver。每个有效 NPC 回复仍只进入一轮完整官方 Action Selector。ActionEngine 的 RC5 改动仅在既有 `check()`、结构化选择、审批和执行边界旁路采集诊断，不改变动作是否可用、是否进入官方 Prompt 或如何执行。

Critical Action Availability Diagnostics 固定观察 `isInjured`、`characterIsKilled`、`becomeFriendsWith`、`becomeLoversWith`、`becomeSoulmatesWith`、`becomeRivalsWith`、`becomeNemesisWith`、`becomeBloodBrothersWith` 与 `becomeBestFriendsWith`。每条记录包含 `actionId`、`wasAvailable`、`validTargetCharacterIds`、`sourceCharacterId`、`availabilityReason`、`selected`、`selectedTarget` 和 `validationResult`，并区分既有状态、前置条件、冲突关系、校验拒绝和 Effect 失败。线上运行时不会根据对话文本自造 Ground Truth；“可用但未选择”只标为待裁定，只有明确标注的回归或实机样例才能归类 `SELECTOR_MISS`、`UNREPRESENTABLE_BY_OFFICIAL_BINDING`、Wrong Target 或 Critical False Positive。

DeepSeek 新增 `deepseekActionStateTransitionRecallOverlay`，默认 `false`。开启后只在独立兼容层插入稳定块 `action_state_transition_rules`，版本为 `state-transition-overlay/v1`，当前静态估算 414 Token。规则严格覆盖已完成的新受伤、官方死亡 SOURCE=受害者/TARGET=凶手绑定，以及明确建立或双方接受的正式关系；威胁、计划、问句、尝试、落空、阻挡、假设、既有旧状态、普通暧昧/友善/愤怒/辱骂和单次性行为均不触发这些状态转换。

Stable Prefix 仍由 `deepseekActionStablePrefixOptimization` 独立控制且默认 `false`。RC5 Stage A 为 Overlay 关 / Stable 关，Stage B 为 Overlay 开 / Stable 关，Stage C 为两者都开；统计不把同时切换得出的结果当成单变量结论。Stage C 的消息顺序固定为 intro、`action_state_transition_rules`、available actions、examples、roster、recent actions、recent messages、final instruction。兼容层先按官方消息槽位生成并验证 `blockId`，排序只读取 `blockId`；消息数量、角色、内容合同、ID 或唯一性无法验证时，Overlay 不插入、Stable 不实施，并以 `stablePrefixApplied=false` 和失败原因保持官方消息顺序安全回退。`blockId` 不发送给 Provider。

用量页新增“关键动作召回”和“RC5 Action A/B/C 元数据”面板，显示来源/目标、可用性、选择、校验/执行结果、Overlay 请求/实施、Stable 请求/实施、回退原因，以及各 Stage 的平均输入、缓存命中率和平均未命中 Token。`scripts/test-v7.10-rc5-action-recall.js` 与 `scripts/test-v7.10-rc5-overlay-stable-prefix.js` 覆盖九动作旁路观测、Ground Truth 分类边界、死亡绑定、Overlay Token 上限、A/B/C 隔离、`blockId` 顺序、异常安全回退、统计和 UI 静态合同。

## RC6 最终信件系统修复

RC6 只修改 Letter 外围；ActionEngine、ActionPromptBuilder、Registry、Schema、Recall Overlay、Stable Prefix、Chat Prompt、Memory Engine、Presence、Final Summary 以及 Letter/Reply/Summary Prompt 均保持 RC5 基线。Workshop 2.0.4 实机已确认独立 `run/letters.txt` 不可靠而 `run/votc.txt` 可执行，因此正式 Outbound Transport 固定为 `votc_run_file`，A1 只保留为历史 transport diagnostic，不再控制正式投递回退。

新信通过 Numeric Gate 后记录 `payloadGameDay`、`trackerGameDayAtCreation`、`reconciledGameDayAtCreation`、`deliveryBaseDay`、`dateDelta` 与 `dateSourceDecision`。Rev2 已按用户裁定覆盖旧 RC6 Tracker-base 合同：`deliveryBaseDay` 固定为已校验的 Payload `sendDay`，`expectedDeliveryDay=sendDay+delay`；实时 `VOTC:DATE` 只作为运行期当前日权威值和偏差诊断。fixture `payload=419184 / tracker=419198 / delay=7` 因而得到 `419191`，不再保留旧版 `419205` 结论。

Diagnostic 3.0 将 A3 升级为 `A3 Official-Parity Artifact`：在显式 `root` character scope 中复用正式 Letter Artifact helper 的 `type=journal`、`visuals=scroll`、`modifier`、`wealth` 与 `save_scope_as` recipe，并使用 Workshop 已存在的 `votc_huixin_title1` localization key。A3 分别监听 PRE、POST 与 `scope:votc_test_letter` 存在性 Marker，区分 `RUN_FILE_NOT_EXECUTED`、`ARTIFACT_EFFECT_ABORTED`、`ARTIFACT_SCOPE_NOT_CREATED` 与 `ARTIFACT_NOT_VISIBLE`；A3 PASS 后才解锁真实 Letter ID 的 B/C/D。正式 `message_second_scope_<letterId>`、`votc_latest_letter`、`votc_letter_artifact` 与 `message_event.362` 语义未修改。

Inbound 重试继续使用 100/200/350/600/1000 ms，每次只记录 attempt、时间、payload 是否存在、Letter ID、正文类型/长度、最多 40 字预览、原始日期字段和 validation error。结构仍不完整时进入 `PAYLOAD_INCOMPLETE_TIMEOUT`，普通合同错误与数值错误继续分别使用 `INVALID_LETTER_PAYLOAD` 和 `INVALID_LETTER_PAYLOAD_NUMERIC`。超时记录使用 `invalid_payload_*` 错误 ID，永不进入正式 Pending；状态页的“重新读取信件数据”只复用原 trigger context，不重新发起 CK3 payload 请求，也不允许并发重读。

## RC6 Final Rev.2 生命周期与亲属关系修复

共享 `votc.txt` 改由持久化串行 Run Command Queue 管理。Action Effect、Letter Effect 与 Conversation Close 均记录 `commandId`、owner、kind、effect、writtenAt、status 与专属 ACK Marker；物理文件同一时刻只写一个顶层命令，末尾由 CK3 effect 输出 `VOTC:RUN_ACK/<kind>/<commandId>`。匹配 ACK 后才精准移除并推进下一条，错误 kind、错误 ID 和通用 `VOTC:EFFECT_ACCEPTED` 均不能清队列；App 重启会恢复未 ACK 命令。会话初始化和结束处的全文件 clear、500ms 定时 clear 已删除。

`letters.txt` 继续是官方 Date Producer 入口，`votc.txt` 只承载 Effect/Command。Conversation Close ACK、Pending Letter 启动、真实 STALLED 与用户手动同步可幂等调用 `ensureDateProducerRunning()`；恢复 effect 先在 CK3 检查 `talk_scene`，再触发 `mcc_event_v2.9998`，只有后续收到实时 `VOTC:DATE` 才标记恢复。状态拆分为 Tail Consumer、Date Producer、Last Observed Marker、Marker Age、Last Progress 和 Source；重复同日 Marker 显示 `LIVE_NO_PROGRESS`，扫描历史 Marker 只能用于 reconcile，不能伪造 fresh timestamp 或 `HEALTHY`。

第三方人物 Profile 不再 first-wins。Canonical Aggregator 按角色 ID 合并完整 Character、各参与者 parents/children/siblings 中的 gender、exact birth date 与 owner relation evidence；完整 Character 字段优先，同级证据冲突时输出 `RELATION_CONFLICT_GENDER` / `RELATION_CONFLICT_BIRTHDATE` 并降级为 unknown/null。Mentioned Character Context 与 Current Relationship Authority 共用一个 Resolver，固定 `child > parent > sibling`，长幼优先 exact birth、仅无 exact 时才使用不同整数 age；未知性别或冲突日期只能输出“子女／手足／兄弟／姐妹”等中性或不分长幼称谓。运行时保留 `RELATION_PROFILE_MERGED`、`RELATION_CONFLICT_TYPE`、`RELATION_AGE_UNRESOLVED` 和 `RELATION_RESOLUTION` 诊断。

## Run Command Queue 启动恢复加固

RunFileManager constructor 现在只执行路径解析和状态加载，Conversation 生命周期不再拥有 Queue recovery。主进程在 Electron ready 阶段先扫描 debug.log 尾部最多 4MB 的 `VOTC:RUN_ACK/<kind>/<commandId>`，再建立实时 Tail，并在 Tail 就绪后第二次扫描闭合启动间隙；只有完成两次 reconciliation 后才调用 `initializeAfterAckReconciliation()`。历史 ACK 只能从 FIFO 队首连续消费，错误 kind、错误 ID 或缺少队首 ACK 都不能越过。已在 CK3 执行但 Electron 未消费 ACK 的命令会以 `ackSource=startup_debug_log_reconciliation` 收口，不会盲目 replay。

队列状态文件升级为 version 2，使用同目录临时文件与原子 rename；enqueue 先 durable 再允许 dispatch，落盘失败会回滚内存并抛出 `run_command_persist_failed`。active command 记录 `lastWrittenAt` 与 `writeAttempts`。30 秒未收到 ACK 时，Watchdog 先做一次历史 ACK 扫描；仍无法确认才进入 STALLED，绝不自动重放。状态页只暴露不含 Effect 正文的命令元数据，并提供带重复效果风险警告的显式 retry/cancel。启动 reconciliation 收到 Conversation Close ACK 时仍会幂等 re-arm Date Producer；Action/Letter Prompt、Memory Engine、Kinship Resolver 和 Payload `sendDay + delay` 均未修改。

## v7.10.0-RC6 Final Rev.3 Candidate：修复 6.2 验证与机械性收尾

本节覆盖 Rev.2 之后的 6.2 收尾，Terra 的核心状态机合同保持不变。

### 状态、恢复与 ACK

- Pending 只接受 `queued`、`blocked`、`awaiting_ack`、`stalled`。`failed`、`acknowledged`、`cancelled` 是终态，只进入 `recentCommands`，不会成为 FIFO 队首。
- 首次 dispatch 先持久化 `awaiting_ack`、`lastWrittenAt` 和 `writeAttempts`，再写入 `votc.txt`；因此物理写入后进程崩溃不会留下可自动重放的零历史状态。启动发现 `writeAttempts`、`lastWrittenAt` 或 `writtenAt` 任一存在但没有 ACK 的命令时，记录 `startup_ack_unconfirmed` 并进入 `STALLED`；不自动 replay，不增加写入次数，也不再次写入 `votc.txt`。
- 仅路径不可用且零写入历史时进入 `BLOCKED`。一旦已进入物理写入不确定区，即使文件 API 返回失败也保守进入 `STALLED`；BLOCKED 命令支持不产生重复 Effect 的安全重试与取消，STALLED 仍必须经过重复 Effect 风险确认后才能重试。状态文件读取或解析失败时禁止清空、恢复或新 dispatch。
- 看门狗只会对 `writeAttempts=0` 的 `queued/blocked` 命令重新尝试写入；已有写入历史的命令不会被自动重试。

### 日志与路径合同

- `run-command-recovery.js` 使用反向 1 MB 分块扫描，最多读取 64 MB，并按当前 Pending 的 `kind + commandId` 过滤 ACK。超过扫描范围的 ACK 不会触发 replay，命令按启动规则进入 STALLED。
- CK3 用户目录切换由 `refreshPathFromSettings()` 统一检查。空队列或零写入 Pending 可以从 A 切换到 B；任一命令存在写入历史时拒绝切换。设置、RunFileManager 与 ACK Tail 作为同一事务切换，Tail 重启失败时恢复 A 的设置、run 文件路径和 Tail；清空路径时同步停止 Tail。
- 删除 `Conversation.end()` 对 `cleanLogFile(debug.log)` 的调用，并移除该函数及测试注入；主进程不再写入、截断或重写 CK3 `debug.log`。日志只用于 Tail、日期扫描和 ACK 读取。

### 表层与验证

- Renderer 状态页新增 BLOCKED 面板，显示“命令尚未成功写入 CK3，因此重新尝试不会造成重复 Effect”，提供“安全重新尝试”和“取消命令并继续队列”；STALLED 面板继续显示“没有看到 ACK 不代表 CK3 没有执行。重新执行可能造成重复效果。”
- preload / IPC 增加 BLOCKED retry/cancel 表层；状态 API 继续移除 `effectText` 后再返回 Renderer。
- `scripts/test-v7.10-rc6-rev3-run-command-recovery.js` 更新 T1–T10 并新增 T11–T18：failed terminal 隔离、路径恢复、debug.log 只读、CK3 A→B 保护、旧 4 MB 窗口外 ACK、写入前 durable dispatch intent、`lastWrittenAt` 迁移、损坏状态 fail-closed 和路径/Tail 回滚均已覆盖。
- `scripts/test-manifest.js` 将该组标记为 `v7.10-rc6-rev3-run-command-recovery`。完整 `node scripts\\test-release.js` 已通过 62 个发布组；分类仍为 131 个测试文件、62 个直接发布组、68 个历史归档和 1 个统一入口。
