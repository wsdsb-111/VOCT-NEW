# V8.4 GameState Adapter 与 Index Proposal

## 1. 目标与非目标

目标是为 V8.4 后续阶段提供一个可隔离、可诊断、可回滚的 CK3 Save/GameState 读取边界。它必须支持当前已确认的未压缩文本样本，并为 ZIP、binary、split 和异常文件保留显式分支。

本提案不是实现计划的授权，不在本轮新增生产 adapter、worker、持久化 schema 或 Prompt 投影。

## 2. 推荐边界

```text
CK3SaveSource
  -> ContainerDetector
  -> Metadata/Gamestate Extractor
  -> Parser Worker
  -> CK3 Schema Adapter
  -> Normalized Snapshot
  -> Bounded Indexes
  -> Read-only Query Service
```

### Source 与 detector

`CK3SaveSource` 只负责 path、stat、header bytes、可读性和临时文件生命周期。`ContainerDetector` 输出 `PLAIN_TEXT_SAVE`、`COMPRESSED_ARCHIVE`、`BINARY_CONTAINER`、`IRONMAN_UNREADABLE` 或 `UNKNOWN`，并保留 header/version/kind/meta length。检测失败不得静默回退到“当作纯文本”。

### Extractor 与 worker

Extractor 先读 metadata，再按容器类型输出 Gamestate stream 或临时文件。完整文本 Query 和 ZIP/binary parser 建议在 worker/child process 中运行，主进程只收取 bounded result。worker 失败要返回 diagnostics，不得阻断现有对话和日志链路。

## 3. Normalized Snapshot 草案

```js
{
  source: {
    containerKind,
    gameVersion,
    saveGameVersion,
    gameDate,
    playthroughId,
    contentFingerprint,
  },
  characters: {
    byId: Map<string, CharacterSummary>,
    nameToIds: Map<string, string[]>,
  },
  titles: { byId: Map<string, TitleSummary> },
  wars: { activeById: Map<string, WarSummary> },
  diagnostics: { missingFields, parseWarnings, limits },
}
```

`CharacterSummary` 只保留历史解析和当前关系需要的字段：id、name keys、birth、gender hint、culture/faith raw ID、dynasty、family references、alive/dead date、location、domain/title references、court employer/positions 和 selected traits。不要把原始完整 record 传入 renderer 或 Prompt。

`TitleSummary` 只保留 key、holder、de facto/de jure liege、date、history、capital 和必要 laws；`WarSummary` 只承诺样本确认的 attacker、defender、start date、CB、called-to-war、battle result 和 variables。Ended war 不应凭空补字段。

## 4. Index 建议

| Index | 用途 | 样本观察 |
| --- | --- | --- |
| `characterById` | 精确 ID 查询 | 144,287 条 |
| `nameToCharacterIds` | 同名候选 | 50,502 个 normalized name key，value 必须是数组 |
| `historicalIdToCharacterIds` | 若未来 parser 发现直接 ID | 当前为 0 |
| `titleById` | holder/history/title graph 起点 | 20,504 条 |
| `titleHolderHistory` | 时间边界和继承诊断 | 8,089 条有 history 的 title |
| `realmToRuler` | 有限 realm ruler 查询 | 原型仅得到 149 条，不能视为完整王国图 |
| `warById` | active war 查询 | 107 个对象 |

索引 key 必须统一为 string。`nameToCharacterIds` 不得在重复名字时覆盖；所有推导关系要带 source path、sample date 和 confidence/status。

## 5. Cache 与身份

建议 cache key 至少组合：`playthroughId`、game date、game version、容器 kind、文件 size/mtime 和内容 hash fragment。`playthroughId` 在样本中可读，但 branch identity 只有一个样本无法确认；在 branch 合同确认前不得只用 playthrough ID 覆盖 Worldline。

cache 必须是只读 snapshot cache，不能成为人物绑定、Prompt 注入或 worldline mutation 的隐式入口。任何过期、时间倒退、fingerprint 不一致都应返回 `UNKNOWN`/diagnostic 并等待重新抽取。

## 6. 查询合同草案

```text
getSaveMetadata() -> metadata + status
getCharacter(id) -> bounded summary + source paths
findCharactersByName(name) -> candidates[] + ambiguity status
getTitleHistory(titleId, asOfDate) -> entries[] + status
getActiveWars(asOfDate) -> wars[] + status
getDiagnostics() -> parser/container/index warnings
```

接口只返回明确存在的字段；`historical_id` 未发现时返回 `NOT_FOUND`，不能用姓名、文化或现任头衔替代成“已解析”。

## 7. 进入正式实现前的 gate

- 至少一个 `UNIFIED_TEXT_ZIP`、一个 binary/split 或明确的“不支持”结果。
- 同 campaign 两个日期样本、分叉/回滚样本，完成 fingerprint 与 branch 规则。
- Save A/B checkpoint reconciliation，验证人物死亡、头衔变更、战争结束和新增人物。
- worker OOM/取消/损坏文件回归；证明 Electron main 不持有完整 raw AST。
- 对 20–30 条人工 Ground Truth 做姓名歧义、出生/性别、死亡边界和当前状态分离校准。
