
# 1. V8.14 不变量 / Non-negotiable Invariants

以下合同属于 P0，不允许在实现中弱化。

## 1.1 Owner / Campaign 隔离

所有 Memory4 数据必须至少由：

```text
campaignToken
ownerId
```

唯一限定。

禁止：

```text
Campaign A
读取
Campaign B / null / unresolved
```

除非处于明确的 Legacy unresolved 管理 UI，不得进入正式 Recall。

## 1.2 Responder-owned Memory

当前回答者为 B 时：

```text
只能读取 B-owned Memory Space
```

即使用户问的是 C：

```text
B谈C
≠
读取C自己的私人Memory
```

合法来源包括：

```text
B亲历
B直接观察
B被合法告知
B听到的传闻
B自己的Year/Life派生项
B自己的Legacy历史
```

## 1.3 Current Truth 与 Historical Memory 分离

Memory4 不负责：

```text
“世界现在是什么”
```

Current Worldline / CK3 负责当前事实。

Memory4 负责：

```text
“B曾经经历、听说、相信、承诺、记得什么”
```

不能用旧记忆覆盖当前事实，也不能把系统当前可读事实自动当作 NPC 可知事实。

## 1.4 Durable = 0 合法

一场 Conversation 必须允许：

```text
Narrative = success
Durable = NO_DURABLE_CONTENT
```

禁止把：

```text
Durable entries = []
```

解释为：

```text
摘要失败
对话不存在
双方没见过
Recent2失效
```

## 1.5 Conversation Narrative 与 Durable 独立

V8.14 继续保留：

```text
Conversation / Episode Narrative
Recent2
Legacy Summary UI
```

Durable Extraction 是另一个独立结果。

## 1.6 四层内容模型保持固定

对用户可见的长期记忆内容仍只有：

```text
Official Recollection
Detailed Durable Entry
Year Digest
Life Chronicle
```

Known Entity Index / Profile：

```text
不是第五种摘要
```

## 1.7 2+1 是上限，不是配额

每个 responder：

```text
Overview Slot ≤ 1
Detail Slot ≤ 2
```

可以：

```text
0 + 0
0 + 1
0 + 2
1 + 0
1 + 1
1 + 2
```

禁止为了“填满”而召回低相关内容。

## 1.8 Hard Gate 先于 Ranking

以下条件必须先过滤：

```text
Campaign
Owner
身份解析
知情权限
可见性
删除状态
来源版本
明确时间轴
明确日期 / 年份
```

不能靠重要性或 Topic 分数抵消。

## 1.9 Derived View 不得高于 Source

```text
Year Digest
Life Chronicle
```

都是派生视图。

它们不得：

```text
覆盖 Detail
覆盖 Official source
覆盖 Original Conversation Evidence
```

## 1.10 V8.13 Cache Boundary 不得破坏

Memory4 Dynamic Recall 必须继续位于：

```text
V8.13 Cache Boundary
```

之后。

同一 Conversation、同一 responder：

```text
Frozen Prefix text
Frozen PrefixFingerprint
Block order
Cache anchor
```

必须稳定。

# 3. 数据权威层级

V8.14 不采用一个全局简单的“谁永远高于谁”。

根据问题类型决定。

## 3.1 当前状态问题

例如：

```text
C现在在哪？
C是否活着？
C现在是什么头衔？
```

权威顺序：

```text
合法可知的 Current CK3 / Worldline
>
历史 Memory
```

## 3.2 历史 CK3 事件

例如：

```text
当年什么时候结婚？
曾经被囚禁吗？
什么时候失去头衔？
```

优先：

```text
对应时期 Official source
+
其他合法历史证据
```

## 3.3 对话承诺 / 私密动机 / 玩家交流

例如：

```text
你答应过我什么？
C当时私下告诉你什么？
```

优先：

```text
Original Conversation Evidence
↓
Canonical Detailed Entry
↓
Derived Year/Life
```

# 4. Canonical Source Contract

V8.14 必须区分：

```text
Evidence Source
Memory4 Canonical Unit
Derived View
```

## 4.1 Evidence Source

最高可追溯来源：

```text
Original Conversation / Episode
Original CK3 Official memory
Worldline source
Legacy Summary segment
```

## 4.2 Memory4 Canonical Unit

Memory4 自身的事实基本单位：

```text
Detailed Durable Entry
```

它是结构化、可索引、可编辑、可追溯的长期记忆单位。

## 4.3 Derived View

```text
Year Digest
Life Chronicle
Known Entity Index
Memory4 Index
```

均可从源数据重建。

# 7. Entry ID 合同

`entryId` 必须：

```text
稳定
可重建
不依赖 UI 排序
不依赖数组位置
```

推荐基于：

```text
campaignToken
ownerId
sourceFinalizationId
source segment/message identity
normalized memory fact key
```

生成 hash。

禁止使用：

```text
数组 index
当前时间戳单独作为主键
```

导致恢复重试产生重复 Entry。

---

# 8. 时间模型

V8.14 必须保留至少三个时间概念。

```text
conversationDate
acquiredDate
eventTime
```

## 8.1 conversationDate

该对话发生时间。

## 8.2 acquiredDate

Owner 何时第一次合法获得该信息。

通常：

```text
conversationDate == acquiredDate
```

但 Legacy / 转述 / 导入时不一定。

## 8.3 eventTime

被谈及事件实际时间。

状态：

```text
observed
reported
planned
unknown
```

禁止：

```text
planned future date
→ 写成 observed event

unknown event date
→ 默认 conversationDate
```

---

# 9. Dual Temporal Index

Memory4 Index 必须维护两条主时间轴：

```text
Event-Time Index
Conversation/Acquired-Time Index
```

用户问：

```text
1154年发生什么？
```

走：

```text
Event-Time
```

用户问：

```text
1164年我们聊过什么？
```

走：

```text
Conversation-Time
```

```json
{

  "decision": "STORE",

  "entries": [],
```

```text
NOT_PRESENT
```

与 Durable 独立。

```json
{
  "ownerId": 81358,
  "narrativeStatus": "SUCCESS",
  "summaryId": "summary_x"

```

```text
Narrative SUCCESS
```

# 12. Per-NPC Visibility Projector

V8.14 必须建立：

```text
Visibility Projector
```

而不是仅使用“整条消息在场 / 不在场”。

## 12.1 第一层：Presence

根据：

```text
join
leave
temporary leave
return
sleep
unconscious
```

筛选候选消息。

## 12.2 第二层：Fragment Visibility

同一 Message 中：

```text
公开语言
公开动作
私人心理
秘密行为
```

必须按 fragment 可见性区分。

例如：

```text
“他笑着答应，心里决定背叛。”
```

旁观者可见：

```text
笑着答应
```

不可见：

```text
心里决定背叛
```

## 12.3 不确定性合同

如果无法可靠判断某 fragment 是否可见：

```text
默认不授予旁观者
```

禁止模型猜测：

```text
“应该听见了”
```

# 13. Participant 与 Entity 分离

必须区分：

```text
participantIds
entityIds
```

场外 C 可以：

```text
entityIds += C
```

但不能因此：

```text
participantIds += C
knownBy += C
presence += C
```

# 14. Durable Admission Policy

允许进入长期记忆：

```text
RELATIONSHIP_CHANGE
COMMITMENT
DURABLE_KNOWLEDGE
MAJOR_EXPERIENCE
LONG_TERM_GOAL
EMOTIONAL_ANCHOR
```

默认拒绝：

```text
普通寒暄
重复对白
流水账动作
无长期意义玩笑
Current Truth 快照
可直接由 CK3 获取的金钱 / 地点 / 职位
```

# 15. Durable Compression Quality

建议：

```text
普通：0~4
重要：0~6
重大：≤8
```

`≤ Final Summary 20%`：

```text
只作为固定测试集的平均目标
```

禁止作为单场强制截断条件。

必须优先保留：

```text
否定
条件
承诺对象
参与人
因果
来源语气
```

# 16. Extraction Validation

模型只负责：

```text
提议 Durable Entry
```

```text
Owner
Campaign
source IDs
visibleMessageIds
时间
participants
entities
knownBy
visibility
```

```text
拒绝写入
+

```

# 17. Extraction 幂等

幂等范围：

```text
campaignToken
ownerId
sourceFinalizationId
source segment/message identity
normalized fact key
```

恢复重试不能：

```text
重复写入同一 Entry
```

同一 Finalization 中不同事件仍允许多个 Entry。




# 20. Recognition Level

运行时 Profile 可派生：

```text
DIRECT_RELATIONSHIP
DIRECT_INTERACTION
DIRECT_OBSERVATION
MENTION_ONLY
UNKNOWN
```

注意：

```text
UNKNOWN
```

> **当前没有足够确认认知的证据。**

不能渲染成：

> “我从来不认识 C。”


# 25. Profile Cache Contract

Profile 可缓存：

```text
导航数据
索引指针
Interaction counts
```

不得长期缓存：

```text
alive
current location
current title
current relationship
```

除非有明确 revision / runtime truth invalidation。

当前事实必须按需重新读取或使用可靠 revision。


# 33. Finalization Transaction

单个 Owner 的 Durable 提交流程必须：

```text
1. Resolve campaign / owner
2. Build visible transcript
3. Run extraction
4. Validate proposed entries
5. Build idempotent write plan
6. withSummaryMutation / Memory4 mutation
7. Write Canonical Detail
8. Update Index
9. Update Known Entity evidence
10. Mark Year dirty
11. Mark Life affected/dirty
12. Commit transaction
13. Invalidate dynamic recall caches
```

---

# 34. Publish Order

禁止先发布：

```text
index pointer
```

再写 Detail。

正确：

```text
Canonical Detail
↓
Index
↓
Derived dirty flags
```

如果宕机：

```text
允许重做后续阶段
```

但不得重复生成 Entry。

---

# 35. Partial Failure

如果 NPC A 成功、NPC B 失败：

```text
A 不回滚
B 单独 retry
```

禁止：

```text
重跑整场所有 NPC
```

# 98A. GPT-6 Astra / GPT-6 Sol 双模型施工治理合同

> 本节规定 V8.14 / Memory Engine 4.0 的双模型协作流程。其目标不是平均分配工作量，而是让核心实现、独立测试、独立审查和最终验收形成明确的责任分离，避免“同一模型按自己的实现假设写代码、写测试并自行验收”的闭环偏差。

# 108. V8.14 最终实施合同

> **V8.14 / Memory Engine 4.0 Implementation Contract**  
> Memory Engine 4.0 以 Campaign-scoped、responder-owned、可追溯的 Detailed Durable Entry 为长期记忆 Canonical Unit，同时保留独立 Conversation Narrative / Recent2，以保证普通对话即使没有长期事项也不会丢失近期连续性和人物认知证据。所有 Durable 事实必须来自当前 Owner 合法可见的消息或片段，并保留来源、时间轴、认知状态、置信度、知情对象和版本；模型负责提议，代码负责 Campaign、Owner、可见性、时间、来源和幂等校验。Known Entity Index 由代码基于 Episode、消息、可见性、关系和其他可核验证据维护，不以 Life/Year 是否出现人物作为“认识”判断；Relationship-aware Profile 只聚合导航和当前授权信息，不成为独立事实原本。Year Digest 与 Life Chronicle 均为可重建派生视图，任何 Detail 编辑、删除或状态变化必须传播 dirty/revision，且 Dirty 派生视图不得继续作为当前有效来源；用户手工修改 Year/Life 后进入 manual_override，自动任务不得静默覆盖。Recall Planner 先执行 Campaign、Owner、知情、来源版本、删除状态与时间轴 Hard Gate，再在合法候选之间排序；每名 responder 的动态召回最多 1 个 Overview 与 2 个 Detail，多 NPC 完全独立，多实体共用同一 2+1 总预算。Legacy Bridge 从 Memory4 Recall 启用首日即存在，并以部分覆盖映射逐事件去重，不允许一次部分迁移屏蔽整篇旧摘要。当前世界状态由经授权的 CK3/Worldline 提供，历史记忆不得覆盖当前事实，系统可读也不自动等于 NPC 可知。所有 Memory4 Dynamic 块继续位于 V8.13 Cache Boundary 之后，并继承 responder-private 动态历史、去重与缓存合同。V8.14 只有在数据一致性、Campaign 隔离、第三人/多人召回、双时间、Legacy 兼容、编辑删除、1000+ Entry 性能、Provider 成本、缓存和 CK3 实机测试全部通过后，才允许标记为 Freeze Candidate。
