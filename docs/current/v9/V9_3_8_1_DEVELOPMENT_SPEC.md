# V9.3.8.1 开发方案：多人时间召回额度与场内冻结复用

状态：原开发方案，已并入 V9.3.9。最终代码与验收状态见 [V9.3.9 实施报告](V9_3_9_IMPLEMENTATION_REPORT.md)，合并范围见 [V9.3.9 合并计划](V9_3_9_IMPLEMENTATION_PLAN.md)。下文保留本方案形成时的设计依据，不作为独立 V9.3.8.1 发布声明。

## 背景与目标

V9.3.8 已将每位回应 NPC 的固定玩家历史改为完整 Recent2、合法官方追忆和当前玩家—回应 NPC Pair 事项簿；明确历史分句可召回时间摘要和第三人摘要。现行时间与第三人上限均为 3 篇，记忆硬上限为 2／3／4+ 人的 80,000／84,000／88,000 Token。Recent2 与固定记忆首次构造后冻结。

V9.3.8.1 拟保留 Recent2、来源权限、全文完整性及单行上下文 UI 合同，调整时间摘要数量和多人记忆预算，并补足动态摘要成功召回后的冻结复用。一次成功召回的完整摘要在本场后续对话中继续供同一回应者使用，不再因每轮重新检索而失去 Prompt 前缀复用机会。

## 人数分档与额度

参与人数包含玩家。动态摘要数量是本场对话的累计唯一来源上限，跨目标共享；已经冻结的同一来源再次使用不重复占槽。

| 本场人数 | 时间摘要上限 | 第三人摘要上限 | 配置上下文比例 | 记忆硬上限 |
| --- | ---: | ---: | ---: | ---: |
| 2 人 | 5 篇 | 3 篇 | 65% | 80,000 Token |
| 3 人 | 5 篇 | 3 篇 | 70% | 84,000 Token |
| 4 人及以上 | 3 篇 | 3 篇 | 75% | 96,000 Token |

比例和硬上限是两道限制。每次请求实际可用的记忆额度取比例预算、该人数硬上限，以及扣除非记忆 Prompt、输出预留后 Provider 当前可用空间中的较小值。不得因摘要已冻结或预计可以命中服务商缓存而从本次请求的 Token 预算中扣除该摘要。

用户计划手动把模型上下文窗口从 128,000 调至 192,000 Token。程序必须读取当前有效配置，不得把 192,000 写成固定值。在 192,000 配置下，65%／70%／75% 分别为 124,800／134,400／144,000 Token，三档都会由 80,000／84,000／96,000 的人数硬上限约束；Provider 实际余量仍可能进一步降低当次预算。

## Token 估算口径

方案估算采用本轮讨论给出的常见来源规模：单篇普通 Legacy 摘要约 2,500–3,000 Token；官方追忆约 200–500 Token；事项簿只读取当前玩家与当前回应 NPC 的 Pair，通常不超过约 2,000 Token。不得把玩家与所有 NPC 的 Pair 事项簿同时加进单个回应请求。

按本轮已讨论的保守估算，双人对话现有 3+3 极端情况约 40,000 Token；将时间摘要从 3 篇增至 5 篇，新增两篇约 5,000–6,000 Token，约为 45,000–46,000 Token，仍明显低于 80,000 Token。该数值是设计估算，不替代最终 Prompt 的实际分词和 Provider 余量检查。

此前给出的六人表达式 (2,500 + 500 + 2,000) × 6 + 6 × 2,500，按算术结果是 45,000 Token，而不是 34,200 Token；即便把它作为跨回应者的保守合计，也低于 4+ 人的 96,000 Token 记忆上限。实际单次 Provider 请求只装入当前回应者有权读取的玩家 Pair 基线和本请求授权的冻结摘要，不应将其他回应者的 Pair 事项簿重复累加进该请求。

这些来源尺寸是容量规划输入。运行时仍须按完整 Prompt 和当前 Provider headroom 计算；摘要全文不得静默截短或省略。若完整来源超预算，先压缩较旧对话，仍无法容纳时在 transport 前暂停并说明所需、可用及分项预算。

## Recent2 与固定玩家记忆

Recent2、合法官方追忆和当前回应者对应的玩家 Pair 事项簿构成本场固定基线。按本场开始时的来源状态为每个回应者建立快照并冻结；后续轮次不重读 Recent2 或 Pair 文件，也不随其他 NPC 的发言扩展该回应者的固定玩家历史。来源全文、来源键、修订号、Campaign 和 Forget 状态须与该快照一同追踪。

固定基线仍只锚定当前玩家。第三人 L0 仅可提名，不得借此读取其历史索引或摘要原文；合法的明确历史关系询问仍按既有 L1 权限和每目标 16 条事项上限处理；具体历史经过才可进入动态摘要召回。不得新增模型检索／提取请求，也不得恢复 Durable、Year/Life 自动生成、恢复或后台重建。

## 动态摘要召回成功后的本场冻结

动态召回必须从“逐轮临时结果”改为“本场可复用的冻结快照”，执行以下规则：

1. 只在授权查询找到完整摘要、摘要全文实际进入该回应者的 Provider 请求，且该请求成功完成后，才把来源提交到冻结集合。取消、失败、未注入或未完成来源复验的结果不冻结，也不占用成功召回配额。
2. 冻结记录保存本场 ID、回应者 ID、Owner、Campaign、类别（时间／第三人）、来源键、revision、原始完整摘要文本及原时间轴／来源信息。相同来源键和 revision 在本场只计一个唯一名额。
3. 冻结完成后，该回应者后续请求直接复用已保存的全文，不重新扫描候选、重选排名或重复读取同一摘要。新历史分句仍可查找尚未冻结的新来源，但只在本场相应类别还有空位时加入；时间与第三人额度按上表跨目标、跨本场累计。达到上限后，不静默驱逐旧快照或替换来源，并通过诊断／状态说明额度已满。
4. 对话级计数器只负责执行全场唯一来源配额，不授予跨回应者的记忆读取权限。冻结文本仍按回应者及其 Owner／Campaign 来源权限隔离；一个回应者已召回的私有来源不得仅因共享计数器而传给另一回应者。另一回应者只有在自己的来源授权复验通过后才可使用对应全文。
5. 每次发送前仍按来源键、revision、Owner、Campaign 和 Forget 状态复验。若来源已编辑、删除、遗忘或失去战役绑定，必须使相关冻结项失效并阻止旧文本再次进入 Prompt；不得把失效快照当成有效缓存。
6. 游戏时间在本场静止，不意味着可以每轮动态重算。冻结使用本场首次成功召回时的完整文本与时间信息；后续不因轮次变化而改写“本轮”等易变措辞。Prompt 标签应使用稳定表述（例如“本场已核验历史摘要”），并保留摘要自身的日期和来源。

失败 Provider 请求即便曾包含候选摘要，也不得提交成功冻结状态。已成功冻结的摘要在后续轮次中继续占用每个相关 Prompt 的上下文 Token；冻结节省的是重复检索并保持内容稳定，不会让摘要脱离 128K／192K 窗口预算。

## Prompt 前缀与缓存复用

动态摘要首次成功注入后，应进入该回应者的稳定冻结 Prompt 前缀，位于可变对话历史和当前用户发言之前；后续请求保持该块 ID、顺序、包装文本及摘要全文字节稳定。新增其他冻结摘要时，只按稳定来源顺序扩展冻结块。Recent2、官方追忆、Pair 事项簿和动态冻结摘要都应处于相同的稳定前缀生命周期管理中。

当前 PromptBuilder 将 memory-temporal-extra 标为不稳定块并置于可变对话之后，因此现状不能保证动态摘要进入可复用的稳定前缀。V9.3.8.1 需调整这一布局及对话状态提交时机：首次召回请求携带同一冻结块格式，成功后记录快照；后续轮次从快照重建完全相同的前缀，不再重新召回该来源。

应用侧可以保证快照复用和稳定前缀条件，不可以宣称每次都发生 Provider 缓存命中。服务商是否命中还受其缓存 TTL、最小前缀长度、路由和原生缓存策略影响；必须单独记录原生 cached-token 用量。即使 Provider 命中，摘要仍属于该请求的输入上下文。

## 玩家上下文用量提示

沿用 V9.3.8 的单行低干扰 UI：只显示玩家当前本场对话的上下文窗口，不生成逐 NPC 窗口、不把多个回应者的请求相加。不同场次和回应者的后端上下文状态保持隔离，新场次从自身请求开始统计。

显示容量应随当前模型／Provider 配置变化。生成中标记临时估算；请求结束后优先显示该请求的原生 input/output usage，缺少字段时明确标作估算。remaining 是由配置容量减去当前请求用量得到的本场请求快照，不是服务商账户余额。UI 与记忆阻断均应使用同一实际配置来源，不得为展示 192,000 而硬编码。

## 预期改动范围

实施时先读对应目录的 AGENTS.md，再以最小范围调整记忆预算策略、时间摘要筛选及诊断上限、对话级召回状态／成功提交和失效处理、PromptBuilder 稳定前缀布局，以及针对这些合同的发布回归。README、文档索引和 CHANGELOG 只在真实实施及验证状态明确后更新；本方案本身不修改 Runtime、设置默认值、摘要存储格式或 Provider 协议。

## 验收标准

- 2 人为 5 时间 + 3 第三人、80,000 Token；3 人为 5 + 3、84,000 Token；4+ 人为 3 + 3、96,000 Token。百分比、Provider headroom 和非记忆 Prompt／输出预留仍参与每次预算计算。
- 时间和第三人额度跨本场目标与轮次累计；同一来源 revision 再次复用不重复计数，新来源按类别占用空位。
- 只有来源全文真正注入且 Provider 请求成功后才冻结；失败、取消、漏注入的候选不会进入冻结快照。
- 成功冻结项在同回应者的后续轮次复用完整文本，不重复召回；本场新话题允许在未满额度时召回新来源。
- 4+ 人的共享额度不会把任一 NPC 的私有来源带入其他回应者 Prompt；不同对话场次之间不继承冻结项。
- 稳定前缀位置、块 ID、顺序和文本经重复构造一致；当前用户新发言不会改变既有冻结前缀。首次增加新冻结摘要后，后续请求具备相同前缀复用条件。
- 来源 revision、Campaign 或 Forget 发生变化时，旧快照被拒绝且不得重放；L0 仍不读取第三人原文。
- 超预算时先压缩较旧对话；完整来源仍装不下则 transport 前暂停并显示预算分项，任何来源都不静默裁剪。
- UI 仅显示玩家本场一行；配置窗口改变后容量随之变化，估算和 Provider 原生用量语义清楚。
- 自动发布回归与部署验证通过后，再分别记录真实 CK3、游戏内 Provider 原生 usage／缓存数据、Soak 和远端 CI。任何未执行的外部 Gate 均保持 NOT_RUN／PENDING，不宣称 Full Freeze。
