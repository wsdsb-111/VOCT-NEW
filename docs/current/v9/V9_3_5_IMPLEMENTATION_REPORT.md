## 实施结果

历史叙事记忆仍由 Legacy 摘要提供。新增本地有向事项索引及准确来源回查：Recent1 → 当前关系相关事项 → 必要时 1–2 篇源摘要；索引缺失、无命中或不可验证时继续使用原 Legacy 全文、时间和人物召回。Durable、Year／Life、Memory4 恢复与旧 Sidecar 没有重新接入生产链。

本地索引、回填和检索不调用 Provider。本轮没有调用付费 API，没有读取或修改真实用户 APPDATA，没有运行真实 CK3。自动化、原生窗口、远端 CI 与实机证据分别见[验证报告](V9_3_5_VERIFICATION_REPORT.md)。

## Phase 0–2：来源、解析与两级检索

- `src/app/shared/pair-important-matters.js` 是主进程和 UI 共用的确定性解析器，只复制 `【需要长期记住的事项】` 中的条目，保留条件、否定和续行；无标题不从叙事中推测事实，歧义段落须确认。
- `pair-long-term-ledger.js` 从已提交、已授权的 Owner→Counterpart Legacy 投影派生索引。按 Campaign、Owner、Counterpart 分文件，原子写入、可重建、不改原摘要。来源身份和正文修订分开；同日多场会话、同文本不同 Owner 不能混用。
- `MemoryStore` 保留每个合法定向投影的来源元数据，不因摘要归并而丢失方向。读取时检查现有源文件状态及内容摘要；等长修改且时间戳不变也能撤销旧索引。仅检查已知、已授权的 Pair 源文件，不扫描旧 Sidecar。
- `pair-memory-source-retrieval.js` 用本地中文 n-gram、英文词项和日期检索事项；最多选 12 项、4 个候选源、实际注入最多 2 篇经键／修订校验的源摘要。同源多事项只展开一次，Recent1 和其他召回去重。最终再验来源版本，变动则丢弃该包并保留 Legacy 兜底。
- 强来源命中且没有独立时间／场外人物查询时，不再额外执行 Legacy 全文排名；其余情况保留旧回退。检索性能没有预设必须更快，合成对照如实记录。

## Phase 3：摘要 UI 与回填

真实 Renderer 入口增加独立 Pair UI 模块及共用解析器，没有假设不存在的 TSX 工程。人物主标签显示真实姓名；未取得姓名时显示“姓名未载入”，ID／哈希只在折叠诊断中出现。

摘要页提供“自动提取长期事项”、预览／确认、单 Pair 和 Owner 批量回填、取消与逐 Pair 进度。后端对整个索引搜索、日期过滤、排序和分页，单页默认 20、上限 50；不是只筛当前页。组合关键词须全部命中，中文旁数字独立分词，数字 41 不会匹配 141；列表过滤与聊天模糊相关性排名分别处理。批量逐 Pair 原子提交，取消发生在 Pair 之间，成功部分保留并可幂等续做。损坏来源、陈旧预览和不可写 Campaign 有明确错误。

点击事项先调用受限 IPC 重新核验 Source Key／Revision，再展示原文并定位真实摘要。过期源拒绝打开，不信任客户端路径、日期或旧行号。离线唯一绑定 Campaign 仅可只读浏览和预览，不能回填。

## Phase 4：Recent1、NPC 方向和预算

正常 v3 路由每个直接 Counterpart 的冻结基线为最近 1 篇 Legacy；合法官方摘要仍有独立槽位。最近一次合法发言者和结构化收件人决定回应关系，忽略空流式占位，不默认把玩家置顶；证据不足保守选择在场对象。Direct／Group Witnessed／Undetermined 明确区分。

切换交谈对象保留已冻结前缀，在动态部分提供当前 Pair 的 Recent1 与相关事项；不会因 seen 集合永久压掉当前关系。新增内容版本为 9.3.5，既有 Prompt block ID 保持。无事项的旧摘要仍能按全文意图召回，尾部约定保留在动态 Extra。

Temporal 和 Mentioned／Entity 各自最多 3 篇，合并去重后最多 6 篇；Pair 源摘要最多 2 篇也共享同一预算，并非叠加无界额度。会话首次生成冻结：2 人为上下文 10%／3600 Token，3 人为 12.5%／4500，4 人以上为 15%／5400，取较小值且保留 Provider 安全余量。预算计算包含最终标题、日期和诊断文案；不足时沿既有截断策略缩短或省略，不能承诺每轮所有全文均完整注入。

## 用户补充：中途入场角色的重要事项

根因位于最终摘要的可见性修复：原逻辑在重建叙事时清空 memories，或因修复一个叙事范围而删除与该范围相交的所有事项，连角色入场后合法可见的事项也会丢失。

`finalization-visibility.js` 现在逐条验证事项的消息／片段来源、知情集合与在场窗口；合法的入场后公开事项保留，耳语、缺席期间和跨离场／回场边界的混合来源仍拒绝。重建叙事不再无条件清空已经验证的事项。`perspective-projector.js` 为新定向投影明确输出 `【需要长期记住的事项】`，没有合格事项时标注“无”。

同一次 Final Summary 提示要求覆盖每个有实质内容的在场时段，包含迟到与回场后的重要约定、未完成事项等，不再以全场最多 10 条挤掉后入场者。没有增加二次模型提取或改变 Provider 输出安全上限。独立反例覆盖合法迟到事项、耳语、混合可见性、缺席、回场及跨会话重复 messageId。

这解决了确定性的丢弃问题，不能保证模型每次一定生成高质量事项。过去已经落盘、没有事项段落的摘要不会被本地解析器凭空补写；它们仍走 Legacy 全文兜底，可用现有摘要编辑／整理流程修订。回填不会偷偷再发模型。

## Phase 5：信件 Legacy 归档

旧流程可能把“归档受理”或一个方向已保存当作双方完成。现在必须从实际 Sender 与 Recipient 各自的 Legacy 文件核验 Campaign、方向、Letter／Finalization／Projection 标识、日期和正文修订，才能记为 COMPLETE。源修订证明随任务保存；旧任务缺字段仅在精确旧 Letter marker 证明成立时兼容，否则阻止自动恢复。

`letter-manager.js` 分开报告物理投递状态、摘要归档状态及方向性错误。崩溃恢复只补缺少的合法摘要，已保存的模型结果复用，不重发 CK3 信件、弹窗或宝物效果。Forget 后恢复转为 MANUAL_BLOCKED，不复活摘要。旧 Memory4 Recovery 不扫描、不自动转换；此类历史记录须将来显式备份、预览后维护处理，本版不绕开退役边界。

专项还发现 Letter 只读 Prompt 的 scoped Store 继承了指向原 Store 的 Pair ledger，可能改变原缓存；现已为 scoped Store 配置独立 ledger／缓存，通过原有只读测试。
