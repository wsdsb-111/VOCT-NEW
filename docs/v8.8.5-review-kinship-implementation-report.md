# V8.8.5 审查问题与扩展亲属改进报告

日期：2026-09-13。状态：代码与自动化回归通过，用户已确认关系提取与动作执行的 CK3 实机链路恢复；扩展亲属矩阵、全 Provider Token 实测与长时 Gate 尚待完成，不宣布 Full Freeze。

## 修复内容

1. **排队与确认计时分离**：`conversation/conversation.js` 不再从确认函数启动时计算后排 Action 的 12 秒 ACK 超时，也不再取消尚未写入的合法排队命令。`actions/run-file-manager.js` 持有 120 秒未写入 TTL，定期清理已到期排队动作；确认计时依据 `lastWrittenAt/writtenAt`。已写入但未 ACK 的命令不可因此过期或自动重放，游戏侧去重与旧会话隔离保留。
2. **金币金额保护收窄**：`actions/action-confirmation.js` 只在用户文本中存在唯一数字候选、明确支付动词且无检测到的否定/改口时返回确定性金额。多个数字（包括改为中文数字、多人支付）或检测到否定/改口时不覆盖，保留经过既有门禁和本地校验的 Action 模型参数。本版选择“交回模型”，不是宣称能确定性理解所有自然语言；多数字中包含日期等也会保守放弃覆盖。
3. **好感度不再提前宣称成功**：标准 `z_changeOpinionOf.js` 九种语言的 `message` 均改为请求/等待确认，旧成功文案移入 `confirmedMessage`，仅 `CONFIRMED` 使用。签名、参数及 CK3 Effect 不变，只有 ACK/无效果/不一致/超时均不得显示为已改善。
4. **年龄空值不等于新生儿**：共享年龄服务拒绝 null、undefined、空白、布尔值、负数和非数字；真实 0 岁保留。同步修复角色解析、亲属出生天数解析、关系 Profile 构建中的先行空值转零路径。已故人物不使用当前年龄冒充死亡年龄。
5. **动作载体与阻塞恢复**：实机日志显示连续 39 个 Action 正常 ACK 后，紧接前一 ACK 写入的一条命令无 BEGIN/ACK，随后旧 STALLED 队首令所有动作返回 `action_queue_blocked`。`votc.txt` 现以同目录临时文件完整写入 UTF-8 BOM 后原子替换，避免 CK3 的 0.4 秒轮询读到半写文件并提前设置去重标记；当玩家发起新动作时，只在旧 STALLED 载体已经成功清空后将其作为未知结果隔离并推进队列，保留证据且绝不重放。
6. **Provider Action 配置**：DeepSeek 的 State Transition Recall Overlay 与 Stable Prefix A/B 对新配置和缺失旧字段均默认开启，显式关闭仍保留。OpenAI-compatible 新增同一 Action Schema 传输选择：标准模式发送 `response_format.json_schema`，兼容模式发送 `json_object` 并继续使用本地官方 Schema 校验；聊天与摘要请求不受影响。
7. **跨 Provider Token 统计**：OpenRouter、OpenAI-compatible、Player2 与 DeepSeek 的流式解析现在会保留 `choices: []` 的末尾 usage-only 数据块；Gemini 的 `usageMetadata` 统一映射到标准输入/输出/总 Token 字段。若兼容端点完全不返回 usage，则按实际发送 Prompt 与最终回复生成明确标记为 estimated 的统计，并纳入服务商 Token 汇总，避免请求已完成但面板仍显示 0。
8. **智谱 GLM 官方 Provider**：新增独立 `zhipu` 服务商，不借用 OpenAI-compatible 预设。默认大陆官方端点 `https://open.bigmodel.cn/api/paas/v4`、`glm-5.3-flash`、90,000 上下文、`reasoning_effort=low` 与 `thinking={ type: "enabled", clear_thinking: true }`；配置损坏时推理强度仍 fail-safe 为 `low`。GLM 的 `cached_tokens` 映射到统一缓存字段，`reasoning_tokens` 与可见输出 Token 同时保留；流式末尾 usage 和非流式 usage 走同一归一化。DeepSeek Overlay、Stable Prefix 与 Schema 传输特例保持仅属于 DeepSeek / OpenAI-compatible，不会继承给 GLM。

## 扩展亲属设计

- `character-kinship-graph.js` 补入已读取的直接兄弟姐妹边；父母数组通过父母当前性别确定父系/母系，不依赖数组位置。
- 父亲的兄弟子女属于堂亲；父亲的姐妹子女以及母亲的兄弟姐妹子女属于表亲。父母分支或关键性别缺失时使用“堂表亲”，不猜测。反向关系从其自己的父母分支推导，不能机械复制。
- `compareCharacterSeniority` 优先比较出生天数、其次出生日期，最后才使用同一当前数据中的非空年龄。相同生日/同龄、出生证据冲突或只有死亡年龄时不强分长幼。
- 堂表兄姐弟妹比较目标与关系主体；伯父/叔父比较目标与主体的父亲，不能与主体年龄比较。姑母、舅父、姨母和父系/母系祖父母按实际家谱路径与性别确定。
- `relation-intent-parser.js` 与 `anchored-relation-resolver.js` 增加对应查询，按分支、性别、长幼筛选；缺失信息和多候选保持未解析/歧义状态。
- `relationship-current-truth.js` 继续以 canonical Runtime 性别为准，关系侧未知或冲突不升级为确定事实。缓存指纹补入原始年龄和出生日期，避免年龄数据更新后仍显示旧称谓。

## 英文模板兼容与边界

- `prompts/prompt-script-sandbox.js` 在已知 `pListMccTest2.js` / `pListMccTest2JE.js` 英文执行入口接入 `legacy-family-presentation.js`；默认英文文件也声明对应入口。既有旧英文文件无需被覆盖，年龄字段同样通过共享服务展示 unknown/去世年龄。
- 输出亲属姓名、Runtime ID、英文关系及精确中文称谓、性别、年龄、生死信息和推导中间人物 ID，保留可用婚姻状态/traits/死亡信息。原简易 kinship reference 被共享结果替代，避免重复注入互相矛盾的称谓。
- 每人至多 32 条、每次模板执行总计至多 96 条；明确标注截断，未列出不等于不存在。不会扩充 `gameData.characters`，不会将亲属变成发言人或 Action 目标。
- **数据边界**：只推导当前输入中实际存在的 CK3 家谱和人物资料，不自动加载整个宫廷，也不从旧摘要/历史定义补猜缺失父母和叔伯祖辈。如果旧日志只提供本人及直系亲属，扩展家谱不足时仍无法凭空输出具体叔伯/堂亲。
- Prompt 稳定 cache anchor、块 ID/顺序、Memory Engine 2.6 标签及 2.5 存储、IPC、主题、Electron 包版本均保持不变；变化位于人物描述的动态内容。
- 标准 Action 在应用重启/重新加载动作时沿既有 `ActionRegistry.seedDefaults()` 同步；本次不改用户模板文件和运行中的会话/队列，不自动关闭用户程序。
