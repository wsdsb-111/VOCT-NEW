## `character_lookup` 的性质

样本的 lookup 是独立 section，形式上表现为 `definitionKey = runtimeId`。例如：

```text
tangyin_yue_014 = 96895
nansong_yue_085 = 96896
```

## 全 Gamestate 数字反向搜索

对样本存档做了原始文本反向搜索并保留上下文分类：

- `96895`、`96896` 同时出现在 `character_lookup` 与人物记录区，并可能出现在 pinned/关系引用中；最可靠的历史关系仍然是 lookup 条目，而不是普通数字出现位置。
- `140239` 出现在 Character 记录、title holder/history、dynasty/house head、claim、court employer、artifact identity 和 pinned character 等多个顶层对象/字段中；这证明它是一个活跃 Runtime ID，但不能从这些引用反推出历史 Definition ID。
- `Yuefei_name` 出现在至少四条人物记录中，且性别、出生、文化、信仰不同；姓名 localization key 只能作为候选召回条件。

## Character 完整字段边界

本轮查询的运行时 Character 对象可读到 `first_name`、`birth`、`female`、`culture`、`faith`、`dynasty_house`、`family_data`、`alive_data`、`court_data`、`landed_data`、`dead_data`、`traits` 等字段。目标字段 `historical_id`、`historicalId`、`historical_character_id` 在第一轮全量人物记录审计中均未出现。

因此后续 adapter 应将：

1. Runtime ID 与完整 Character snapshot 分开存储；
2. Definition ID 作为可选绑定证据存储；
3. `NOT_FOUND`/`AMBIGUOUS` 保留候选和证据，不降级成伪造的历史 ID。
