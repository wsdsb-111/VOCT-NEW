# V8.4 GameState 性能勘探基准

## 1. 测试口径

以下是指定 `autosave_1.ck3` 的单次本地运行结果，Node 使用 `--max-old-space-size=4096`。机器、操作系统文件缓存和磁盘状态会影响时间；这些数字是能力勘探，不是发布 SLA。

`targetedParse` 使用 Jomini Query 对日期、角色、标题、战争等指定路径查询，并没有把整个 229 MB 文本 materialize 成一个生产对象。`tempGamestateParse` 只验证临时 Gamestate 的 parser 入口和日期读取，不等于完整语义解析。

## 2. 结果

| 阶段 | 结果 |
| --- | ---: |
| full file read | 57.85 ms / 229,445,646 bytes |
| uncompressed body direct stream | 177.33 ms / 229,407,347 bytes |
| temp Gamestate extract | 128.82 ms / 229,407,347 bytes |
| temp Gamestate parse（日期入口） | 334.95 ms |
| incremental top-level scanner | 2,654.91 ms |
| targeted semantic Query | 5,186.99 ms |
| compact index build | 772.53 ms |
| exploration total | 10,689.58 ms |
| parse checkpoint RSS / heap | 2,119 / 530 MiB |
| index checkpoint RSS / heap | 2,155 / 595 MiB |

临时抽取文件只在测试期间存在并在结束时删除。RSS/heap 是进程检查点，不是操作系统级 peak；本轮没有执行“完整 AST 保留后再释放”的生产模型，因此不能把 2.15 GiB 当成最终实现的精确峰值。

## 3. 解释

1. 纯读文件很快，但语义 Query 和索引构建的主要成本来自文本解析、对象 materialization 和索引复制。
2. 顶层 scanner 可以在不构造完整对象的情况下发现 section occurrence，当前能力为 `PARTIAL`，不能回答任意深层路径。
3. 观察到的内存量足以支持把完整解析放进 worker/child process，隔离 Electron main process 的延迟和 OOM 风险；本轮只形成建议，没有施工。
4. 不能用这次未压缩样本推断 `UNIFIED_TEXT_ZIP`、binary 或 split save 的时间。正式 benchmark 至少需要每种容器一个样本、冷/热缓存各一次和失败路径一次。

## 4. 索引原型尺寸

| 原型 | 条目 | JSON 序列化尺寸 |
| --- | ---: | ---: |
| `characterById` | 144,287 | 30,164,502 bytes |
| normalized records | 144,287 | 28,882,036 bytes |
| `titleById` | 20,504 | 5,833,785 bytes |
| `warById` | 107 | 38,670 bytes |
| `historicalIdToCharacterIds` | 0 | — |

这说明“把完整 Character record 放入常驻 renderer/main 内存”不是合适的默认方案。建议由 worker 生成受限的 normalized index，并按查询类型返回小结果；正式实现还需测量 raw object 释放后的常驻内存和并发访问。

## 5. 复现入口

一次性工具为 `scripts/explore-v8.4-gamestate.js`。它要求显式传入 save、Jomini entry 和输出 JSON 路径，默认不写仓库、不写用户数据。该工具不是发布 gate，也不是正式 V8.4 parser。
