# V8.15.2 信件投递后记忆归档热修（2026-10-08）

## 问题与证据

用户已实机确认上一轮日期链路恢复，信件宝物及完整回信正文正常；随后发现没有摘要和人物目录。本轮只修复投递确认到记忆归档的交接，不再次更换日期生产者。

只读待处理记录中，用户指定的信件仍停在 `effect_file_written / not_started`，而对应 RunFile 命令已有 ACK 并移入历史。结合用户宝物截图，可以确认该封信的游戏投递成功、归档没有完成持久化。保留日志中未找到对应接受回调记录；日志可能轮转，不能据此证明回调从未执行。

生产链存在两个缺口：接受入口依赖弹窗 widget 的剪贴板 `LETTER_ACCEPTED`；即使该回调到达，旧归档还要求重新解析当前日志得到原信件、原收件人及已到期日期。原发信快照停留在发送日，或者后来已进入另一场对话，都会使这项验证失败。普通命令 ACK 本身不足以证明信件宝物成功创建，不能直接绕开归档门禁。

## 最小修复

- `resources/app/out/main/letters/letter-manager.js` 在生成回复时保存双方姓名和双方关系的来源快照；不保存全角色私密资料，也不扩大收件人的召回权限。
- 正式宝物 Effect 写入前，持久化每封信的随机回执 token。官方 journal/scroll、正文、制造者、全局变量和消息事件保持原样；创建后的 scope 存在才写 `VOTC:LETTER_RECEIPT`，携带实际战役、玩家、收件人、游戏日和日历日期，不携带信件正文。
- App 同时核验信件 ID、token、Campaign、双方 ID、来源日期和到期游戏日。裸剪贴板通知、普通 ACK、错战役、错人物和未到期回执均不能启动新信归档。接受处理串行化，重复旧回执不能错误消费下一封信。
- 验证通过后，先持久化接受证据，再使用冻结来源接入既有 `LetterMemoryFinalization`。摘要写入双方有向目录，逐 Owner 构建 Detail，再沿既有任务生成 Year/Life。当前日志已换人物不会阻塞归档；回信披露仍仅在当前人物和日期能够真实核对时执行，不从旧快照授权当前特质。
- 已捕获的恢复任务沿既有幂等阶段重试；摘要失败不再写游戏 Effect，不重新生成回信或宝物。不改变 Memory Engine 4.0 标签、3.0 协议、2.5 存储、IPC、Prompt Block IDs、Cache Anchor 或 Provider 配置。

本轮不修改 Workshop 或官方 2.0.3 App。回执属于 App 动态生成的 RunFile，使用现有日志读取器和游戏侧机制；上一轮 App/Mod 方案 B 依赖继续有效。

只读复核：该信为 `sent / not_started`，恢复任务 `LETTER_MEMORY_FINALIZATION` 的 Narrative 仍为 `PENDING`，尝试次数 0。这是待生成任务，不是已生成摘要或已建成人物目录。重新启动 App 后由既有任务链生成；模型生成失败可通过失败摘要恢复入口重试，不需要重新寄信。

补建工具 `scripts/repair-confirmed-letter-memory.js` 要求明确实机确认、应用停止、准确来源绑定、已写 Effect 和到期证明。已有来源快照必须精确匹配；历史无快照的信件仅接受人工核实的双方姓名，不臆造关系。独占随机临时文件、原记录备份及替换前复核用于保留原数据。维护期间不得同时启动 App 或其他写入进程；停机检查不是跨进程事务锁。
