# VOTC v6.5 动作系统工作流程总结

> 状态：已实施并完成静态回归验证  
> 适用范围：`resources/app/out/main/main.js`、`resources/app/default_userdata/actions/standard/` 与动作回归脚本  
> 说明：本文描述当前 v6.5 的生产流程。`VOCT_v6.5_动作系统重构设计_测试反馈修订版.md`、Phase 0/0.5/0.6 报告记录的是重构设计和当时的基线问题；如与本文冲突，应以当前代码和实际测试结果为准。

## 1. 重构目标与结果

v6.5 将旧的“整条消息 → category/脚本列表 → 动作模型”路径拆成可验证的事件流程，解决了以下问题：

- 不再让否定、假设、计划、回忆或传闻污染真正发生的动作。
- 同一条消息可保留多个动作事件，并按原文位置执行。
- 同类别的不同事件不会因 category 相同而被合并。
- 玩家消息与 NPC 回复分别评估，不再通过 `pendingPlayerActionMessage ?? placeholder` 二选一。
- 动作的类别、证据模式、互斥组、优先级与风险等级下沉到 Action Script metadata。
- 动作模型只在已验证事件的证据范围内选择角色、目标和参数，不能把事件提升为另一种游戏效果。

## 2. 生产工作流程

```text
玩家消息 + 当前 NPC 回复
        │
        ▼
buildTurnEvaluationPlan()
  ├─ 玩家消息：以玩家为动作来源
  └─ NPC 回复：以该 NPC 为动作来源
        │
        ▼
getActionTriggers()                 （低成本候选召回）
        │
        ▼
parseActionEvents()                 （唯一的执行事实来源）
  ├─ ActionEvent[]                  （真实已执行事件）
  └─ rejectedCandidates[]           （假设/回忆/失败尝试等）
        │
        ▼
resolveMetadataSemanticCandidates() （仅匹配 Positive Evidence）
        │
        ▼
事件级 allowlist + 去重
        │
        ▼
Action LLM                           （仅解析 actor / target / args）
        │
        ▼
本地 Schema 校验 → check() → 批准策略 → run() → CK3 Effect
        │
        ▼
动作结果、跳过原因和缓存分块写入 usage analytics
```

### 2.1 候选召回：`getActionTriggers()`

候选层只判断文本是否值得进入进一步动作分析，不再证明动作已经发生。它覆盖金币、拘押、伤害/死亡、关系、职位、封臣、地点、战斗、日常互动、亲密行为、派系、囚犯处置、计谋等类别，并保留较高召回率。

例如“我现在把 50 金币交给你”支持“金额/货币 → 转移动词”的自然语序，可唤醒 `gold`；但金额、支付方向和是否真正执行仍由后续层决定。

### 2.2 执行事件：`parseActionEvents()`

事件解析器将文本按子句与连接词拆分，为每个真实事件生成：

```js
{
  eventId: "evt_1",
  category: "death_or_injury",
  evidence: { text, start, end },
  executionStatus: "executed",
  resultStatus: "succeeded" | "failed",
  sourceClauseIndex
}
```

以下内容不会进入 `ActionEvent[]`，而是保留在 `rejectedCandidates[]` 供诊断：

- 假设、传闻、回忆/转述；
- 执行前失败，例如“试图拔剑，但剑卡在剑鞘里”；
- 不构成当前执行事实的候选。

“挥剑刺向他，但他躲开了”则保留战斗事件：`executionStatus = "executed"`、`resultStatus = "failed"`。因此可以记录战斗，而不会派生出受伤或死亡效果。

事件按 `evidence.start` 排序；去重键包含事件 ID、发言者和证据 span，所以“先刺伤第一个卫兵、再刺伤第二个卫兵”可保留两个独立伤害事件。

### 2.3 语义解析与 metadata

所有标准动作均声明 `triggerCategories` 与 `semantic` metadata。注册表加载时验证 metadata 结构：

```js
semantic: {
  evidencePatterns: [/* RegExp */],
  excludePatterns: [/* RegExp，可选 */],
  exclusiveGroup: "physical_outcome", // 可选
  priority: 100,                       // 可选
  riskLevel: "low" | "medium" | "high"
}
```

`resolveMetadataSemanticCandidates(event)` 只读取 `event.evidence.text`。候选需同时满足类别与证据匹配；同一 `exclusiveGroup` 中只保留优先级更高且**已经匹配证据**的动作。优先级不能让没有死亡证据的 `characterIsKilled` 覆盖“刺伤”的 `isInjured`。

少数需要依赖发言者方向或复杂组合语义的动作保留兼容解析标记 `requiresLegacyResolution`；无动作回退使用 `fallback` 标记。这是有意保留的渐进式兼容边界，而不是重新允许读取完整原文。

### 2.4 玩家与 NPC 的独立评估

`Conversation.evaluateCompletedActions()` 先取得待处理的玩家消息，再构建独立评估计划：

1. 玩家消息以玩家角色为动作来源评估；
2. 当前 NPC 回复以该 NPC 为动作来源评估；
3. 两条消息的结果分别关联各自消息 ID 并进入审批/执行处理。

因此，玩家给金币与 NPC 随后战斗、玩家无动作而 NPC 离开、玩家战斗与 NPC 日常动作等组合不会相互替代。

### 2.5 动作模型、审批与执行

每个事件单独调用选择流程。动作提示词会附带事件 ID、类别、执行/结果状态、证据 span，以及仅包含 Positive Evidence 的候选文本。模型只可从该事件的语义 allowlist 与本地 `check()` 允许的动作中选择，并负责解析目标和参数。

随后仍由本地逻辑执行：结构化输出校验、目标/参数校验、`check()`、危险动作审批策略、`run()` 与 CK3 原生前置条件。高风险动作保持 fail-closed：例如未指定凶手时 `characterIsKilled` 返回失败，不写入死亡效果。

## 3. 标准 Action metadata 迁移

迁移范围为 `resources/app/default_userdata/actions/standard/` 的 36 个 shipped Action Scripts。每个脚本均已具备类别与风险说明；典型互斥组包括：

| 业务场景 | 事件类别 | metadata 结果 |
|---|---|---|
| 死亡与受伤 | `death_or_injury` | `physical_outcome` 中按匹配和 priority 区分死亡、受伤 |
| 关系变化 | `relationship` / `intimate_contact` | 依据证据选择朋友、挚友、恋人、灵魂伴侣、仇敌等 |
| 职位与雇佣 | `employment_or_office` | 区分任命、骑士、议会、宫廷职位与罢免 |
| 地点与离开 | `location_or_exit` | 区分 `changeLocation` 与 `leavesConversation` |
| 计谋 | `scheme_start` | 区分个人计谋与敌对计谋 |
| 金币 | `gold` | 保留发言者方向兼容解析，避免付款方/收款方颠倒 |

## 4. 外挂程序中的动作显示（v2.0.4）

动作设置页在 v2.0.4 中读取 registry 的安全摘要，并在每个动作下显示：

- 风险等级：低 / 中 / 高；
- 解析方式：事件解析、方向兼容解析或无动作回退；
- 触发类别。

原有的启用开关、危险动作审批图标、重新加载、打开脚本文件和筛选功能均保持不变。界面不会显示正则表达式或实际对话证据。

## 6. 修改新动作的最小流程

1. 在 Action Script 中声明 `triggerCategories`、`semantic.riskLevel`，并在适用时补充证据模式、互斥组和优先级。
2. 保持 `args`、`check()`、`run()` 的现有 API；高风险效果必须在 `run()` 中缺少目标或前置条件时安全失败。
3. 为真实叙述、问句/未来式、失败尝试、描述性对话至少各加一项确定性回归测试。
4. 若该动作需要区分同一句内不同事件，断言 `ActionEvent` 的证据 span、顺序和 allowlist，不要只断言 message-level category。
5. 运行第 5 节全部验证命令；再在 CK3 与实际模型提供商环境中手动冒烟测试。
