# VOCT v6.6 Pre-Change Audit

> 审查日期：2026-08-20  
> 审查方式：只读当前 `main.js`、四个高风险/代表性 Action Script 与现有回归脚本；未在本审查阶段修改生产代码。  
> 判定标准：当前源码与可运行测试高于 v6.5 历史报告。

## 结论摘要

v6.5 的 `ActionEvent`、Positive Evidence、metadata 解析和玩家/NPC 评估计划已经存在，但 v6.6 方案列出的九项问题中有八项在当前生产路径中得到确认。最优先的两个实际安全缺口是：

1. 所有动作均默认把消息发言者作为 `sourceCharacter`，这与死亡、囚禁、任命等 Script 的 source/target 语义冲突。
2. 审批仅根据 `isDestructive`，没有将 `semantic.riskLevel = "high"` 纳入统一策略；`isInjured` 与 `isImprisonedBy` 均属于此脱节情形。

## 关键证据

### 参与者映射

- `ActionEngine.evaluateForCharacter()`：约 6447 行以 message speaker 选择 `actionSource`，约 6491 行以其执行 `check()`，约 6671 行将其传入 `runInvocation()`。
- `characterIsKilled`：`sourceCharacter` 是 victim，`targetCharacter` 是 killer。
- `isImprisonedBy`：`sourceCharacter` 是 prisoner，`targetCharacter` 是 jailor。
- `isEmployedAsKnightBy`：`sourceCharacter` 是 appointee，`targetCharacter` 是 employer。
- `isInjured`：实际写入的是 `targetCharacter`（伤者）；source 仍为叙事 actor，因此需要固定 patient target，而不是套用死亡/囚禁的 source/target 映射。

因此“我杀死张三”若固定 speaker 为 source，会把玩家当成受害者；同类反转也影响囚禁与任命。伤害的风险则是模型可自由选择错误伤者，必须将 target 固定为解析出的 patient。

### 审批风险

- `ActionRegistry.getEffectiveDestructive()`：约 4729 行仅以 override 或 `isDestructive` 决定。
- `evaluateForCharacter()`：约 6638 行取得该布尔值，约 6641 行根据 approvalMode 决定审批。
- `isInjured` 与 `isImprisonedBy` 均声明 `semantic.riskLevel: "high"`，但未声明 `isDestructive: true`。

在“自动接受非危险操作”模式下，它们会被当前逻辑当作非危险动作直接执行。

### 语义与生命周期

- `getSemanticActionProfile()`：metadata 未命中时保留 `getLegacySemanticProfileForEvidence()` 的结果。
- `shouldEvaluateForMessage()`：allowlist 为空时没有 resolution mode，后续 `semanticAllowlist.size === 0` 会放开 category 候选。
- `sendMessage()`：只保存 pending 玩家消息；`evaluateCompletedActions()` 在 NPC 成功生成后才消费该消息。

## P0 最小实施方案

### 1. Participant Role Model

先为死亡、囚禁、任命骑士声明：

```js
participantRoles: { source: "patient", target: "actor" }
```

伤害动作声明：

```js
participantRoles: { source: "actor", target: "patient" }
```

新增 `ActionEngine.resolveEventParticipants()`，只依据事件的 Positive Evidence、发言者和当前会话角色表解析 source/target。无法唯一解析时返回 `unresolved`，并跳过该状态型动作；不得回退为 speaker=source。

### 2. Unified Risk Policy

新增 registry 的 effective risk / effective destructive 计算：

```text
high risk → 强制 destructive，用户 override 仅可进一步要求审批，不可降级高风险。
medium / low → 保持既有 destructive override 兼容。
```

审批循环改为读取统一策略，并在 action approval 记录中保留 risk level。

### 3. P0 测试门槛

在修改生产路径前新增独立测试，至少覆盖：

- “我杀死张三” / “张三被我杀死”；
- “我把张三关进地牢” / “张三把我关进地牢”；
- “我任命张三为骑士” / “国王任命我为骑士”；
- “我刺伤张三” / “张三刺伤我”；
- high risk 且无 `isDestructive` 时，在 `non-destructive` 模式不得自动执行。

## 非 P0 变更边界

本轮不把 `main.js` 拆分模块，不重写 Prompt/Provider/摘要系统，不删除已经声明 `requiresLegacyResolution` 的金币方向兼容逻辑。Resolution mode、独立 player lifecycle、mini runtime harness、Gate 软化、message-scoped dedupe 与 parser fuzz 进入后续 v6.6 阶段，并分别建立测试。
