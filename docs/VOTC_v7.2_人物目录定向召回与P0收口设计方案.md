# VOTC v7.2 人物目录定向召回与 P0 收口设计方案

> 文档性质：V7.1 现状审计后的开发方案，不代表本文所列项目已经实现。  
> 目标版本：V7.2  
> 核心目标：让 Memory Engine 严格按照“每个人只从自己的记忆目录取回记忆”的模型工作，并彻底关闭动作失效、连续会话不保存摘要两个 P0 风险。

## 一、结论

V7.1 已经完成了新系统的基础骨架，但尚未完全符合目标模型，因此需要 V7.2。

当前已经具备：

- 每个角色拥有独立摘要目录。
- 一场多人对话结束后，摘要按有向人物关系写入各参与者目录。
- NPC 生成回复时仅查询该 NPC 自己的目录；玩家不执行记忆召回。
- Memory Engine 2.1 与摘要管理 UI 使用同一套人物目录数据，不再维护第二套重复摘要树。
- 摘要可在 UI 中查看、搜索和修改。

当前仍不完整：

- A 与 B 对话时，系统会扫描 A 或 B 的整个目录后统一排序，尚未先精确读取“与对方的对话”文件。
- 场外人物识别只检查最近三条玩家消息，NPC 提到 X 时不能可靠触发其他 NPC 从各自目录召回 X。
- 召回条数没有按“直接对话对象”和“被提及场外人物”分别定义。
- 动作系统自动化回归已经通过，但仍需增加“启用动态记忆注入”条件下的动作集成门禁。
- 连续会话摘要已有恢复和幂等机制，但会话切换仍以不等待结果的方式启动异步终局；第二场会话摘要缺失的 P0 风险尚未完全关闭。

## 二、目标记忆模型

### 2.1 唯一数据所有权

每个角色只有一个人物摘要目录，目录表示“这个角色知道和记得的内容”。

```text
conversation_summaries/
├─ A_ID_A姓名/
│  ├─ 与B姓名的对话.json
│  ├─ 与C姓名的对话.json
│  └─ 与X姓名的对话.json
├─ B_ID_B姓名/
│  ├─ 与A姓名的对话.json
│  ├─ 与C姓名的对话.json
│  └─ 与X姓名的对话.json
└─ C_ID_C姓名/
   ├─ 与A姓名的对话.json
   ├─ 与B姓名的对话.json
   └─ 与X姓名的对话.json
```

必须遵守以下边界：

1. A 的回复只能使用 A 目录中的记忆，不能直接读取 B、C 或 X 的目录。
2. B 的回复只能使用 B 目录中的记忆。
3. 玩家目录继续保存摘要并允许管理，但玩家不是模型回复者时不进行提示词记忆注入。
4. 同一场多人对话可分别写入多个有向关系文件，这是不同角色各自拥有的记忆副本，不属于重复系统。
5. 使用同一个 `finalizationId` 标记同一场会话，防止重试时在同一个关系文件中重复追加。

### 2.2 直接参与者召回

当 A 与 B 对话时：

- 为 A 生成回复：只读取 `A/与B的对话.json`。
- 为 B 生成回复：只读取 `B/与A的对话.json`。
- 若 A 是玩家，不为 A 注入记忆；B 仍读取 `B/与A的对话.json`。

当 A、B、C 或更多人同时对话时，对每个将要回复的 NPC 建立独立召回计划。例如为 B 生成回复时：

- 从 `B/与A的对话.json` 读取 B 对 A 的记忆。
- 从 `B/与C的对话.json` 读取 B 对 C 的记忆。
- 继续为其他所有在场人物读取 B 目录中的对应关系文件。
- 不设置参与人数数量上限，以 token 预算控制最终内容长度。

### 2.3 场外人物召回

如果当前任意发言者提到不在场的 NPC X：

- 为 A 生成后续回复时，搜索 A 自己目录中与 X 有关的摘要。
- 为 B 生成后续回复时，搜索 B 自己目录中与 X 有关的摘要。
- 为 C 以及更多在场 NPC 生成后续回复时执行同样规则。
- 不读取 X 自己的目录，也不在不同所有者目录间共享结果。
- 被提及人物数量不设固定上限，仍由统一 token 预算公平分配。

“有关 X”按以下优先级判定：

1. 精确关系文件：`与X的对话.json`。
2. 摘要的参与者 ID 或人物 ID 包含 X。
3. 结构化主题、人物索引中包含 X。
4. 摘要正文包含 X 的姓名或已确认别名。

只允许使用 ID 和明确人物索引确定同名人物；姓名文本匹配不能覆盖更高优先级的 ID 匹配。

## 三、召回数量与 token 预算

摘要数量只是最低覆盖规则，最终上限必须由 token 预算决定，否则多人和多场外人物场景会无限膨胀提示词。

### 3.1 推荐条数

#### 一对一直接对话

每个 NPC 对当前对话对象默认召回 3 条：

- 最近 2 条摘要，用于保持近期连续性。
- 与当前问题最相关的 1 条历史摘要，用于召回较早事件。

如果相关摘要已经属于最近 2 条，则去重后允许少于 3 条，不使用低相关内容强行补足。

#### 三人及以上直接对话

对每个其他在场人物先保证 1 条最近摘要；完成基础覆盖后，再从所有直接关系中补充最多 2 条与当前话题最相关的摘要。

示例：B 正在与 A、C、D 对话时，B 至少得到 B-A、B-C、B-D 各 1 条；剩余预算再按相关度补充 2 条，而不是只照顾排序最靠前的一个人物。

#### 场外人物

每个被提及的场外人物 X 默认召回 1 至 2 条：

- 保证 1 条最近且确实涉及 X 的摘要。
- 预算允许时，再增加 1 条与当前话题最相关的 X 摘要。

### 3.2 预算规则

每次 NPC 回复的记忆预算建议为：

```text
memoryTokenBudget = clamp(floor(contextLimit * 0.08), 800, 2400)
```

预算分配：

- 55%：当前在场人物的直接关系记忆。
- 30%：被提及的场外人物记忆。
- 15%：该角色自己的长期稳定、未解决或高重要度结构化记忆。

某一区域未用完的预算可以流向其他区域。人数或场外人物过多时，不以 `slice(0, N)` 丢弃整个人物，而应先对每条关系做一条公平覆盖，再缩短单条摘要文本。这样“没有人物数量上限”与模型上下文的物理上限可以同时成立。

## 四、V7.2 召回架构

### 4.1 每个回复者生成独立路由计划

新增明确的 `MemoryRoutePlan` 概念：

```text
respondingCharacterId  当前准备回复的 NPC
directCounterpartIds   所有其他在场人物，不含回复者本人
mentionedOutOfSceneIds 当前会话已识别的场外人物
query                   当前问题与必要的近期上下文
tokenBudget             本次回复可用记忆预算
```

如果回复者是玩家，直接跳过路由和提示词注入。

### 4.2 MemoryStore 增加两条精确查询路径

1. `loadDirectPairSummaries(ownerId, counterpartId)`
   - 只读取所有者目录中的对应关系文件。
   - 按 `finalizationId` 去重。
   - 支持时间排序和主题相关度排序。

2. `searchOwnerFolderForEntity(ownerId, entityId, entityNames)`
   - 只扫描 `ownerId` 的人物目录。
   - 依次使用关系文件、参与者元数据、结构化人物索引和正文匹配。
   - 不允许退回全局其他人物目录。

现有“加载所有者整个目录后统一排名”的路径只作为内部稳定记忆的补充，不再负责直接关系的首要召回。

### 4.3 MemoryEngine 分通道召回

`retrieveForResponder(routePlan)` 按以下顺序执行：

1. 直接关系通道：逐个对话对象精确取回，保证公平覆盖。
2. 场外人物通道：逐个 X 在回复者自己的目录中检索。
3. 内部稳定记忆通道：补充未解决、高重要度和长期记忆。
4. 合并去重：使用 `memoryId + finalizationId + ownerId` 去重。
5. token 分配：按本方案的比例和回流规则选取内容。

输出调试信息至少包括：所有者 ID、直接对象 ID、场外人物 ID、候选数、选中数、token 数和未选中原因；不得记录完整私人摘要正文。

### 4.4 全发言者人物提及检测

现有只查看最近三条玩家消息的实现需要替换为会话级检测：

- 检查当前会话中玩家和 NPC 的新发言。
- 每条消息只解析一次，并记录消息 ID 或 turn ID。
- 维护 `mentionedOutOfSceneIds` 集合，不使用固定数量截断。
- 排除玩家本人、当前回复者和所有在场人物，避免把直接参与者重复归入场外人物通道。
- NPC 在本轮队列中提到 X 后，尚未生成回复的其他 NPC 可立即使用各自的 X 记忆。
- 已经生成完毕的前序回复不做逆向重生成；这是对话时序边界，不属于漏召回。

## 五、摘要落盘模型

### 5.1 多人会话的有向保存

一场有 N 名参与者的会话完成后，保持当前的 `N × (N - 1)` 有向关系写入：

- A 目录保存面向 B、C……的会话记录。
- B 目录保存面向 A、C……的会话记录。
- 其他参与者同理。

同一份群聊摘要可以出现在同一所有者的多个关系文件中，因为召回路由需要通过任一相关人物找到该场会话。每个文件内以稳定 `finalizationId` 保证重试幂等。

### 5.2 连续会话终局协调器

V7.2 必须引入单一 `FinalizationCoordinator` 或等效的串行终局队列：

1. 结束当前会话时先从管理器中分离该 `Conversation` 实例。
2. 将该实例的终局任务放入持久化队列，不再直接丢弃未等待的 Promise。
3. 新会话可以立即创建，但不能复用上一会话的历史、参与者、摘要状态或 `finalizationId`。
4. 终局任务可以后台执行，但同一用户数据目录的写入必须串行提交。
5. 应用正常退出时等待队列排空；无法等待时必须先写入可恢复快照。
6. 恢复快照记录尚未完成的有向关系文件，重启后只补写缺失目标，不重复调用已经成功的摘要模型请求。

一次终局仅在以下内容全部持久化后才标记完成：

- 结构化记忆与会话事件。
- 知识索引。
- 所有参与者的全部有向摘要关系文件。
- 最终恢复状态与幂等标记。

## 六、两个 P0 问题的当前审计

### 6.1 P0-1：V7 动态记忆启用后动作系统全部失灵

当前判定：**代码级回归已通过，实机闭环仍需 V7.2 门禁确认。**

当前证据：

- `scripts/test-action-regression.js` 通过，共 28 组动作回归脚本。
- 动作解析、参与者绑定、执行契约和 trace 回归均处于通过状态。
- 尚无足够证据证明“真实模型回复中同时注入 Memory Engine 记忆”时，所有动作仍能在 CK3 实机执行。

V7.2 收口任务：

1. 新增开启 Memory Engine 的动作集成测试，记忆块中故意放入动作词，确认旧记忆不会被误当成本轮动作。
2. 动作识别只消费本轮模型响应中的动作协议，不读取召回摘要中的类似文本。
3. 覆盖成功、询问、将来意图、失败尝试和叙述性提及五类语义。
4. 覆盖单人、多人、场外人物被提及和连续会话切换后的动作执行。
5. 对全部标准动作定义执行确定性契约检查；对代表性动作验证 CK3 source/target 绑定。
6. 进行至少 100 次连续动作调用压力回归，目标为 0 次来源人物串线、0 次目标人物串线、0 次因记忆文本产生的幽灵动作。
7. 完成一次真实 CK3 + 当前模型提供商的人工冒烟测试后，才允许把该 P0 标记为实机关闭。

### 6.2 P0-2：与第一名 NPC 对话后，第二场会话不保存摘要

当前判定：**已有部分修复，但尚未彻底关闭。**

当前已经存在：

- 每个新 `Conversation` 使用独立会话 ID 和记忆状态。
- 稳定 `finalizationId`、终局恢复快照和幂等写入。
- 人物目录的双向及多人有向关系保存。
- V7.0.1 终局恢复、V7.1 目录隔离自动化测试通过。

剩余风险：

- 会话管理器在创建新会话前调用 `finalizeConversation()`，但当前不等待该异步任务，也没有统一终局队列。
- 两场摘要生成和多个关系文件写入可能并发，失败生命周期与应用退出时机不清晰。
- 现有测试没有完整复现“第一场结束后立刻开始并结束第二场”的实际操作。

V7.2 必须新增以下回归：

1. 玩家-A 结束后立即开始玩家-B，确认两场都调用一次摘要生成，并写入玩家、A、B 的正确关系文件。
2. 人为延迟第一场落盘，再完成第二场，确认终局队列顺序、状态和目标目录均正确。
3. 第二场首次摘要返回空内容或写入失败，确认恢复快照可重试且第一场不重复。
4. 在终局队列未排空时退出并重启，确认缺失文件被补齐。
5. 连续进行 50 场交替 NPC 会话，要求 50/50 场均有唯一 `finalizationId`，无跨会话参与者和摘要串线。
6. 多人会话后立刻切换一对一会话，验证两种参与者集合不会互相污染。

## 七、开发阶段

### 阶段 0：先建立问题复现与行为基线

- 为精确关系召回、NPC 提及场外人物和连续两场摘要建立失败测试。
- 固定 V7.1 当前数据格式样本，确保 V7.2 不破坏已有可编辑摘要。
- 验证：新测试在未实现 V7.2 前能准确暴露缺口，现有回归仍全部通过。

### 阶段 1：实现人物目录精确路由

- 实现 `MemoryRoutePlan`。
- 增加直接关系文件精确读取和所有者目录人物检索。
- 将统一全目录排名降级为补充通道。
- 验证：A-B、A-B-C、十人会话均只从当前回复者目录召回，且每个在场对象至少获得一条覆盖。

### 阶段 2：实现全发言者场外人物召回

- 使用消息/turn 增量解析替换“最近三条玩家消息”。
- 所有 NPC 共用场外人物 ID 集合，但分别从自己的目录检索。
- 实现无人物数量截断的公平 token 分配。
- 验证：玩家或任一 NPC 提到 X、Y、Z 后，所有后续 NPC 回复者均获得属于自己的相关记忆。

### 阶段 3：关闭连续会话摘要 P0

- 引入终局协调器和可恢复提交状态。
- 串行化摘要目录写入，隔离每个 `Conversation` 的终局上下文。
- 完成连续 50 场、延迟、失败、退出恢复测试。
- 验证：所有场次均产生唯一且完整的有向摘要文件集合。

### 阶段 4：关闭动作系统 P0

- 增加带记忆注入的动作集成测试。
- 验证动作协议与记忆文本严格隔离。
- 跑完整动作回归、压力回归和 CK3 实机冒烟。
- 验证：自动化与实机均通过后才关闭 P0。

### 阶段 5：UI 与发布收口

- UI 继续只显示唯一人物目录树，不新增第二套 Memory Engine 摘要列表。
- 搜索人物时首先定位该人物目录，再展示其他所有者目录中涉及此人的记录。
- 编辑保存后立即使索引失效并重建该文件的轻量索引。
- 更新版本、V7 阶段优化记录与测试报告。

## 八、验收标准

### 8.1 记忆正确性

- 一对一：A 与 B 对话时，B 只得到 `B/与A` 的摘要；A 是玩家时不为 A 注入记忆。
- 多人：每个 NPC 分别从自己的目录读取与全部在场人物的直接关系摘要。
- 场外人物：任意发言者提到 X 后，每个后续 NPC 只从自己的目录召回 X 相关摘要。
- 无人数硬上限：至少通过 10 名在场人物、5 名场外人物的自动化用例；允许压缩内容，但不得因固定数组截断丢掉某个人物。
- 所有权隔离：任何召回 trace 中的 `ownerId` 必须等于当前回复者 ID。
- 去重：同一回复中相同 `finalizationId` 的同一场会话不重复注入。

### 8.2 摘要可靠性

- 连续 50 场会话保存成功率 100%。
- 每场均拥有唯一稳定 `finalizationId`。
- 每场参与者产生完整的 `N × (N - 1)` 有向关系写入。
- 应用退出恢复不重复调用已成功的摘要请求，不重复追加已保存记录。

### 8.3 动作可靠性

- 现有 28 组动作回归继续全部通过。
- 带 Memory Engine 注入的动作集成测试全部通过。
- 100 次连续动作压力测试无 source/target 串线和幽灵动作。
- CK3 实机冒烟通过后记录为“实机已验证”；此前只能标记为“静态/自动化通过”。

### 8.4 发布检查

```powershell

node scripts\test-v7.0.1-finalization-runtime.js
node scripts\test-v7.1-memory-engine.js
node scripts\test-memory-ui.js
node scripts\test-v7.2-memory-routing.js
node scripts\test-v7.2-sequential-finalization.js
node scripts\test-v7.2-action-memory-integration.js
node --check resources\app\out\main\main.js
```

所有自动化通过后，还需执行真实 CK3 日志、动作效果和当前模型提供商的人工回归。

## 九、兼容与非目标

### 9.1 兼容策略

- 不删除、不批量改写玩家已有摘要。
- 继续使用当前人物目录和关系文件格式，优先通过读取路由升级完成 V7.2。
- 新增字段必须可选，旧记录缺少人物 ID 时才使用受限的姓名兼容匹配。
- UI 编辑后的摘要仍是召回数据源，不建立只读影子副本。

### 9.2 本版本不做

- 不引入向量数据库或额外联网检索服务。
- 不为每次召回增加一次额外 LLM 请求。
- 不重新建立旧摘要系统与 Memory Engine 两套并行 UI。
- 不在 V7.2 扩展与人物目录定向召回、摘要可靠性或动作 P0 无关的功能。

## 十、最终交付定义

V7.2 只有在以下三项同时满足时才算完成：

1. **目录模型完成**：所有 NPC 都按“自己的目录 → 当前参与者/场外人物”的路线精确召回。
2. **摘要 P0 关闭**：连续、并发、失败和退出恢复场景都不会漏掉第二场或后续会话摘要。
3. **动作 P0 关闭**：动态记忆启用时动作自动化与 CK3 实机验证均通过，召回文本不能触发动作。

在此之前，V7.1 应描述为“人物目录已经统一、Memory Engine 2.1 基础可用”，不能描述为完整实现了目标动态记忆模型。
