# V8.8.1 第三方亲属关系锚点实施报告

日期：2026-09-10  
状态：代码与自动化回归完成；真实 CK3 / Provider Gate 待执行

## 完成内容

- 新增 `relation-intent-parser.js`，将关系类型、显式性别、出生顺序、最近出生和关系词来源拆为确定性 DTO。
- 新增 `relation-anchor-resolver.js` 与 `anchored-relation-resolver.js`，明确区分回应者、关系主体和查询目标三个 Runtime ID。第三方姓名、头衔和“府”表达从关系词前的候选中解析；同名/同称号不静默选择。
- `character-family-facts.js` 改为以关系主体查询 Kinship Graph。已解析目标会以 CK3 当前结构化事实注入姓名、Runtime ID、性别、生死和年龄；不再只读取回应 NPC 的家族。
- 对“得一子/得一女”等显式性别表达实施 fail-closed：Anchor 或候选无法可靠解析时，Prompt 仍收到不得将男性/女性亲属反向改写的约束。
- 仅亲属意图才生成该事实块；普通闲聊保持旧行为，不额外注入家谱或增加 Prompt token。
- `getMentionableCharacterProfiles()` 补齐直接子女的儿子/女儿、长子/次子/幼子、长女/次女/幼女、公子、世子、嗣子、千金、子嗣和后嗣辅助别名。别名只辅助召回，不替代 Runtime ID 图查询。
- 每次检测到亲属意图时输出单行 `[VOTC Relation]` 诊断，包含 intent、sex、Anchor、Target 与 resolution status。

## Golden Test 与边界

`嗯~朕听闻最近幽王府又得一子，名唤什么？我一边喝茶一边问道` 的自动化 fixture 没有任何摘要、Memory 或 Supplemental 数据。结果完全来自：

```text
primaryTitle / 幽王府
→ Relation Anchor Runtime ID
→ CK3 children
→ male + 最新 birthDateTotalDays
→ 赵允韬 Runtime ID
```

该用例验证生成前 Prompt 强制包含“男性”，不会把目标写成女儿、她或女子。它是结构化关系事实测试，不是 Provider 最终自然语言输出实机验收。
