# V7 阶段优化记录

本文件记录 VOTC V7/V7.x 的功能与架构优化。V6/V6.x 历史继续保留在 `docs/V6阶段优化记录.md`，README 只维护版本索引与当前基线。

## 第一阶段：v7.0 Memory Engine 2.0

### A. 摘要耐久性

- Rolling Summary 的批次选择与 checkpoint 提交迁入 `resources/app/out/main/memory-system/rolling-summary-manager.js`，修复“切片后的局部数组继续使用绝对索引”造成的消息跳跃。
- checkpoint 采用两阶段提交：先选择批次并调用摘要 Provider，只有拿到有效结果后才更新 `committedThroughHistoryIndex`、`committedThroughMessageId`、`summaryVersion` 与 `currentSummary`。
- Rolling Summary 改为替换语义：`旧摘要 + 新批次 → 新摘要`，不再把完整新摘要继续追加到旧摘要后方。
- Final Summary/Extraction 失败时，将原始消息、rolling 状态、参与者与 presence window 写入 `%APPDATA%/VOTC/votc_data/memory_recovery/conversation_<uuid>.json`。下一次建立会话时自动重试一次；再次失败仍保留快照，不清除原始数据。

### B. 结构化长期记忆

- 新增 `resources/app/out/main/memory-system/`，包含 `MemoryEngine`、`MemoryStore`、`MemoryExtractor`、`MemoryRanker`、`KnowledgeService`、`RollingSummaryManager`、`MemoryConsolidator`、`MemoryTrace` 与统一类型定义。
- 每场会话只进行一次最终摘要请求。Provider 返回结构化 JSON 时，系统提取 event、promise、relationship、secret、belief、plan、conflict、information、rumor、unresolved 与 letter；若 Provider 仍返回自然语言，则降级保存 session summary，不丢失旧摘要兼容输出。
- MemoryRecord 使用 `schemaVersion: 2`，记录 type/subtype、日期、参与者、主体、canonical text、重要度、可信度、认知状态、来源、provenance、关系影响、未决状态、visibility 与 knownBy。
- 新数据写入 `%APPDATA%/VOTC/votc_data/memory/` 下的 episodes、characters、pairs、knowledge 与 index；原 `conversation_summaries` 文件继续作为只读兼容来源。

### C. 角色知识边界与视角

- 每条记忆通过独立 KnowledgeRecord 记录角色的 witnessed/told/heard/inferred/rumor 知情方式；私密记忆只向实际知情角色检索。
- Participant Presence 保存每名角色的加入与离开消息边界。结构化记忆按 messageId 计算当时在场者；缺少 messageId 的自然语言降级摘要，只授予覆盖整场会话的参与者。
- 移除“回应 NPC 没有第三方摘要时读取玩家摘要文件”的回退，避免 NPC 偷读玩家私有记忆。
- 模型输出的参与者、speaker 与 visibility 会在本地按实际会话参与者再次收敛；对话提取不能把普通内容直接升级为 world/public，secret 强制使用受限知情组。
- Episode 保存共享事件与本地生成的角色 Perspective；事实、信念、计划和传闻保持不同类型，不把角色观点自动升级成世界事实。

### D. 本地检索与 Prompt 分层

- MemoryRanker 按 `0.30 查询相关 + 0.20 实体相关 + 0.20 重要度 + 0.15 时间衰减 + 0.10 关系相关 + 0.05 可信度` 本地排序，不增加每轮 LLM 请求，也不引入向量数据库。
- `importance >= 0.9` 的关键记忆优先固定；open promise、unresolved thread 与关键关系记忆进入稳定长期记忆层。超长关键记忆会在预算内截断，而不是静默丢弃。
- Memory block 预算为当前模型上下文的约 12%：稳定记忆使用 30%，查询相关记忆使用 50%，剩余空间留给 rolling summary。
- Prompt 顺序保持缓存友好：固定 Cache Anchor 与稳定角色内容在前，稳定长期记忆随后；当前游戏资料、话题相关记忆、第三方人物上下文靠近 history。`VOTC_CACHE_ANCHOR_v1` 与 `VOTC_SUMMARY_CACHE_ANCHOR_v1` 未修改。
- CK3 `character.memories` 只注入当前回应角色，信件 Prompt 同样不再汇总玩家与收信人的全部游戏记忆。

### E. Consolidation 与抗漂移

- 单角色结构化记忆超过 100 条时，本地生成 consolidation 索引，固定 critical memory、open promise、unresolved thread 与 relationship trend。
- consolidation 只保存 derivedFrom 引用与趋势，不删除关键原始记忆，也不修改 CK3 世界状态；游戏效果仍完全由 Action System 负责。
- 原 pair JSON、多人逐对保存、Summary Provider override、信件摘要与离场摘要路径继续保留；信件双方会获得对应 letter memory。

### F. QA 与可观测性

- 新增 `scripts/test-memory-regression.js`，覆盖三次 rolling checkpoint、Provider 失败不推进、final recovery、秘密隔离与显式传播、晚加入者边界、关键旧记忆召回、token budget、结构化恢复和 legacy lazy adapter。
- 新增 `scripts/test-v7-memory-health.js`，检查模块所有权、Conversation 无 rolling algorithm、两阶段提交装配、玩家摘要 fallback 清零及 responder-only CK3 memory。
- `scripts/test-release.js` 升级为 v7.0 发布门禁，依次覆盖 syntax、v6.9.1 architecture/follow-up、28 组 Action regression、memory health、memory regression 与 character game facts。
- MemoryTrace 记录 checkpoint、extract、classify、knowledge、persist、rank、retrieve、inject、consolidate 与 recover；仅记录 ID、类型、得分、原因和角色，不记录完整 Prompt 或消息正文。

### 兼容与验证边界

- 旧摘要采用首次检索时的只读 lazy adapter，不要求用户批量迁移，也不会自动删除或覆盖旧文件。
- 自动回归不依赖 CK3、真实 Provider 或 `%APPDATA%` 中的用户数据。
- VOTC.exe 启动冒烟只能验证 Electron 主进程可加载；长对话 rolling、秘密传播、多人晚加入、Provider 断线恢复与关键旧记忆召回仍需在 CK3 和实际摘要 Provider 中完成发布前实机验证。

## 第二阶段：v7.0 摘要管理 UI 与人物检索

### A. 新版摘要管理界面

- 摘要页新增 Memory Engine 2.0 状态面板，显示结构化记忆、episode、知识索引人物、旧摘要目录、摘要文件和摘要记录的实时数量。
- 新增按人物展开的记忆覆盖卡片，区分“可访问结构化记忆”“知识边界外记忆”“本人旧摘要目录”“兼容层实际可召回”以及“其他人物目录中的相关摘要”。
- 当前人物能够访问的结构化记忆以只读明细显示，包括类型、子类型、日期、正文、重要度、visibility 与状态。其他人物未知的受限记忆只计数，不显示正文。
- UI 内可直接展开查看四条知识边界规则；“其他人物目录中的相关摘要”只用于管理检索，不会越权注入该人物的对话 Prompt。

### B. 人物精确搜索

- 新增统一摘要目录 catalog，以真实 `角色ID_姓名` 文件夹作为目录拥有者，不再把对话对象误当作文件夹人物。
- 输入姓名或 ID 后，结果按“该人物自己的摘要目录 → 他人与该人物的直接对话 → 其他摘要中参与或提及该人物”排序，并自动展开命中目录和文件。
- 搜索索引覆盖目录拥有者、目录名、对话对象、双方 ID、participants、摘要正文与日期；结果标签明确说明命中原因。
- 搜索框支持 `Esc` 和“清除”按钮，并显示三类命中数量；人物姓名继续使用三主题统一的高对比亮银色处理。

### C. 第三者记忆绑定与覆盖核验

- 对话检索会把当前历史中识别到的第三者人物 ID 传入 MemoryRanker。玩家与 NPC B 提到 NPC C 时，C 相关结构化记忆获得实体相关分，同时旧摘要只从 B 自己的 `B_ID_姓名` 目录惰性读取。
- NPC B 不会回退读取玩家或 NPC C 的私人摘要目录；公开/world 结构化记忆仍按设计对所有角色可见。
- 2026-08-21 对真实用户数据进行只读核验：50 个摘要目录、240 个摘要文件、1004 条旧摘要记录，覆盖 48 个唯一人物 ID；这 1004 条均可由对应人物的 legacy adapter 读取。
- 核验时真实数据中的结构化记忆、episode 与 knowledge 索引均为 0，说明旧摘要兼容召回已可用，但需要结束一场由新版程序处理的有效会话后才会产生 Memory Engine 2.0 结构化记录。

### D. 自动验证

- 新增 `scripts/test-memory-ui.js`，覆盖本人目录精确命中、他人直接对话、第三方参与提及、B 从自身目录召回 C、结构化知识边界、受限正文隔离以及 UI/IPC 装配。
- `scripts/test-release.js` 增加 memory-ui 发布门禁；v7.0 发布回归现为 8 组，原 28 组动作回归保持通过。

### E. 摘要页性能收口

- 摘要列表与 Memory Engine 覆盖统计改为单一 `conversation:getSummariesDashboardData` IPC：240 个 JSON 文件只读取、解析一次，不再由摘要列表和覆盖面板并行重复扫描。
- 覆盖统计直接复用已建立的 summary catalog 计算 legacy adapter 数量，不再为 48 个角色逐目录重新读取旧摘要。
- 搜索输入使用 React deferred value 与 memoized filtering，输入框的即时更新不再被 1004 条正文扫描阻塞。
- 搜索仍展开所有命中目录，但只自动展开排序第一的摘要正文；其余结果保留文件标题和命中原因，用户可按需展开。真实数据中搜索“赵从鉊”命中 208 个文件，自动展开正文由 208 个降为 1 个。
- “人物记忆覆盖”默认折叠，手动查看时每批只渲染 12 人；搜索人物时只渲染命中的人物卡片。摘要目录、对话文件和人物卡片启用 Chromium `content-visibility`，跳过屏幕外布局与绘制。
- 2026-08-21 真实数据只读基准：240 个文件、1004 条摘要的目录解析约 76.0 ms，Memory Engine 覆盖计算约 18.4 ms，合计约 94.3 ms；人物搜索循环平均约 0.64 ms/次。

### F. 搜索排序与窗口边界

- 搜索结果按玩家目录分组时改用有序 `Map`，保留人物精确匹配的排序；按人名搜索时，该人物自己的摘要文件夹稳定显示在第一位。
- 主窗口改为使用主显示器 `workArea` 的位置与尺寸启动，并取消全屏模式，避免 VOTC.exe 覆盖 Windows 底部状态栏。
- 新增 `scripts/test-window-layout.js`；发布回归现为 9 组，涵盖搜索分组顺序和窗口工作区边界。

### G. P0：终结摘要空响应恢复

- 终结摘要 Provider 返回空内容时，当前会话会立刻重试一次；两次均失败才写入恢复快照，因此一次瞬时空响应不会丢失角色摘要。
- 恢复快照由一次启动重试放宽为最多三次。原始对话和参与者信息会保留到摘要成功写入后才删除快照。
- 已为“第一次空响应、第二次成功”及“已重试一次的历史快照仍可恢复”加入 Memory Engine 回归覆盖。

### H. 结构化记忆编辑与按角色对话归档

- 摘要页中的“可访问的结构化记忆”已改为可编辑：玩家可修改记忆正文，保存时同步更新检索用规范文本，不改变角色的知情范围、参与者或可见性。
- 终结摘要的参与者改以会话期间记录的 participant presence 为准，而非仅反查已完成的 NPC 消息名称；即使消息名称未匹配，也会按参与者写入旧式兼容目录。
- 每位参与者的兼容摘要仍按 `角色ID_姓名/与对方角色的对话.json` 分文件保存，角色与不同 NPC 的对话不会混入同一摘要文件。

### I. 既有结构化会话摘要归档

- 新增 `scripts/migrate-structured-episodes-to-summary-folders.js`：只从结构化 episode 读取会话摘要，并追加写入双方角色目录；不会删除结构化数据，不会覆盖或重复现有摘要。
- 已迁移现有的“花魁，李师师（95829）”与“宣和皇帝，赵佶（92558）”会话：双方各创建一个角色目录与一个“与对方的对话”摘要文件。
- 摘要 UI 的目录子项现在直接显示对话文件名（如“与宣和皇帝，赵佶的对话”），形成“角色文件夹 → B 角色对话”的层级。

## 第三阶段：v7.1 Memory Engine 2.1

### A. 人物目录成为统一记忆层

- `conversation_summaries/角色ID_姓名/与对方的对话.json` 由兼容输出提升为 Memory Engine 2.1 的人物视角长期记忆源；内部 structured memory、episode、knowledge 与 pair index 继续负责分类、恢复和知识边界，但不再作为第二套摘要正文 UI 展示。
- 每次为某 NPC 构建 Prompt 时，只扫描该回应角色自己的 `ID_姓名` 目录。A 与 B 的同一场会话分别由 A 目录和 B 目录召回，禁止回退读取玩家或其他 NPC 的私人目录。
- 旧 `past_summaries` 与 `loadDynamicMemoriesFromHistory` 摘要正文注入在 Engine 2.1 启用时断开，消除同一摘要被目录适配层和旧 Prompt 链路重复注入的问题；CK3 人物关系资料仍保留在 mentioned-character context 中。

### B. 无固定人数上限的第三者召回

- `findMentionedCharacterIdsInHistory` 与旧动态检测中的“两名人物”硬上限已移除；当前玩家消息可以识别任意数量已加载角色及其直接亲属。
- 召回同时接收第三者 ID 与姓名别名。直接参与者通过 participant ID 相关性排序，第三者通过 subject ID、目录文件名、参与者姓名、摘要正文与当前查询共同匹配。
- 多 NPC 会话为每个回应者独立执行同一规则：ABCD 同时参与并提到 E 时，A/B/C/D 各自只从自己的目录召回 E 相关摘要。人数不设固定上限，但最终注入仍受当前模型上下文的动态 token budget 保护。
- 同一群聊终局摘要会镜像到同一拥有者目录下的多个配对文件；Engine 2.1 按 `finalizationId` 合并为一条召回，避免群聊人数增加后重复消耗 token。

### C. 终局摘要与玩家编辑

- 会话结束仍以 participant presence 作为参与者真值，为所有实际参与者写入全部有向配对文件，因此 A、B 双方目录都会保留同一场会话摘要；恢复重试继续依赖稳定 `finalizationId` 保证幂等。
- 新增人物摘要原子写入：先写临时文件再替换正式 JSON，避免进程中断留下半截文件。
- UI 编辑以人物目录摘要为唯一入口；编辑镜像摘要时优先按 `finalizationId` 定位同一记录，而非假定两个文件的数组索引永远一致。多文件提交失败时回写已更新文件，避免双向内容分叉。
- 内部结构化 Memory 编辑新增最多 20 版历史、`updatedBy` 记录与跨 Memory/Pair Index/Knowledge/Character Consolidation 事务回滚；任一索引或知识写入失败都会恢复修改前版本，不会留下错误知情范围。

### D. 摘要管理 UI 收口

- 状态面板更新为 Memory Engine 2.1，只显示人物摘要目录、人物对话文件与可编辑摘要数量；删除重复的“人物记忆覆盖／可访问结构化记忆”树。
- 保留“人物目录 → 与 B 的对话 → 摘要记录”层级、正文编辑/删除、按姓名或 ID 搜索、本人目录优先排序、相关参与者与正文检索。
- dashboard 统计改为直接读取内存索引数量，不再为已移除的结构化人物树逐角色重建可访问记录，降低摘要页刷新开销。
- MemoryTrace 新增摘要 Provider 延迟、摘要持久化延迟、召回耗时、候选/入选数量、实际 token 与内部索引大小指标；只记录数字、ID 与错误码，不记录摘要或 Prompt 正文。

### E. 自动验证与发布边界

- 新增 `scripts/test-v7.1-memory-engine.js`，覆盖四名回应者分别从自己的目录召回 E、其他人物目录隔离、群聊镜像去重、提及人数硬上限清零、旧摘要 Prompt 链断开和单一目录 UI。
- `scripts/test-memory-ui.js` 更新为 Engine 2.1 单一目录界面契约；`scripts/test-release.js` 更新为 V7.1 发布门禁，共 14 组回归。
- 本地自动测试不调用真实摘要 Provider，也不伪造 CK3 实机 50 次连续会话。方案中的 50/50 摘要、100 次 Action、100 次 Memory 修改及长时间游玩仍属于发布前实机验收项。

## 第四阶段：v7.2 Memory Engine 2.2 与 P0 收口

### A. 人物目录精确召回

- 新增 `MemoryStore.loadDirectPairSummaries(ownerId, counterpartId)`，A 与 B 对话时不再先让 A 或 B 的整个目录参与统一排名，而是精确读取当前回应者目录中的“与对方的对话”文件。
- 新增 `MemoryStore.searchOwnerFolderForEntity(ownerId, entityId, entityNames)`，场外人物检索严格限制在当前回应 NPC 的目录内，依次使用关系人物 ID、participants/subjects、人物名称与摘要正文匹配。
- Memory Engine 2.2 将召回拆为直接关系、场外人物和内部稳定记忆三条通道。一对一默认最近 2 条加相关 1 条；多人对话为每个其他在场者保证 1 条，再补充全局相关 2 条；每个场外人物默认 1 至 2 条。
- 直接关系占基础预算 55%，场外人物占 30%，稳定记忆占 15%；某类不存在时预算流向现有关系通道。总预算为上下文约 8%，限制在 800–2400 token。
- 多人过多时优先缩短单条摘要而非用固定 `slice(0, N)` 丢弃整个人物；同一群聊镜像仍按 `finalizationId` 去重，并保留它所覆盖的多个关系人物 ID。

### B. 全发言者场外人物识别

- 新增 `MentionTracker`，按消息 ID 增量处理会话历史，每条消息只扫描一次。
- 玩家和 NPC 的发言都可以把场外人物加入当前会话集合；NPC 在本轮提到 X 后，尚未回复的其他 NPC 会分别从自己的目录召回 X。
- 当前玩家、当前回应者与全部在场人物从场外人物集合排除，避免直接参与者重复进入第三者通道。
- 提及人物数量没有固定上限；同名匹配仍优先依靠人物 ID 和已经加载的明确人物资料。

### C. 连续会话摘要 P0

- 新增 `FinalizationCoordinator`。结束会话时先分离旧 `Conversation`，再将其终局任务按会话 ID 去重并串行入队；新会话可以立即建立，但不会与上一场共享历史、参与者或 `finalizationId`。
- `ConversationManager.endCurrentConversation()` 不再直接丢弃 `finalizeConversation()` Promise，并提供 `flushFinalizations()` 与待处理计数。
- 应用退出时先结束当前会话并等待终局队列排空，再执行真正退出，降低最后一场摘要在进程关闭时丢失的风险。

## 第十三阶段：v7.7.1 Memory Engine 2.3

## 第十四阶段：v7.7.2 候场加入与主动离场

- CK3 已选择的 NPC 默认继续全部在场，保持既有双人和多人流程不变；首句发送前，聊天面板可把非最后一名在场 NPC“设为候场”。
- 候场人物不进入回应队列、不注入当前关系或记忆、不写入 `knownBy`，整场从未入内的人物不会成为终局参与者。
- “请入内”插入 `【人物入内】` 系统消息并从该消息 ID 打开人物在场窗口；加入当轮不热插队补话，从下一轮参与回应。
- “请离场”插入 `【人物离场】` 系统消息并使用半开区间 `[joinedAtMessageId, leftAtMessageId)` 关闭窗口。离场后立即请求该角色的离场前摘要；离场标记及后续内容不会进入该角色的提示词、知情集合或最终配对摘要。
- Memory Engine 2.3 的抽取提示、Knowledge `knownBy` 和 `owner × counterpart` 投影都要求引用消息位于相关人物的共同在场窗口内，防止迟到者获知入场前秘密或离场者记录后续密谈。
- 当前在场名单放在历史消息之后、当前用户消息之前，属于动态后缀，不改变 history 前稳定区块的聚合指纹。动作脚本造成的自然离席也会关闭同一人物窗口。
- 同一人物主动离场后不允许在本场重新入内，并至少保留一名在场 NPC。该约束避免重复窗口导致回应队列和冻结记忆重新排序。
- 新增 `scripts/test-v7.7.2-staged-presence.js`，覆盖缺省兼容、候场、入内不插队、主动离场即时摘要、动作离席、离场后内容隔离、2–6 人有向视角投影、缓存前缀及 UI/IPC 合同。发布门禁增加到 35 组、测试文件增加到 68 个。
- 详细实现和实机验收边界见 [VOTC_v7.7.2_候场加入与主动离场实施记录.md](VOTC_v7.7.2_候场加入与主动离场实施记录.md)。真实 CK3 参与者选择、聊天按钮点击与 Provider 摘要质量仍需发布前实机冒烟。
