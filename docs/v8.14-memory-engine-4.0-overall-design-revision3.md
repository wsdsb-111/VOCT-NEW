# VOCT V8.14 — Memory Engine 4.0 总体设计稿（Revision 3）

> 状态：**设计方案，尚未实施或验收 V8.14**。本稿根据《V8.14_Memory_Engine_4.0_总体设计稿_Revision2.md》和现有 V8.13.2.2 代码审阅修订。文中的字段、目录、预算和 Gate 是目标合同，不代表当前应用已具备。VOCT 为本文沿用的项目名；仓库界面名称为 VOTC。

## 1. 目标、现状与责任边界

Memory Engine 4.0 以 Campaign 隔离、NPC 本人可知的 Detailed Durable Entry 为长期事实单位；对话叙事、人物认知和当前世界状态各有独立来源。普通对话可以产生零条长期事项，但不能因此抹掉实际发生的对话。

| 问题 | 权威来源 | 不允许的推断 |
| --- | --- | --- |
| 我是否认识 C、以何种方式认识 | Known Entity Index 中有来源的认知证据；当前明确关系可补充 | Life/Year 没写 C，所以不认识；索引无记录，所以从未认识 |
| 我与 C 现在是什么关系 | 当前可靠的 CK3／关系事实；未知则明确未知 | 用旧记忆中的称谓改写当前关系；把关系标签解释成具体起因 |
| 我经历或获知过什么 | 本人合法可见的 Detail、官方追忆、Year/Life 与 Legacy | 读取 C 的私人记忆代替 B 的记忆；把转述当亲历 |
| C 当前是什么状态 | 有知情授权的 Current Runtime Truth／Worldline | 用历史记忆覆盖现在；系统可读就等于 NPC 知道 |

现有可复用基础：Memory Engine 3.0 的 `schemaVersion: 2` 人物摘要与 Recent2、官方追忆覆盖文档、Extra≤3、双时间轴与 Temporal Focus、在场窗口与 `knownBy`、内部结构化记忆、V8.13 冻结前缀及动态尾部。内部抽取已同时生成详细叙事与高价值事项，4.0 是事实单位、索引、派生概览和规划器的升级，不应重复建设同一来源的事实库。

当前代码对照入口：[抽取和结算](../resources/app/out/main/memory-system/memory-engine.js)、[存储与索引](../resources/app/out/main/memory-system/memory-store.js)、[逐角色历史](../resources/app/out/main/conversation/conversation.js)、[双时间索引](../resources/app/out/main/memory-system/summary-date-index.js)、[Prompt 排列](../resources/app/out/main/prompts/prompt-builder.js)；这些链接用于审查现状，不表示目标 Schema 已实现。

V8.13.2.2 的逐篇、当前对话文件及 Owner 目录的 Legacy Campaign Binding 已有 Preview／Commit 实现；它仍需打包窗口和 CK3 实机验收。V8.14 将其作为迁移前置能力复用，不重复开发或将本地测试当作实机 Gate。现有未提交工作属于既有 V8.13.2.2 工作区状态，本文不改变代码。

## 2. 内容层与零事项合同

对用户显示四层记忆内容，另保留会话叙事记录：

1. **Official Recollection**：CK3 原生 `log_memories` 文本；Campaign 与 Owner 绑定，每场按现有机制覆盖，场内按回应者冻结。它记录官方历史经历，不断言事件仍是当前状态。
2. **Detailed Durable Entry**：NPC 本人知道、对未来仍有意义的最小事项。可为承诺、关系实质变化、重要知识、重大经历、长期目标或关键情感节点；一场允许零条。事件起因、条件、结果要短而准确。
3. **Year Digest**：有日期证据的 Detail 在某事件年的可重建概览；无事项的年份不创建空文档。
4. **Life Chronicle**：按人生阶段或跨年趋势浓缩的可重建概览；不是通讯录，也不是判断是否认识某人的依据。

**Conversation/Episode Narrative 与 Recent2 保留为独立的近期连续性来源。** 它们可以记录普通闲谈、未达到长期准入门槛的计划讨论、话题衔接和多人各自见闻。`NO_DURABLE_CONTENT` 只表示本场没有新的长期事项；合法叙事仍应落盘、按 Owner 投影，继续参与 Recent2、Legacy 查看与认知证据。不得用 Durable 的空数组触发“详细摘要缺失”质量错误，也不得用“有摘要”强迫产出一条 Durable。

抽取结果为每个 Owner 单独给出：`NOT_PRESENT`（无合法可见正文）、`NO_DURABLE_CONTENT`（成功检查但零事项）、`STORE`（一条或多条通过门禁）、`EXTRACTION_FAILED`（模型、格式、来源或持久化失败）。`NOT_PRESENT` 不等于从未认识该人；`EXTRACTION_FAILED` 保留可重试快照，不能伪装成成功空结果。结算时详细叙事和 Durable 决策是两个独立质量结果。

长期准入拒绝普通寒暄、重复对白、流水账及可直接由当前 CK3 读取的金钱、位置、职位快照。过去的任职或迁居是历史事件，可以保留事件时间与来源。单场建议普通 0～4、重要 0～6、重大剧情最多 8 条；数据集上的 Durable 文本平均目标为原详细终局叙事的 ≤20%，**不能作为单场硬截断规则**。重要的否定、承诺条件、参与人和因果不得为达比率而丢失。

## 3. 逐 NPC 可见正文与知情门禁

以现有消息 ID、分段在场窗口、入场／离场／暂离／返回、睡眠／昏迷状态为第一层确定性过滤。每个 NPC 的可见正文按原始消息顺序形成，其源 ID 不重新编号；恢复和分块仍使用原 ID。

仅按“人在场”保留整条消息不足以保护私密内容。对一条同时含公开言语与内心活动的消息，应先按已有可见性标注、叙事片段来源和获知对象分片；无法可靠分开时不得把私密片段授予旁观者，也不得用模型猜测谁听到了秘密。返回提示只能说明本人暂离／昏迷后回来，不补发缺席期间发生的事情。

每条拟存 Detail 必须满足：所有 `visibleMessageIds` 真实存在、严格递增、属于该 Owner 的合法可见片段；来源正文支持所写人物、行为、时间、否定和条件。模型负责提议内容，代码负责 ID、Presence、Campaign、Owner 和可见性校验；无足够可见证据时拒存，保留诊断／恢复。逐 Owner 抽取可以复用一次结算中的源解析，但不能把其他 Owner 的可见切片或 Prompt 结果直接复制过来。必须验证额外调用量与结算时间。

`participantIds` 表示实际行动／在场者，`entityIds` 表示被谈到的人物或其他实体。场外 C 可作为 `entityId`，需要可信身份解析和本人知情证据；不能为了索引 C 而把 C 加进本场参与者、在场窗口或 `knownBy`。转述须标明谁告诉了谁；直接目击、听人讲述、传闻和推断不可合并为同一种来源。

## 4. Canonical Detail 与时间合同

下面是**目标结构示例**，不是既有磁盘 Schema。V8.14 可见版本为 `4.0`；旧人物目录和 `schemaVersion: 2` 摘要保持可读，Sidecar 使用独立的 `memory4SchemaVersion`，不就地改写旧文件。

```json
{
  "memory4SchemaVersion": 1,
  "entryId": "mem4_example_001",
  "revision": 1,
  "campaignToken": "<current-native-token>",
  "ownerId": 81358,
  "sourceConversationId": "conversation_example",
  "sourceFinalizationId": "final_example",
  "sourceSummaryIds": [],
  "visibleMessageIds": [11, 12, 13],
  "counterpartIds": [47689],
  "participantIds": [81358, 47689],
  "entityIds": ["char:81358", "char:47689"],
  "memoryType": "COMMITMENT",
  "text": "上官德俊答应在未来北伐时协助后勤与情报。",
  "conversationDate": "1158.8.11",
  "conversationTotalDays": 423112,
  "acquiredDate": "1158.8.11",
  "eventTime": { "from": "1158.8.11", "to": "1158.8.11", "precision": "day", "status": "observed" },
  "temporalRefs": [{ "role": "EVENT", "from": "1158.8.11", "precision": "day" }],
  "topics": ["北伐", "承诺"],
  "locationEntityId": null,
  "evidence": { "source": "spoken", "epistemicStatus": "asserted", "confidence": 0.86, "visibility": "participants", "knownBy": [81358, 47689] },
  "importance": 0.86,
  "state": { "status": "active", "supportedByEntryIds": [] }
}
```

`conversationDate` 是何时谈起；`acquiredDate` 是 Owner 何时获知；`eventTime` 是被记录的事件何时发生／将发生，并区分 `observed`、`reported`、`planned`、`unknown`。示例中 1158 年发生的是**作出承诺**，北伐本身尚未发生、也没有可确定的实施日期；两者不得混为同一件已发生事件。不能把计划日期写成已发生的事实，也不能把未知事件日默认为对话日。现有 `temporalRefs`／双时间解析可作为输入；对相对时间仍以本场 CK3 游戏日期为锚，不使用电脑日期。`totalDays` 仅在来源合法且可验证时用于排序。

来源分类、可信度、认知状态、可见性、知情对象、编辑版本和删除状态必须保留现有内部记忆可表达的语义。单一 `directness` 无法替代它们：“B亲耳听C说D已死”证明 B 听过此话，不证明 D 已死。重复抽取以 Owner、Campaign、来源 Finalization、源片段和规范化事实键幂等；不同事件即使来自同一终局也不能互相去重。

承诺状态至少 `active / fulfilled / cancelled / superseded`，每次变化记录来源证据与时间；只是后来未再提及不能自动视作已履行。当前状态未证实时，应表达为“仍有当年承诺记录，是否已履行不明”。

## 5. Known Entity Index 与 Profile

Known Entity Index 是代码维护的**认知证据索引**，不占用独立摘要或固定 Prompt 层。键为 `campaignToken × ownerId × entityId`；存来源 ID 和可核验的交互计数、首次／最近时间，以及观测范围是否完整。相同 Finalization 的多份有向摘要、分块、恢复重试与镜像必须去重。

目标记录示例：`{ campaignToken, ownerId, entityId, evidenceTypes, directConversationCount, sharedSceneCount, mentionCount, firstSeenDate, lastSeenDate, sourceEpisodeIds, evidenceCompleteness, sourceRevision }`。上述日期在原资料缺失时为 `null`，次数在证据不完整时不得渲染成“总共仅有这些次”；索引按源版本重建，不作为不可更改的事实原本。

认知等级按证据区分：`DIRECT_RELATIONSHIP`、`DIRECT_INTERACTION`、`DIRECT_OBSERVATION`、`MENTION_ONLY`、`UNKNOWN`。等级是表现方式，不是来源本身；应同时保存多个证据类型。当前明确配偶、亲属或正式关系可以支持认识，不能从关系标签猜测关系形成经过。仅同场并不必然直接交谈；只有验证过实际双向或单向可见互动，才增加 `directConversationCount`。合法共同可见场景只增加 `sharedSceneCount`；在他人谈话里听到 C 仅增加 `mentionCount`。

旧“与C的对话.json”是 Owner→Counterpart 的人物视角投影，**不能单凭文件存在推断直接对话七次**。重建索引优先读取 Episode、原始消息、在场／可见证据；旧摘要只能提供有限证据，并标注 `evidenceCompleteness: partial`。`UNKNOWN` 表示目前无可确认认知证据，不能在模型 Prompt 中硬译为“我从未认识C”。若 Candidate 实体只有同名而身份未解析，不能合并 ID 或计数。

Known Entity Profile 按需把该索引、当前可靠关系、合法可见的 Worldline／CK3 数据、Memory4／Legacy 指针合并。Profile 可缓存其结构化导航数据；当前生死、职位、关系等随当前事实读取并经知情门禁，不得作为永远有效的旧字段持久化。Profile 整体不进 Prompt；只有问题需要时，才在动态尾部渲染极短的来源限定结论，如“曾直接交谈；当前关系证据未知”。认识某人不自动赋予其当前位置等私人当前事实的知情权。

关系变化触发：必须有同 Campaign、同人物对、可比较的前后可靠状态及变化来源，才记录 `relationshipChangeDetected` 并提高抽取优先级。数据缺失不等于 `neutral`；动作仅 ACK 不等于关系已由 CK3 确认改变。关系改变但可见正文不含原因时，可记录变化，不许编造“背叛”等起因。没有正式关系标签变化的重大事件也可以产生 Detail。

## 6. Year Digest 与 Life Chronicle

Year Digest 以 `campaignToken × ownerId × eventYear` 为默认事实概览键，只有可信事件时间的 Detail 才进入事件年；未知事件时间放入待定时间索引，不能借用 conversationYear 填空。按“那年我们聊过什么”查询时，使用独立的 Conversation-Time 索引访问当年对话或 Detail 的获知时间。跨年事件标出区间与时间精度，不悄悄复制成多个确定日期事实。

年度 `items` 保存短文、`sourceEntryIds`、实体／主题、时间轴、来源与可信度；一个事件由多条 Detail 合并时仍保留所有来源。只在当年新增／更正 Detail 后标记 dirty；超预算或重复度过高才压缩。落盘目标 300～700 Token、建议硬上限 1000 Token；Prompt 中 Overview 只提取相关 300～400 Token 子片段，不整篇强塞。

Life Chronicle 按人生阶段／跨年趋势概览，记录派生自哪些 Year Items 或 Detail，不能凭压缩文本新增人物关系或事件。它不负责识别“是否认识C”。旧年份可逐步压缩为十年／人生阶段片段，但查询具体年份或日期时仍以可追溯 Detail、Year 和旧摘要为入口。Year、Life 都是可重建视图，Canon 为 Detail、官方来源及未迁移的 Legacy。

任何 Detail 编辑、状态变化或删除，先更新 Canon 与索引，再令相关 Year／Life 变脏；变脏项在重建前不得以旧正文作为当前有效来源继续召回。重建结果携带源版本集合；若生成期间源版本变化，丢弃过期结果重新排队。人工修改 Year／Life 需标注覆盖来源、与自动重建的合并／冲突规则，不能静默覆盖用户手工文本。删除还要失效 Profile、召回缓存、Prompt 历史中对应动态副本以及所有 Legacy 桥接映射；下一轮不能从派生视图“复活”已删除事项。

## 7. Recall Planner 与真实状态

先做硬门禁，再排序。硬门禁包括：Owner/Campaign、身份解析、本人知情、可见性、来源有效版本、删除状态，以及明确年份／日期和时间轴的匹配。任何 Topic、重要性或关系加分都不能越过硬门禁。精确日期未命中时说明没有可确认记录；不得拿邻近年份高分事项补位。

查询解析为独立的 `axis = EVENT / CONVERSATION / MIXED / MEMORY_RECALL` 与 `granularity = LIFE / PERIOD / YEAR / EVENT / EXACT_DATE / FOLLOW_UP`。不明确时保留轴的不确定性并做受预算约束的双轴候选；不能把“记得五年前”直接解释为最近或最重要的对话。`PERIOD` 是明确区间查询：选跨年 Life 阶段概览，或在一个 Overview 内聚合可验证的相关年度片段，保持同一 0～1 概览槽，不逐年新增槽。`FOLLOW_UP` 沿已成功回复确认的 Temporal Focus，约束同一人物／主题／事件链寻找后续事实；不只选日历上最近一条。

每名 responder 的动态 Packet 最多 `Overview ×0～1`（Life 或 Year）与 `Detail ×0～2`。多人独立查询本人 Owner，互不共享 Packet；多实体也共用同一 2+1 总槽，不按人物倍增。优先一条合法 Detail 覆盖多个问及实体。Life/Year 决定回答粒度；同一粒度内按证据权威、时间／人物／主题相关性、参与方式、置信度、冗余及当前提问者关联排序。因此“先 Life 后 Detail”不是让较粗视图覆盖较强的具体证据。

| 查询 | 首选内容 | 限制 |
| --- | --- | --- |
| “你这一生经历过什么？” | Life + 最多 1 条代表性 Detail | 不用 Life 列出所有认识的人 |
| “你还记得1158年吗？” | 1158事件年 Year + 最多 2 条 Detail | 对话年问题改用 Conversation-Time |
| “1158年8月11日发生什么？” | 当日 Detail；必要时 Legacy 精确命中 | 无命中不拿1159年替代 |
| “后来呢？” | 当前焦点的下一相关 Detail | 焦点只在成功回复后提交 |
| “还记得C吗？” | Profile先定认知方式，再查B本人 Detail/Year/Life/Legacy | C的私人目录不作为B的证据 |
| “C现在还是朋友吗？” | 当前可靠关系；Memory只补历史缘由 | 当前关系未知时不得靠旧记忆硬判 |
| “C现在成都，十年前呢？” | 获准使用的当前事实 + 历史Detail/Year | 过去临安不否定现在成都 |

第三人来源排序基于 responder 本人的合法证据：亲自交谈／共同可见事件、合法被告知、本人年度／人生派生项，再至本人 Legacy；不能使用 C-owned 私密文本。对“为什么恨C”，当前 `enemy/rival` 只能回答关系状态；原因必须另有可验证的 Detail、官方事件或合法世界事实。Official、Detail、Year、Life 没有全局恒定权威顺序：判断**当前状态**以获准的当前 CK3 事实为准；判断**历史 CK3 事件**优先其直接官方证据；判断**对话中的承诺／私密动机**以可见对话来源为准。派生概览绝不高于自己的源证据。

## 8. Prompt 预算与缓存合同

沿用本场首次生成时冻结的 Memory Engine 总预算：二人 `min(上下文10%, 3600)`、三人 `min(12.5%, 4500)`、四人及以上 `min(15%, 5400)` Token；计数含玩家。本场各 responder 共用这个额度上限，实际内容各自私有。现有官方追忆、Recent2、内部稳定记忆及冻结世界线布局保持会话级稳定；Memory4 的 Overview、Detail、可见的 Profile 极简说明与 Legacy 补充占**同一动态剩余额度**。

```text
Memory4 实际动态上限
= min(设计硬上限 1200, 本轮 Memory Engine 总预算减冻结已用额度,
      Provider 当前请求剩余安全额度)

该上限包含 Overview、Detail、Profile 简述、Legacy 补充和必要来源说明；
Overview 建议 ≤300～400，单个 Detail 建议 ≤300～400，0～2 个 Detail。
```

原设计“900～1200”表示建议工作区间，**1200 是硬上限**，不是保证能拿到的固定预算。Year落盘上限1000不等于可在单轮输入1000。候选不足则留空。Legacy回退不能绕开2+1槽位及总 Token；旧 `Extra≤3` 的候选统一接入新Planner并避免重复注入。

Legacy 命中若对应一段年度概览，占用 Overview；若对应一项具体旧事件，占用 Detail。仅截取有来源、与问题有关的片段，不能把整篇旧摘要伪装成一条 300 Token Detail；无法安全切分时在预算内保守裁剪并保留来源提示，必要时报告证据不足。

新动态块必须位于 V8.13 Cache Boundary 后、先前成功注入的动态召回要继续沿本人私有 Prompt 历史保留；历史压缩移除对应副本后才能重召回。不能只比较一次 `PrefixFingerprint`：同一会话、同一 responder 的冻结前缀文本和指纹都应稳定；升级后新会话可有合法新内容。任何冻结块内容、位置、Block ID 或缓存锚变动都应单独作为兼容性变更评估。真实 `cached_tokens`、命中率、TTFT 和请求长度需做 Provider A/B，不能由静态布局推定收益。

## 9. 存储、索引与一致性

优先沿用现有**单条 JSON + 元数据索引**模式；Revision 2 推荐的 JSONL 在需要编辑、删除、承诺状态更新和原子回滚时会引入版本追加、tombstone 与压实复杂度，暂不作为 V8.14 默认格式。若性能基准证明单条文件有实质瓶颈，再单独评估 JSONL，不改变逻辑 Schema。

```text
现有人物目录（原摘要文件继续可读）
├─ 与C的对话.json
├─ 官方追忆摘要.json
└─ memory4/
   └─ <campaign-key>/                # 由原生 Campaign Token 安全映射，不用名称猜测
      ├─ entries/<entry-id>.json      # Canonical Detail
      ├─ years/<event-year>.json      # 可重建视图
      ├─ life.json                    # 可重建视图
      ├─ known-entities.json          # 可重建索引
      ├─ index.json                   # 可重建的稀疏元数据/倒排指针
      └─ metadata.json                # Schema、源版本与状态
```

索引最少按 Owner/Campaign、实体、主题、事件时间、获知／对话时间、Counterpart、Entry状态与来源版本定位；1000+ Detail 单轮查询只读索引筛过的少量正文，不全量打开每条文件。检索延迟与磁盘读取次数应设基线并在 1000+ 项数据下验证。`index.json` 仅是可重建加速层，失配／损坏时不得把不完整索引当作“此人不知道”，应降级到有界恢复或明确失败诊断。

一次写入以 Campaign、Owner、Finalization ID 与版本为范围，保留可恢复的提交状态：先确认源身份与可见性，再提交 Detail／Index，最后更新派生 dirty 标记；宕机或部分失败时只允许重做缺失阶段，不重复生成事项，也不发布指向未提交正文的指针。持久删除需有可核验的删除／撤销记录与索引失效，且不能被后台重建、旧缓存或迁移重试重新加入。用户运行时文件、存档、日志、Provider数据均不属于仓库内容。

## 10. Legacy Bridge 与迁移

现有 2.5 人物目录、`schemaVersion: 2`、编辑／删除合同保持兼容。没有可确认原生 Campaign 的旧摘要维持 unresolved，不参与已知 Campaign 的正式召回；逐篇与批量绑定都必须按当前真实存档确认、预览再提交。一个活动对话未加载 Campaign 时不能冒用上一场的 Token。

启用Memory4召回的第一阶段就需要 Legacy Bridge，防止尚未转化的历史失忆。先从同一 Owner／Campaign 的旧摘要按事件／对话双时间轴检索；首次实际命中、用户手动触发或空闲时可惰性重压缩，但只转换有来源支持的片段。空闲任务只能处理已确认Campaign且无编辑竞争的条目。

去重采用 `sourceSummaryId + sourceFinalizationId + sourceMessageIds/segmentIds + event identity` 的覆盖映射。一个 Legacy 摘要可能含多件事：只转换其中一件时仅排除该件的重复文本，**不能排除整篇剩余内容**。同一Finalization也可以有多条不同事件。原摘要若缺逐段来源，迁移结果标记较低可验证度，不凭模型猜测隐藏参与者或精确日期；无法安全拆分时保留Legacy而不强制转换。Legacy编辑／删除后，来源映射及派生视图必须失效并重审，不能靠已转换副本逃避删除。

UI建议在原NPC摘要目录下增加认知导航、官方追忆、人生、年度、Detail、Legacy分区；Known Entities 显示证据方式与计数是否完整，而非伪装为第五种摘要。先支持只读和来源诊断，再上线可编辑／删除及从源重建；UI新增路径需要三主题（内部键 `parchment`／`knight`／`ink`，用户可见为“游牧”／“骑士”／“水墨”）可读性与打包窗口验收。

## 11. 施工顺序、诊断与验收

**A：基础合同与Durable Core。** 保留现有叙事／Recent2；实现逐Owner可见片段、零事项四态、Canonical Detail、来源／Campaign硬校验、幂等持久化、删除与恢复、稀疏索引、Known Entity基础证据。Legacy Bridge 与旧路径同时可用；没有这一层不可切换正式召回。

**B：认知与关系。** Profile聚合、Current Relationship／Worldline的身份和知情边界、关系变化的可靠检测；缺失关系不得当成中立。需要分开记录“认识方式”“当前关系”“当前事实是否可知”。

**C：召回。** Axis × Granularity、双时间硬过滤、逐回应者2+1、多实体共享槽、Legacy部分覆盖去重与Temporal Focus；接入V8.13动态尾部、整体预算和私有历史。此阶段即可针对第三人／多人／精确年份进行实机验证。

**D：派生概览。** 按事件年的Year、Life分段、增量压缩、来源版本、编辑／删除失效；后台任务与摘要终局错峰，单个NPC失败不拖住其他Owner。

**E：迁移与UI收口。** 用现有Campaign Binding完成真实存档验收；惰性重压缩、覆盖映射、只读诊断到编辑入口逐步启用。无需重做V8.13.2.2功能。

Revision 2 的官方追忆精确动态查找、自动十年压缩调优、置信度衰减、传闻置信传播、跨年主题图及高级手工编辑保留为后续增强；不得作为替代本版来源门禁、迁移一致性或验收 Gate 的前提。分阶段上线时 A～E 各阶段有独立回退入口，不能因某层数据未就绪让旧摘要失效。

每轮诊断最少给出：Owner/Campaign、认知来源与完整性、Axis/Granularity、目标时间及时间轴、候选各层数量、Campaign／知情／日期／状态拒绝数、选中来源ID、Legacy覆盖范围、Token实际占用、派生版本／dirty状态，以及是否发生降级。默认不写玩家完整问题或摘要正文到诊断。新旧请求并排比对结算耗时、Provider调用数、Token、Prompt缓存和召回准确度。

**Freeze Candidate 的必要 Gate**：

1. Late Join、Early Leave、暂离、私密思想均不泄露，且不漏记合法可见内容；逐Owner来源ID可核查。
2. 普通闲谈 `NO_DURABLE_CONTENT`，详细叙事与Recent2仍可用；模型失败保持可重试，不能被计作零事项。
3. 关系变化、承诺条件、否定、来源语气在压缩后保留；固定样本集的平均精简目标≤20%，不为比率删除重要事实。
4. B曾与C直接互动但Life/Year无C时仍可正确认出；仅同场、仅被提及、仅关系、证据缺失四种情况分别正确表述；同场多投影不重复计数。
5. 第三人不读取第三人私有Memory；多个NPC的Packet、知情、现时授权完全独立。
6. Event-Time和Conversation-Time分别命中；五年前、精确日期、跨年区间、后来呢不回退到无关年份或事件链。
7. 当前CK3状态与历史证据各按所问时间、事实类型和知情权限使用，转述不变成亲历或已证实事实。
8. 每名回应者多实体共用 Overview≤1、Detail≤2；动态块含Legacy与Profile总计≤1200，且不突破Memory Engine及Provider剩余预算。
9. 新旧摘要Campaign隔离；Legacy部分转换后未覆盖的事件仍可召回；删除／编辑不会被Year、Life、缓存或恢复任务复活。
10. 1000+ Detail候选不全量读取正文，索引损坏可诊断和恢复；多人结算时长、额外Provider请求与失败重试都有量化基线。
11. 同场同Responder冻结内容及Fingerprint稳定；真实Provider A/B的`cached_tokens`、TTFT和输入总量无不可接受回退。
12. 完整发布测试与打包Electron、CK3真实存档、多人对话、Provider与长时运行各按证据分别通过。代码门禁不能替代后者。

只有上述合同和测试覆盖后才可标记“V8.14 / Memory Engine 4.0 Freeze Candidate”；正式 Freeze 以实际 CK3／Provider／缓存证据签发。本文本身不变更现行 Memory Engine 3.0 的可见版本或存储格式。
