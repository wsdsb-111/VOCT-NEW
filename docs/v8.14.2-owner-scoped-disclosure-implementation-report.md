## 目标与边界

V8.14.2 将“某位 Owner 是否知道另一个人物的一项具体头衔或特质”接入 Memory4 既有的人物认知边界。数据按 Campaign × Owner × Entity × Fact 保存；没有全局公开事实层，不修改 CK3 Trait、Title 或存档。Self、Observed、Known 三通道继续沿用 V8.14.1 合同。

Nickname 默认可见，但不授予真名或精确头衔。Canonical Name 仍由人物身份识别规则决定。头衔默认隐藏；不可观察 Trait 与未知 Mod Trait 默认隐藏，除非当前 Owner 有该事实的有效已知证据。

## 生产实现

Disclosure Scanner 位于 `memory-system/memory4-disclosure.js`，只消费经可见性验证的 spoken fragments。对话来源必须属于 Owner 可知的 public、participants 或 known_group 片段，并带有有效消息/片段来源证据；私密、无效、旁白和 Owner 不可见片段不会参与扫描。信件使用独立的 `validated_letter` 来源证明。

Scanner 只从当前人物结构化资料生成 Title/Trait 候选，并要求正文同时能唯一绑定目标人物、命中其现存候选事实并表达肯定陈述。问句、否定、假设、未来、传闻、含糊指代及无法唯一匹配的别名均 fail-closed；不会凭对话创建 CK3 中不存在的事实。未知 Mod Trait 不会因其类别或名称猜测而成为可观察项。

对话 `finalization_validated_segment` 来源还要求 `sourceTextVerified` 对应原始源文中的逐字段落；摘要改写或仅语义相近的文字不会自动披露。该校验采取保守策略，可能漏标；用户可在人物认知页手工设为 `MANUAL_KNOWN`。本实现不保证每条格式正常的模型输出都会触发披露。

写入复用各 Owner 目录的 `known-entities.json`，在实体下保存 `disclosedFacts`。Fact ID 绑定 Campaign、Owner、Entity、Fact 类型和 key；记录保留获得日期、来源类型、对话/信件 ID、Finalization ID、消息/片段 ID、可见性证明、源文本哈希和 source revision。相同来源幂等更新；Finalization 重建或源 revision 过期时会清理/拒绝过期证据，不从 Legacy 摘要反推披露。

状态包括 `AUTO_DISCLOSED`、`MANUAL_KNOWN` 和 `MANUAL_HIDDEN`。用户手动标记带 expected revision；版本冲突不会覆盖新状态。`MANUAL_HIDDEN` 作为 tombstone 优先于自动证据，`MANUAL_KNOWN` 只作用于该 Owner。Profile 展示始终以当前 GameData 重算：头衔变化不会把旧披露升级为新头衔，已消失 Trait 不再作为当前属性展示，旧证据可留在历史来源中。

`Conversation` 在会话开场按 responder 捕获 Owner-scoped Disclosure Profile。本场新披露在 Finalization 持久化并失效对应 Profile/摘要缓存，下一场对话再读取；不在当前 Prompt 中途改写画像。Cache Anchor、Prompt Block ID、稳定块顺序和 GLM 静态布局未改变，本版本未额外调优 GLM 缓存。

摘要管理器的“人物认知”页展示当前头衔/特质候选、来源和获知时间，并允许逐项设为已知或未知。归档披露只读，不把归档状态冒充当前 CK3 真值。

## 信件来源

游戏收到的原信在 payload 校验成功、并绑定当前 Campaign、玩家、NPC 与有效日期后，先将信件正文作为玩家 → 收件 NPC 的 recipient-only 证据记录；此步骤发生在回复生成之前，因此回复生成失败不会撤销收件 NPC 已合法读到的内容。

NPC 发给玩家的回信使用更严格的确认门：只有 `LETTER_ACCEPTED` 对应的 effect 已实际写入后，接受回调清理输出载体并重新解析 debug.log；随后再次核对 Campaign、双方 ID、原始信件 ID/正文/日期和投递日，验证仍匹配才把回复正文记录给玩家 Owner。仅生成回复或仅出现通用 ACK 不会写入该披露。
