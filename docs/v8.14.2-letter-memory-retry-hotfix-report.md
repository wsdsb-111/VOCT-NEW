## 信件接受与归档

加载入口缺口：Workshop 本体 `common/on_action/votc_load_boundary.txt` 原来仅记录 LOAD_SESSION，没有启动日期 runner。读档后已有 pending、又未发起新对话时，无 runner 读取应用排入的 date re-arm，形成自举断点。现在在 empty-scope `on_game_start` 的 `every_player` 下，延迟一个游戏日触发既有 `mcc_event_v2.9998`。它沿既有 invisible window 清旧/重建固定名 runner，对话场景仍按原规则清理；未提高轮询频率。原版 scope 用法和 Mod UTF-8/结构通过本地静态校验，不冒充游戏脚本执行。

- `LETTER_ACCEPTED` 只有在当前待投递信确有 Effect 写入记录后才完成；旧通知不能消费仅 queued 的回信，也不能提前启动下一封。
- 生产信件不再在生成回信后立即归档双方完整交换。接受后先重验 Campaign、双方 ID、原信 payload、接受日期及到期日，再持久化冻结来源任务，后台请求摘要与每 Owner 的长期提取。
- `letter-memory-finalization.js` 以 Campaign、letter ID、正文/回信哈希幂等保存恢复任务，使用 `GameData.saveRecoveredSummary` 写普通双向摘要目录；typed letter memory 与 episode commit marker 分阶段保存。失败只补未完成步骤，不重新生成已经提交的 Owner，也不重发游戏 Effect。
- 游戏已接受但本地捕获失败时，SENT 状态和冻结原信保留；后续只重试归档捕获。缺少可信接受来源时明确保留待验证载荷，不伪造日期或跨战役绑定。
- 每 Owner Canonical 成功后等待 Year/Life 派生；派生失败保留同一任务，只补派生。未知事件日期不造年份，`NO_DURABLE_CONTENT` 合法保留 Legacy。
- 信件原文以 `validated_letter`、真实 `sourceLetterId` 和源文哈希提供姓名/时间证据，不虚构 conversation message ID 或物理共场。相对日期锚定原信日期，而非收到回信的日期；时间词仍须正文可验证，不以文件日期冒充事件日。

## 摘要重试与重构

- 对话结束后统一重试使用服务端可信 read snapshot 的 Campaign，异步期间仍检查上下文身份及来源哈希。坏输出不代替真正 Provider 重试。
- 模型整理成功后，更新所选 Owner 的 Legacy 投影，再重新提取对应 Detail 并重建 Year/Life。归档来源须具有同 Owner/Campaign 的持久证明，不开放任意归档 Memory4 写接口；Official 继续只读。
- 提取及派生失败复用已有 Memory4 recovery snapshot。已有 Canonical 的派生重试只重建 Year/Life；完整来源事实哈希改变时旧任务不能提交。
- 手工版本保留；部分失败返回 `summaryUpdated`、Canonical 与 Derived 各自状态，不再宣称整条链完成。前端确认、恢复计数及结果文案已同步，信件记忆重试不重发信件。
