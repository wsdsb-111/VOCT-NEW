# Source Guidelines for the V9.3.9 Candidate

`src/app/` is the editable runtime source. `scripts/build-runtime.js` maps Main, Preload and Renderer to `resources/app/out` and default assets/package metadata to `resources/app`. Edit source first; generated resources are kept for direct VOTC.exe use and existing contract tests, then verified against the build.

Preserve JavaScript structure, Prompt bytes, cache IDs, IPC keys and the existing protocol 3.0/storage 2.5 contracts. The V9.3.9 candidate presents historical conversation memory as `Legacy Summary`; the fixed player baseline requires full Recent2, legal official recollection and the complete legal player Pair ledger. Explicit player historical clauses may combine up to 5 temporal summaries for 2/3 participants or 3 for 4+ participants and up to 3 third-person summaries total across targets, subject to current Owner/Campaign/Forget/source/revision permissions. The 2/3/4+ participant limits are 65%/70%/75% of the configured context window and 80,000/84,000/96,000 Tokens, further limited by available non-memory prompt space, output reserve and actual Provider headroom. Compact older conversation through the existing mechanism first; if complete sources still do not fit, stop before transport and expose needed, available and component budgets. Context usage is dynamic to the configured window, scoped to conversation and responder, updated each turn, and must distinguish provisional estimates from the last request's actual usage. Do not reintroduce Memory4/Durable production extraction, recovery, recall or writes, Sidecar reads/writes, Year/Life generation or background rebuilds. Pair important-matter indexing uses the shared `src/app/shared/pair-important-matters.js` parser; Renderer code must call `VOTCPairImportantMatters.parseImportantMatters()` when available and return no parsed rows when the global is absent, rather than copy parser rules. Keep Legacy data in existing summary files and index transactions. V9.3.9 implementation evidence is linked from `docs/current/v9/V9_3_9_IMPLEMENTATION_REPORT.md`; V9.3.7 reports and the V9.3.5 index/source contract remain historical and compatibility references.

All payload files are listed in `build/runtime-inputs.json`. Add deliberate source files there using the existing mapping; report the final mapping from actual build evidence rather than hardcoding an unsettled count here. No secrets, user profiles, saves, logs, summaries, untracked local artifacts or Three-Mod code may enter source or build outputs. Source bytes are preserved by `.gitattributes`; do not normalize Prompt content.

Build tools use Node built-ins only. Runtime dependencies remain vendored in `resources/app/node_modules`, checked by `build/runtime-dependencies.lock.json`; do not install, upgrade or rebuild native dependencies as part of a source build. The existing Electron shell is reused, not rebuilt from Electron source.

V9.3.7 age and kinship facts require source-bound CK3 evidence. Calendar-only ages remain diagnostics; UNKNOWN must not become absence. Public otherParent and current step-family facts never grant Memory access. Current step-family requires fresh current marriage and complete public parents; reject explicit death, life conflicts, secret or ambiguous evidence. Historical Legacy facts retain their original authorization; do not infer historical step-family from former spouses. New exporter fields require a fresh CK3 export.
